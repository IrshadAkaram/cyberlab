GraphQL Security (Introspection & DoS)

GraphQL ek flexible query language hai jisme client decide karta hai ki use kaunsa data chahiye via a single /graphql endpoint. Par yahi flexibility vulnerabilities create karti hai: agar Introspection open ho toh attacker pura internal schema dump kar leta hai, recursive queries se CPU/RAM crash (Denial of Service) kar sakta hai, aur alias batching se rate limits bypass ho jate hain. GraphQL empowers clients to request exactly what they need through a unified /graphql endpoint. However, this architectural flexibility introduces severe attack surfaces: unhardened introspection exposes hidden schemas and admin mutations, unbounded circular queries trigger CPU/memory Denial of Service, and alias batching easily bypasses perimeter rate limiters.

Without strict depth limits and complexity scoring, any client can author a catastrophic denial-of-service attack!"

1
GraphQL kya hai? What is GraphQL?
GraphQL ek API language hai jo Facebook ne banaya. Isme sirf ek endpoint hota hai /graphql, aur client decide karta hai ki use exactly kaunsa data chahiye — zyada bhi nahi, kam bhi nahi. GraphQL is an API query language built by Facebook. It has just one endpoint /graphql, and the client decides exactly what data it wants — no more, no less.
2
REST se alag kaise hai? How is it different from REST?
REST me alag-alag URLs hote hain (/users, /orders). GraphQL me ek hi URL se sab kuch milta hai. Aap khud query likhte ho — server sirf sunke jawab deta hai. REST has separate URLs for each resource. GraphQL has one URL for everything. You write the query describing what you need, and the server replies with exactly that.
3
Problem kya hai? What is the security problem?
GraphQL me ek built-in "X-Ray machine" hoti hai jise __schema kehte hain. Default ON rehti hai. Koi bhi ise use karke poora server ka map download kar sakta hai — sare hidden functions, secrets, sab! GraphQL has a built-in "X-Ray machine" called __schema that is ON by default. Anyone can use it to download a complete map of your server — all hidden functions, admin mutations, everything!
4
Server crash kaise hota hai? How can a server be crashed?
Attacker ek "infinite loop" query bhejta hai — user ke orders, har order ke users, har user ke orders... Server ise ek real request samajhta hai aur database queries karta rehta hai jab tak RAM khatam na ho jaye aur crash ho jaye! Attacker sends an "infinite loop" query — user's orders, each order's user, each user's orders... The server treats it as a real request and keeps hitting the database until it runs out of RAM and crashes!
💡
याद रखें: REST me ek hacker ko 100 alag URLs probe karni padti hain. GraphQL me sirf 1 request se woh pura server ka blueprint pa leta hai. Isliye GraphQL Security zyada important ho jaati hai! Remember: In REST, a hacker must probe 100 different URLs. In GraphQL, just 1 request gives them a complete server blueprint. That's exactly why GraphQL Security matters more!

Imagine a classic restaurant (REST API) with fixed printed menu cards. Each item has its own page; you can only order what's listed. The kitchen's internal processes remain hidden from customers.

Now the restaurant introduces a "Magic Menu" (GraphQL)! Customers hand the waiter a custom slip saying: "Give me the chef's name, full recipe, secret ingredients, and staff salaries — all in one trip!" The waiter obeys without any validation.

This is GraphQL's Core Security Problem: An attacker sends a special __schema order and the waiter (GraphQL engine) returns your entire kitchen blueprint — every mutation, hidden admin operation, and resolver argument — in one second. Then the attacker sends a Circular Query that traps the waiter in an infinite loop until the kitchen (server) crashes from memory exhaustion!

🔍 Introspection Schema Leak

GraphQL ka built-in __schema endpoint enabled hone par koi bhi attacker bina authentication ke tumhara poora API map kar leta hai — sare queries, mutations, hidden admin functions aur object types ka blueprint 1 second me download ho jata hai. When __schema introspection remains enabled in production, any unauthenticated caller receives a complete architectural blueprint of your API — every query, mutation, hidden admin field, and object type — in one round trip.

🔄 Circular Query DoS

Attacker circularly nested query bhejta hai — user { orders { user { orders { ... } } } }. Har nesting level par resolvers ek aur database query trigger karte hain. Bina depth limit ke server memory exhaust hokar crash kar jaata hai. An attacker nests circular relations — user → orders → user → orders — dozens of levels deep. Each nesting level triggers additional database joins. Without a query depth limit, server memory and CPU are exhausted, causing a complete OOM crash.

📦 Alias Batching Bypass

Ek single HTTP POST request me attacker 500 alag alias queries bhej sakta hai (a1: login(...), a2: login(...)). WAF ke liye ye 1 request hai, lekin server ke liye 500 separate operations. IP-based rate limiting completely bypass ho jaati hai. A single HTTP POST can contain 500 distinct aliased operations (a1: login(...), a2: login(...)). Network-level IP rate limiters count 1 request, but the server processes 500 database operations — completely bypassing all perimeter-layer brute force protections.

🔐 Missing Resolver Authorization

REST me authorization ek central middleware me hoti hai. GraphQL me har resolver alag hota hai. Ek bhi resolver me authorization miss hone par, attacker nested query ke zariye sensitive data leak kar sakta hai, chahe parent query protected ho. REST centralizes authorization in route middleware. In GraphQL, every resolver must independently enforce authorization. Missing a check on a single nested resolver allows attackers to reach sensitive data via deep queries, even when the parent field is properly protected.

GraphQL Internal Execution Lifecycle

GraphQL server par request kaise process hoti hai aur attacker kis step ko target karta hai: Understanding the internal execution pipeline of a GraphQL engine reveals where security boundaries fail:

PHASE 01
1. Parse & AST Generation

Incoming string query is lexed and converted into an Abstract Syntax Tree (AST). Syntax errors are trapped here.

PHASE 02
2. Schema Validation

AST is validated against the defined schema types. Crucial Security Step: Query Depth & Complexity rules must execute here before resolvers run!

PHASE 03
3. Resolver Execution

Individual resolvers (parent, args, context, info) execute in parallel. If field-level auth is missing, data is leaked to the response payload.

🎯 Comprehensive GraphQL Attack Taxonomy

🔍

1. Introspection & Schema Extraction

GraphQL ka built-in introspection feature __schema aur __type meta-fields ke zariye attackers ko pure backend schema ka interactive map de deta hai. Attacker GraphQL Voyager ya InQL use karke administrative mutations, internal fields aur unreleased APIs discover kar leta hai. GraphQL's native introspection features allow attackers to issue queries against __schema and __type to recover the entire backend schema. Tools like InQL or GraphQL Voyager automatically visualize all hidden mutations, deprecated fields, and private arguments.

💣

2. Nested Recursive Query DoS

Jab schema me circular relationships hoti hain (e.g. Author -> Books -> Author -> Books), attacker deep nesting queries bhejta hai. Har level par database queries exponentially multiply ho jati hain, jisse server ka event loop block ho jata hai aur database connections exhaust ho jate hain. When schemas declare circular bidirectional relations (e.g., Author -> Books -> Author -> Books), an attacker constructs deeply nested queries. Each level exponentially multiplies database queries, exhausting connection pools and freezing Node.js/Python event loops.

⚡

3. Alias Batching & Brute-Force Bypass

GraphQL aliases (op1: login(pin: 1001), op2: login(pin: 1002)...) allow forcing hundreds of operations into a single HTTP POST. Perimeter WAFs see only 1 request, completely blinding rate limiters and enabling OTP or password brute-forcing in seconds. GraphQL aliases (op1: login(pin: 1001), op2: login(pin: 1002)...) allow packing hundreds of queries into a single HTTP POST request. Edge WAFs count this as a single transaction, bypassing perimeter rate limiters to brute-force OTPs or tokens in seconds.

🛡️

4. Resolver BOLA & Field Authorization Flaws

GraphQL queries allow traversing deep relations (query { order(id: 99) { user { creditCard { number } } } }). Agar intermediate resolver me ownership check (context.user.id == target.userId) nahi hai, toh attacker IDOR / BOLA exploit karke doosre users ka data read kar leta hai. GraphQL graph traversal allows deep relational fetching. If any intermediate or leaf resolver fails to verify ownership against context.user, attackers achieve complete BOLA/IDOR by fetching unauthorized nested entities through permitted parent objects.

Scenario 2: Exponential Circular Depth Denial of Service (DoS)

UNBOUNDED GRAPH TRAVERSAL → SERVER OUT-OF-MEMORY CRASH
High Severity

Attacker schema me thread aur replies ki circular relationship dekhta hai. Wo ek query draft karta hai jisme 15 levels of nested circular fetching hoti hai. Backend database par exponential SQL joins trigger hote hain: 10 threads × 10 replies × 10 threads... Node.js event loop freeze ho jata hai aur container OOM crash ho jata hai: The attacker discovers a bidirectional relationship between thread and replies. They craft a payload nesting 15 levels deep. Resolvers spawn exponential database joins (10 × 10 × 10...), instantly starving Node.js event loop memory and triggering an instant container crash:

POST /graphql HTTP/1.1 Host: api.target.com Content-Type: application/json {"query": "query CircularDoS { thread(id: 1) { replies { thread { replies { thread { replies { thread { id author { threads { replies { id } } } } } } } } } } }"}
💥 Server Out-of-Memory Impact: RAM consumption surged from 135 MB to 4.2 GB in 920 ms! Node.js event-loop lag exceeded 8,000 ms (0 req/s throughput). Kubernetes liveness probe failed, triggering an immediate CrashLoopBackOff across all pods!

Scenario 3: 500-Alias Batching Rate Limit Bypass for OTP Brute-Force

SINGLE HTTP POST → 500 PARALLEL RESOLVER EXECUTIONS
Critical Severity

Password reset endpoint 4-digit SMS OTP maangta hai. Cloudflare WAF 5 requests/minute restrict karti hai. Attacker ek single HTTP POST body me 500 aliases (a0001: verifyOTP(...), a0002: ...) daal deta hai. NESTED RELATION TRAVERSAL → UNAUTHORIZED BILLING & PII DISCLOSURE
High Severity

Root query me authenticated user ka data check karti hai, lekin nested relation resolver order(id: 882) me client identity (context.user.id == order.userId) verify nahi hoti. Attacker apna JWT token bhej kar doosre users ke private billing addresses aur credit cards exfiltrate kar leta hai: The top-level query validates user session, but intermediate field resolver order(id: 882) fails to verify if order.userId === context.user.id. Node.js (Apollo Server Hardened)
Remediated & Hardened 
const { ApolloServer } = require('@apollo/server');
const depthLimit = require('graphql-depth-limit');
const { createComplexityLimitRule } = require('graphql-validation-complexity');

const server = new ApolloServer({
  typeDefs,
  resolvers,
  // 1. Explicitly disable introspection in production
  introspection: process.env.NODE_ENV === 'development',
  validationRules: [
    // 2. Limit query nesting to max 5 levels
    depthLimit(5),
    // 3. Reject high-complexity AST calculations
    createComplexityLimitRule(1000, {
      onCost: (cost) => console.log('Query Cost:', cost)
    })
  ]
});

const resolvers = {
  Query: {
    userOrder: async (_, { orderId }, context) => {
      // 4. Enforce strict resolver authorization
      if (!context.user) throw new Error('UNAUTHENTICATED');
      const order = await db.orders.findById(orderId);
      if (order.userId !== context.user.id) {
        throw new Error('FORBIDDEN_OBJECT_ACCESS');
      }
      return order;
    }
  }
};

                1. Why is GraphQL Introspection considered a vulnerability if it is a built-in feature?

                2. If introspection is disabled, can an attacker still discover the schema?

                Query Depth Limiter AST ko inspect karta hai resolvers execute hone se pehle. Agar koi query defined limit (e.g. 5 levels) se zyada nested hoti hai, toh engine request ko turant reject kar deta hai. Isse circular relations (user -> orders -> user...) database tak pahunch hi nahi paati.
                Query Depth Limiting inspects the parsed Abstract Syntax Tree (AST) prior to resolver invocation. If the nesting level exceeds a preset threshold (typically 5 to 7 levels), the engine immediately aborts query validation, preventing circular relationship queries from executing against the database.
              

            


            
            

              

                ❓
                4. What is the difference between Query Depth and Query Complexity / Cost Analysis?
                4. What is the difference between Query Depth and Query Complexity / Cost Analysis?
              

              

                Query Depth sirf nesting levels count karta hai (height). Lekin ek shallow query bhi server crash kar sakti hai agar wo 1000 items fetch kare (width: users(first: 10000)). Query Complexity har field aur argument ko ek numerical score deti hai (e.g., users = 10 points, per item = 2 points). Agar total cost 500 se zyada ho, toh query block ho jaati hai.
                Query Depth only measures tree height (nesting levels). However, an attacker can crash a server using a shallow query that requests massive collections (e.g., users(first: 10000)). Complexity / Cost analysis assigns numerical weight to each field and multiplier arguments. If total query cost exceeds a configured budget (e.g. 1,000 points), execution is rejected.
              

            


            
            

              

                ❓
                5. Why do traditional perimeter WAFs fail to rate-limit GraphQL APIs?
                5. Why do traditional perimeter WAFs fail to rate-limit GraphQL APIs?
              

              

                Traditional WAFs HTTP request count (IP per second) par kaam karte hain. GraphQL me 1 HTTP POST request ke andar 500 aliases ya array batching use karke 500 alag operations bheje ja sakte hain. WAF use sirf 1 request count karta hai, jabki backend par 500 operations execute ho rahe hote hain.
                Perimeter WAFs track HTTP request volumes per client IP. In GraphQL, a client can nest 500 distinct operations inside a single HTTP POST using field aliases or array batching. The perimeter WAF observes 1 inbound transaction, while the backend resolves 500 intensive operations, making perimeter rate limiting completely ineffective.
              

            


            
            

              

                ❓
                6. What are Automatic Persisted Queries (APQ) and do they improve security?
                6. What are Automatic Persisted Queries (APQ) and do they improve security?
              

              

                APQ me client query string bhejne ke bajaye query ka SHA-256 hash bhejta hai. Agar server par strict Query Whitelisting enable ho, toh server sirf approved hashes accept karta hai aur raw arbitrary query execution ko completely block kar deta hai. Ye GraphQL ka sabse powerful security defense hai!
                With APQ and Persisted Queries, clients send a SHA-256 hash of pre-compiled queries rather than arbitrary query strings. When configured in strict whitelisting mode, the server only executes pre-approved queries, completely neutralizing arbitrary query crafting, introspection attacks, and unexpected circular nesting!
              

            


            
            

              

                ❓
                7. How does BOLA (Broken Object Level Authorization) occur in GraphQL?
                7. How does BOLA (Broken Object Level Authorization) occur in GraphQL?
              

              

                REST me route middleware (e.g. /orders/:id) access control check karta hai. GraphQL me query graph ke through traverse karti hai (user -> orders -> items). Agar kisi child resolver me context.user.id verify nahi kiya gaya, toh attacker unauthorized records fetch kar leta hai chahe parent resolver secure ho.
                In REST, authorization middleware guards entry routes. In GraphQL, execution flows through a graph tree of individual field resolvers. If any child or leaf resolver fails to validate the authenticated user's ownership from context.user, clients can traverse into unauthorized records despite the parent query being legitimate.
              

            


            
            

              

                ❓
                8. Does GraphQL type validation protect against SQL or NoSQL injection?
                8. Does GraphQL type validation protect against SQL or NoSQL injection?
              

              

                Nahi! GraphQL sirf input types enforce karta hai (e.g. String, Int). Agar resolver us String ko directly SQL query (SELECT * FROM users WHERE name = '${args.term}') me concatenate karta hai, toh SQL Injection 100% possible hai. Resolvers me hamesha parameterized queries / ORM use karna chahiye.
                No! GraphQL type validation only confirms primitive data types (e.g., String, Int, Boolean). If a resolver concatenates a String argument directly into a raw SQL query or MongoDB filter, SQLi or NoSQLi will execute unobstructed. Resolvers must always utilize parameterized statements and ORM abstractions.
              

            


            
            

              

                ❓
                9. What is the N+1 problem in GraphQL and why is it also a security concern?
                9. What is the N+1 problem in GraphQL and why is it also a security concern?
              

              

                N+1 problem tab hoti hai jab 1 parent query N child records fetch karti hai aur har child ke liye alag database query chalti hai (1 + N queries). Attackers iska faayda utha kar 10,000 queries trigger kar sakte hain. Isko solve karne ke liye DataLoader use kiya jata hai jo queries ko batch karta hai.
                The N+1 problem occurs when fetching a parent collection of N items triggers N individual database calls for nested relations (1 parent + N child queries). Malicious actors exploit this to induce database CPU exhaustion. Implementing DataLoader batches and memoizes requests to consolidate hundreds of queries into single batch reads.
              

            


            
            

              

                ❓
                10. Which HTTP methods should a production GraphQL server allow?
                10. Which HTTP methods should a production GraphQL server allow?
              

              

                Production me GraphQL queries aur mutations hamesha POST method se aani chahiye with Content-Type: application/json. GET requests me queries URL parameters me jati hain, jisse sensitive parameters browser history aur proxy logs me leak ho jate hain aur CSRF risks badh jate hain.
                Production GraphQL APIs should strictly mandate POST requests with Content-Type: application/json. Allowing GET queries exposes sensitive parameters in server access logs and browser histories, while enabling Cross-Site Request Forgery (CSRF) vulnerabilities when combined with cookie-based session architectures.
