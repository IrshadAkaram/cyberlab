12 GRAPHQL API SECURITY & SCHEMA ATTACKS

GraphQL Security (Introspection & DoS)

GraphQL ek flexible query language hai jisme client decide karta hai ki use kaunsa data chahiye via a single /graphql endpoint. Par yahi flexibility vulnerabilities create karti hai: agar Introspection open ho toh attacker pura internal schema dump kar leta hai, recursive queries se CPU/RAM crash (Denial of Service) kar sakta hai, aur alias batching se rate limits bypass ho jate hain. GraphQL empowers clients to request exactly what they need through a unified /graphql endpoint. However, this architectural flexibility introduces severe attack surfaces: unhardened introspection exposes hidden schemas and admin mutations, unbounded circular queries trigger CPU/memory Denial of Service, and alias batching easily bypasses perimeter rate limiters.

Rohan's Architecture Rule: "In REST, the server enforces the response contract. In GraphQL, the client designs the query execution plan! Without strict depth limits and complexity scoring, any client can author a catastrophic denial-of-service attack!"

GraphQL Internal Execution Lifecycle

GraphQL server par request kaise process hoti hai aur attacker kis step ko target karta hai: Understanding the internal execution pipeline of a GraphQL engine reveals where security boundaries fail:

PHASE 01
1. Parse & AST Generation

Incoming string query is lexed and converted into an Abstract Syntax Tree (AST). Syntax errors are trapped here.

PHASE 02
2. Schema Validation

AST is validated against the defined schema types. Crucial Security Step: Query Depth & Complexity rules must execute here before resolvers run!

PHASE 03
3. Resolver Execution

Individual resolvers (parent, args, context, info) execute in parallel. If field-level auth is missing, data is leaked to the response payload.

🎯 Comprehensive GraphQL Attack Taxonomy

🔍

1. Introspection & Schema Extraction

GraphQL ka built-in introspection feature __schema aur __type meta-fields ke zariye attackers ko pure backend schema ka interactive map de deta hai. Attacker GraphQL Voyager ya InQL use karke administrative mutations, internal fields aur unreleased APIs discover kar leta hai. GraphQL's native introspection features allow attackers to issue queries against __schema and __type to recover the entire backend schema. Tools like InQL or GraphQL Voyager automatically visualize all hidden mutations, deprecated fields, and private arguments.

💣

2. Nested Recursive Query DoS

Jab schema me circular relationships hoti hain (e.g. Author -> Books -> Author -> Books), attacker deep nesting queries bhejta hai. Har level par database queries exponentially multiply ho jati hain, jisse server ka event loop block ho jata hai aur database connections exhaust ho jate hain. When schemas declare circular bidirectional relations (e.g., Author -> Books -> Author -> Books), an attacker constructs deeply nested queries. Each level exponentially multiplies database queries, exhausting connection pools and freezing Node.js/Python event loops.

⚡

3. Alias Batching & Brute-Force Bypass

GraphQL aliases (op1: login(pin: 1001), op2: login(pin: 1002)...) allow forcing hundreds of operations into a single HTTP POST. Perimeter WAFs see only 1 request, completely blinding rate limiters and enabling OTP or password brute-forcing in seconds. GraphQL aliases (op1: login(pin: 1001), op2: login(pin: 1002)...) allow packing hundreds of queries into a single HTTP POST request. Edge WAFs count this as a single transaction, bypassing perimeter rate limiters to brute-force OTPs or tokens in seconds.

🛡️

4. Resolver BOLA & Field Authorization Flaws

GraphQL queries allow traversing deep relations (query { order(id: 99) { user { creditCard { number } } } }). Agar intermediate resolver me ownership check (context.user.id == target.userId) nahi hai, toh attacker IDOR / BOLA exploit karke doosre users ka data read kar leta hai. GraphQL graph traversal allows deep relational fetching. If any intermediate or leaf resolver fails to verify ownership against context.user, attackers achieve complete BOLA/IDOR by fetching unauthorized nested entities through permitted parent objects.

Unbounded Graph Traversal Blocking Server Event Loop
High Severity

Attacker schema me thread aur replies ki circular relation dekhta hai. Wo ek query draft karta hai jisme 15 levels of nested circular fetching hoti hai. Server par har level par queries exponentially multiply hoti hain: 10 threads × 10 replies × 10 replies... Node.js process 100% CPU par freeze ho jati hai aur Kubernetes OOMKilled trigger kar deta hai. The attacker notices a circular relationship between thread and replies. They craft a query nesting 15 levels of bidirectional resolution. Resolvers execute exponential queries (10 threads × 10 replies × 10 replies...), causing memory consumption to skyrocket and triggering container OOM termination.

POST /graphql HTTP/1.1 Content-Type: application/json {"query":"query CircularDoS { thread(id: 1) { replies { thread { replies { thread { replies { thread { id author { threads { replies { id } } } } } } } } } } }"}

Node.js (Apollo Server Hardened)
Remediated & Hardened 
const { ApolloServer } = require('@apollo/server');
const depthLimit = require('graphql-depth-limit');
const { createComplexityLimitRule } = require('graphql-validation-complexity');

const server = new ApolloServer({
  typeDefs,
  resolvers,
  // 1. Explicitly disable introspection in production
  introspection: process.env.NODE_ENV === 'development',
  validationRules: [
    // 2. Limit query nesting to max 5 levels
    depthLimit(5),
    // 3. Reject high-complexity AST calculations
    createComplexityLimitRule(1000, {
      onCost: (cost) => console.log('Query Cost:', cost)
    })
  ]
});

const resolvers = {
  Query: {
    userOrder: async (_, { orderId }, context) => {
      // 4. Enforce strict resolver authorization
      if (!context.user) throw new Error('UNAUTHENTICATED');
      const order = await db.orders.findById(orderId);
      if (order.userId !== context.user.id) {
        throw new Error('FORBIDDEN_OBJECT_ACCESS');
      }
      return order;
    }
  }
};

Python (Strawberry GraphQL Hardened)
Remediated & Hardened 
import os
import strawberry
from strawberry.extensions import MaxAliasesLimiter, QueryDepthLimiter
from strawberry.permission import BasePermission

class IsOwner(BasePermission):
    message = "User does not own this resource"
    def has_permission(self, source, info, **kwargs):
        return info.context.user.id == kwargs.get("user_id")

schema = strawberry.Schema(
    query=Query,
    extensions=[
        # 1. Hard cap query depth to 5 levels
        QueryDepthLimiter(max_depth=5),
        # 2. Defend against alias batching attacks
        MaxAliasesLimiter(max_aliases=10)
    ]
)

# 3. Disable introspection & GraphiQL in production
is_prod = os.getenv("ENV") == "production"
graphql_app = GraphQLView(
    schema=schema,
    graphiql=not is_prod,
    allow_introspection=not is_prod
)

GraphQL Security Auditing Checklist

Interactive 7-Point Security & Triage Review for Burp Suite Repeater

0 of 7 Audited
01
Introspection Schema Dumping Probe
Verify if __schema meta-queries are disabled on public endpoints

In Burp Repeater, send a POST request with body {"query":"{ __schema { queryType { name } } }"}. If response returns HTTP 200 with schema metadata, mark FAIL. If response returns "GraphQL introspection is not allowed", mark PASS.

POST /graphql HTTP/1.1 Host: target.com Content-Type: application/json {"query":"{ __schema { types { name } } }"}
02
Field Suggestions Leakage (Clairvoyance Attack)
Check if disabled introspection still leaks schema via suggestion engine

Send an intentional typo in a query (e.g. { me { user_emai } }). If the error message responds "Did you mean user_email?", the engine is leaking field names and can be brute-forced. Pass only if suggestion masking is enabled.

POST /graphql HTTP/1.1 Content-Type: application/json {"query":"{ user { passwrd_tkn } }"}
03
Circular Query Depth Limit Resistance
Test server response against 10+ levels of circular nesting

Send a query with 10 nested relations. If the server executes it (or delays responding by >2 seconds), mark FAIL. Pass only if a GRAPHQL_VALIDATION_FAILED: Query exceeds maximum depth error is returned instantly.

POST /graphql HTTP/1.1 Content-Type: application/json {"query":"{ user { posts { author { posts { author { posts { id } } } } } } }"}
04
Alias Batching Rate Limit Resistance
Verify if 50+ aliases in a single payload are rejected

Send 50 aliases in 1 request to a login, OTP, or expensive calculation resolver. If all 50 execute, rate limiting is completely bypassed (FAIL). Pass only if server enforces max alias limits or batching restrictions.

POST /graphql HTTP/1.1 Content-Type: application/json {"query":"query { a1: login(pin:\"1\") a2: login(pin:\"2\") ... a50: login(pin:\"50\") }"}
05
IDE Console Exposure Audit (/graphiql, /altair)
Probe common interactive developer console paths

Send GET requests to /graphiql, /graphql, /altair, and /playground with Accept: text/html. If an interactive HTML explorer loads, mark FAIL.

GET /graphiql HTTP/1.1 Host: target.com Accept: text/html,application/xhtml+xml
06
Resolver BOLA / Object Ownership Check
Test accessing another user's nested objects via ID parameters

Authenticate as User A. Send query requesting User B's order ID (order(id: 882)). If the response returns User B's invoice details or shipping address, mark FAIL (BOLA/IDOR). Pass only if forbidden exception is thrown.

POST /graphql HTTP/1.1 Authorization: Bearer USER_A_JWT {"query":"query { order(id: 882) { id total shippingAddress } }"}
07
GraphQL Injection in Resolvers (SQLi / NoSQLi)
Inject quotation marks and boolean payloads into query arguments

Inject SQL payloads into filter strings: users(filter: "admin' OR '1'='1"). If database syntax error or dumped records appear, mark FAIL. GraphQL types do NOT sanitize raw SQL queries inside custom resolvers!

If total query cost exceeds a configured budget (e.g. 1,000 points), execution is rejected.
