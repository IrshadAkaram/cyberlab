09 Database Injection Vulnerabilities

NoSQL Query
Injection (NoSQLi)

NoSQL Injection tab hota hai jab backend API user ke untrusted JSON inputs ko bina strict type validation ke document database (MongoDB, CouchDB) query filter me pass kar deti hai, jisse attacker BSON operators ($ne, $gt, $regex, $where) inject karke authentication bypass, blind data exfiltration, aur server-side JavaScript execution execute kar leta hai. NoSQL Injection occurs when a backend API accepts untrusted structured JSON inputs into document database queries (such as MongoDB) without strict schema type enforcement, allowing attackers to inject BSON operators ($ne, $gt, $regex, $where) to invert query logic, bypass authentication gates, exfiltrate data, and execute arbitrary server JavaScript.

Critical Auth Bypass & Takeover CWE-943 / OWASP API8:2023 ★ MongoDB BSON Operators & $where RCE
💡
Core Insight: "SQL Injection syntax todta hai, jabki NoSQL Injection query logic ka datatype hijack karta hai!" Developer sochta hai password string hai, lekin attacker object bhej kar database engine ko bol deta hai ki password is not equal to empty string—aur database admin document return kar deta hai. Core Insight: "SQL Injection breaks query syntax grammar, whereas NoSQL Injection hijacks query evaluation data types!" Developers anticipate a primitive string, but attackers supply an object operator telling the engine to match any non-empty password—and the database yields the administrator document.

Normal systems me locker machine input ko strictly 4-digit number samajhkar check karti hai ki kya number exactly match karta hai.

Lekin ek smart attacker (Gyanendra) locker machine ke scanner me number dalne ke bajaye system ke software rules ki ek slip ghusata hai: "Condition: PIN IS NOT EQUAL TO '0000'" ({"$ne": "0000"}). Locker machine ka computer boolean rule evaluate karta hai: "Student ka password kuch bhi ho, bas 0000 na ho toh locker khol do!" Aur bina kisi real password ke locker open ho jata hai!

Yahi NoSQL Injection Hai: Application developer expect karta hai ki user literal value (string) dega, lekin attacker data ke badle database query engine ka command/operator (object) bhej deta hai, jisse database security check invert hokar pass ho jata hai!

Imagine an automated high-security library locker. Students enter their Student ID and 4-digit secret PIN (e.g. PIN: "5678"). A strongly typed system checks whether the submitted value equals the stored pin string.

However, in a loosely typed document system, an attacker (Gyanendra) slips a rulebook card into the scanner: "Condition: PIN IS NOT EQUAL TO '0000'" ({"$ne": "0000"}). The locker logic evaluates the rule: "As long as the student's PIN is not '0000', unlock the vault!" The locker opens immediately without the attacker knowing the real password!

This is NoSQL Injection: The developer assumes incoming input is always a literal string, but the adversary supplies an operational object containing BSON selectors, inverting query logic to grant access!

How NoSQL Injection Works (Deep Technical Architecture) How NoSQL Injection Works (Deep Technical Architecture)

NoSQL Injection tab execute hota hai jab client ka structured input database query filter me as a literal value bind hone ke bajaye direct execution tree ka functional control ban jata hai. Niche iske 5 distinct phases explain kiye gaye hain: NoSQL Injection occurs when client input transitions from passive data into active execution control parameters inside document database query trees. Inspect the 5 technical lifecycle phases below:

🔹 1. JSON / BSON Payload Deserialization & Type Confusion:

Web framework (Express express.json() ya Python FastAPI) incoming HTTP body ko parse karta hai. Developer expect karta hai ki req.body.password ek primitive string hogi (e.g. "MySecretPass"). Lekin attacker JSON body me nested object bhejta hai: {"password": {"$ne": ""}}. JSON parser bina kisi type assertion ke is nested object ko JavaScript runtime object me convert kar deta hai. The web framework (such as Express express.json() or Python FastAPI) deserializes the incoming HTTP body. The developer assumes req.body.password is a primitive string. However, the adversary sends a nested object: {"password": {"$ne": ""}}. The parser creates a live object representation without type enforcement.

⚡ 2. Query Object Construction Without Strict Schema Typing:

Developer raw parsed object ko seedha database query builder me pass kar deta hai: db.collection('users').findOne({ username: req.body.username, password: req.body.password }). Kyunki yahan explicit string casting (String(req.body.password)) ya schema validation (Zod / Joi) missing hai, JavaScript runtime database driver ko ye query structure send karta hai: { username: "admin", password: { $ne: "" } }. The controller passes the unvalidated object directly into the query driver: db.collection('users').findOne({ username: req.body.username, password: req.body.password }). Without explicit type coercion or schema contract enforcement, the driver accepts the nested operator object as a valid query tree component.

🚨 3. MongoDB BSON Query Engine Operator Evaluation ($ne, $gt, $regex, $where):

Jab MongoDB BSON query engine is document tree ko process karta hai, toh keys jo $ character se start hoti hain unhe special internal operators treat kiya jata hai. Engine password field ke value ko compare karne ke bajaye operator rule evaluate karta hai: "Check if password field is not equal to empty string". When the MongoDB BSON engine parses the filter document, keys prefixed with $ are reserved as functional query selectors. Rather than comparing the password field value to a string, the engine invokes the operator logic: evaluating whether the document's password field is not equal to empty string.

🌐 4. Query Predicate Inversion & Unrestricted Document Matching:

Database collection scan karta hai aur user admin ko locate karta hai. Admin ka password hash (e.g. bcrypt hash $2b$12$...) empty string nahi hai, isliye $ne: "" condition TRUE evaluate ho jati hai! Query successfully admin document return kar deti hai, bilkul waise jaise attacker ne sahi password diya ho. The database scans the users collection and matches the record where username == "admin". Because the admin's bcrypt hash is indeed not equal to an empty string, the $ne operator yields TRUE! The database returns the full admin user document to the application controller.

💎 5. Unauthorized Access, Admin JWT Generation & Session Hijack:

Controller check karta hai if (user) { issueToken(user); }. Kyunki database ne valid user object return kiya hai, application server samajhta hai ki credentials verify ho gaye. Server attacker ko high-privileged JWT token mint karke response me de deta hai, jisse poora API infrastructure compromise ho jata hai! The application logic simply checks if (user) { generateJWT(user); }. Because MongoDB returned the matched administrator record, the application assumes successful authentication, signing and returning a root administrative JWT session token to the attacker!
🛠️ Dangerous BSON Query Operators Cheatsheet Dangerous BSON Query Operators Cheatsheet
Operator Description Exploit Utility
$ne Matches all values not equal to specified value. Bypasses password/token matching: {"$ne": null}
$gt / $gte Matches values greater than (or equal to) specified value. Matches any non-empty string: {"$gt": ""}
$regex Executes regular expression pattern match on string field. Blind character-by-character password exfiltration: {"$regex": "^a"}
$where Executes arbitrary JavaScript expression on MongoDB server. Remote Code Execution / Blind timing attacks via sleep()
$exists Matches documents that contain the specified field. Hidden schema & sensitive field discovery: {"mfa_secret": {"$exists": true}}

✅ Secure: Strict Scalar Type Guard + $eq Match 
# ✅ SECURE: Strict scalar type enforcement
from flask import Flask, request, jsonify
from pymongo import MongoClient
import bcrypt

app = Flask(__name__)
client = MongoClient("mongodb://localhost:27017")
db = client["prod_db"]

@app.route("/api/v1/auth/login", methods=["POST"])
def login():
    data = request.get_json() or {}
    raw_user = data.get("username")
    raw_pass = data.get("password")

    # 1. Type Guard: Reject nested dictionaries / BSON operators
    if not isinstance(raw_user, str) or not isinstance(raw_pass, str):
        return jsonify({
            "error": "Validation Error: credentials must be scalar strings",
            "code": "INVALID_PARAMETER_TYPE"
        }), 400

    username = str(raw_user).strip()[:100]
    password = str(raw_pass).strip()[:100]

    # 2. Query solely by scalar username with explicit $eq operator
    user = db.users.find_one({"username": {"$eq": username}})
    if user and bcrypt.checkpw(password.encode(), user["password_hash"].encode()):
        return jsonify({"status": "success", "token": "secure-session"}), 200

    return jsonify({"error": "Invalid credentials"}), 401

// ✅ SECURE: mongo-sanitize strips all $ / . keys
const express = require('express');
const mongoSanitize = require('express-mongo-sanitize');
const bcrypt = require('bcrypt');
const app = express();

app.use(express.json());
app.use(mongoSanitize()); // Strips any key starting with $

app.post('/api/v1/auth/login', async (req, res) => {
  // 1. Explicit scalar type validation
  if (typeof req.body.username !== 'string' || typeof req.body.password !== 'string') {
    return res.status(400).json({ error: 'Invalid parameter format' });
  }

  const username = String(req.body.username).trim();
  const user = await User.findOne({ username: { $eq: username } });

  if (user && await bcrypt.compare(req.body.password, user.passwordHash)) {
    return res.json({ token: 'secure-jwt-token' });
  }
  return res.status(401).json({ error: 'Invalid credentials' });
});

Frequently Asked Questions (FAQ) Frequently Asked Questions (FAQ)

Top Security Engineer & Pentester interview questions on NoSQL Injection concepts, modern bypasses, and enterprise remediation: High-yield technical and interview questions covering NoSQL Injection mechanics, BSON operator exploitation, and production hardening:

Q1: Kya Mongoose ORM use karne se NoSQL Injection automatically prevent ho jata hai? Q1: Does using the Mongoose ODM automatically prevent NoSQL Injection?

Answer: Nahi! Ye sabse common galatfehmi hai. Mongoose strict schema use karta hai, lekin agar query me operator pass kiya jaye (jaise User.findOne({ email: req.body.email, password: req.body.password })) aur schema me password String define ho, toh Mongoose $ne operator ko reject nahi karta—balki use valid MongoDB filter query samajh kar execute kar deta hai! Isliye Mongoose ke sath bhi Zod validation aur mongo-sanitize mandatory hai. Answer: No! This is a prevalent misconception. While Mongoose enforces schema typing for model documents, it treats query filter objects permissively. If an adversary passes {"$ne": ""} into User.findOne({ password: req.body.password }), Mongoose forwards the operator directly to MongoDB unless explicit schema validation or sanitization blocks it.

Q2: SQL Injection aur NoSQL Injection ke impact me kya difference hai? Q2: How does the business impact of NoSQL Injection compare to SQL Injection?

Answer: Dono attacks me high severity data exposure aur authentication bypass hota hai. Lekin SQLi me UNION SELECT se poora database dump kiya ja sakta hai aur multi-statement injection possible hota hai. NoSQLi me primary threat Authentication Logic Bypasses, Blind Regex Exfiltration, aur vulnerable setups me $where clause ke through Remote Server-Side JavaScript Execution hota hai. Answer: Both attacks yield critical business consequences including full administrative account takeover. While SQL injection often leverages UNION techniques or stacked statements, NoSQL injection excels at Authentication Bypass via logic inversion ($ne, $gt), Blind Character-by-Character Exfiltration ($regex), and Remote Server-Side JavaScript Execution ($where).

Q3: Blind NoSQL Injection me $regex operator se secret data kaise extract hota hai? Q3: How does blind data exfiltration work using the $regex operator?

Answer: Jab API screen par database data return nahi karti, tab attacker binary boolean feedback (HTTP 200 vs 401 ya response time) par depend karta hai. Attacker {"token": {"$regex": "^a"}} bhejta hai. Agar match nahi hota toh 401 milta hai. Jab character match hota hai (e.g. ^s), toh 200 milta hai. Phir attacker agle character par move karta hai (^se, ^sec) jab tak poora 64-character token extract na ho jaye. Answer: When an API withholds query result sets, an adversary monitors boolean responses (HTTP 200 vs 401 or response latency). By testing anchor regex patterns like {"token": {"$regex": "^a"}} through ^z, a positive HTTP 200 confirms the first character. The adversary iteratively extends the prefix (^se...) until the full 64-character hash or token is recovered.

Q4: Kya sirf JSON body me hi NoSQLi hota hai ya URL query parameters me bhi? Q4: Does NoSQL Injection only happen in JSON bodies or also in URL query parameters?

Answer: Dono me! Express me agar app.use(express.urlencoded({ extended: true })) use ho raha hai, toh standard query string library bracket notation ko object parse kar leti hai. Example: GET /api/v1/users?username[$ne]=null automatically req.query.username = { "$ne": "null" } ban jata hai! Isliye URL query parameters par bhi strict type casting zaroori hai. Answer: Both! When web frameworks employ nested query parsers (such as Express with extended: true), bracket notation query strings are automatically deserialized into objects. Submitting GET /api/v1/users?username[$ne]=null yields req.query.username = { "$ne": "null" }. Query parameters require identical sanitization contracts.

Q5: MongoDB me $where operator ko secure kaise kiya jata hai? Q5: How should the dangerous $where operator be secured in production?

Answer: Best practice hai ki $where operator ko production me use hi na kiya jaye! Modern MongoDB me aggregation pipelines ($expr) standard query operators provide karti hain jo JavaScript engine execute nahi karti. Sath hi MongoDB configuration file (mongod.conf) me security.javascriptEnabled: false configure karein taaki server-side JavaScript engine completely shut down ho jaye. Answer: The definitive industry best practice is completely banning $where. Modern aggregation pipelines with $expr accomplish dynamic comparisons without invoking the JavaScript engine. Furthermore, set security.javascriptEnabled: false in mongod.conf to completely disable server-side script evaluation.
