What is an API? (Technical Definition) What is an API? (Technical Definition)

Application Programming Interface — Client aur Server ke beech ka secure communication bridge Application Programming Interface — The secure communication bridge between client and server

Architecture: Client ⇄ Server Protocols: HTTP(S) / REST / JSON Role: Abstraction & Security Layer

Application Programming Interface (API) do alag-alag softwares (jaise aapka Mobile App aur company ka Cloud Server) ke beech safe communication ka ek digital bridge aur rules ka set hota hai.

Company apna internal source code ya raw database kabhi direct kisi user ko nahi deti. Iski jagah, server ek API Endpoint (jaise /users/profile) provide karta hai, jisse client app internet ke zariye request bhejti hai aur server database se verified data nikal kar structured JSON format me return karta hai. An Application Programming Interface (API) is a secure digital bridge and standardized communication contract between two software applications (such as a Mobile App and a Cloud Server).

Instead of granting direct access to internal source code or raw database tables, servers expose defined API Endpoints (such as /users/profile). This enables client applications to transmit requests securely over the internet and receive structured JSON responses.

🔌 1. Connection Bridge 1. Connection Bridge
Frontend UI aur Backend Server ke beech safe communication link establish karta hai. Establishes a decoupled communication link between frontend UI and backend services.
📨 2. Structured Data Messenger 2. Structured Data Messenger
Client se HTTP Request le jata hai aur server se clean JSON data wapas app tak lata hai. Dispatches HTTP requests and delivers structured JSON payloads back to the client.
🛡️ 3. Security Boundary 3. Security Boundary
Internal database ko direct access se bachata hai; sirf verified endpoints expose karta hai. Prevents direct access to internal database tables by enforcing controlled API routes.

❓ Hamein API ki zaroorat kyun padti hai? Phone me hi sab kyu nahi rakh sakte? Why do we need APIs? Why not store everything inside the phone app?

1. Phone Storage: Instagram par billions photos aur videos hain. Agar saari photos aapke phone me store hongi, toh phone storage 1 second me full ho jayegi!
2. Security: Agar database aapke phone ke andar hoga, toh koi bhi hacker phone khol kar dusre users ke passwords ya bank details chura lega.
3. Real-Time Sync: Agar movie theatre me kisi ne seat book ki, toh sabhi users ko turant pata chalna chahiye ki wo seat booked hai. Yeh central cloud database aur API ke bina possible nahi hai. 1. Storage Constraints: Platforms host petabytes of user data. Storing full catalogs locally on a mobile device is physically impossible.
2. Security Boundaries: Embedding database credentials inside mobile apps would expose all company records to reverse engineering.
3. Real-Time State: Live seat availability in a cinema or flight booking requires an authoritative central server to prevent double-booking.

🧱 Har API ke 4 Basic Components (Building Blocks) The 4 Fundamental Components of Every API
1. Endpoint (URL)

Server par kaunse address par jana hai (jaise domain/path): https://api.example.com/users The target network location on the web: https://api.example.com/users

2. HTTP Method (Action)

Aap kya karna chahte hain? Data mangna (GET) ya naya data save karna (POST). The desired action verb: fetching data (GET) or creating a resource (POST).

3. Headers (Identity Card)

Request ke sath metadata, jaise aapka login token: Authorization: Bearer <token>. Contextual metadata sent alongside the request, such as authentication tokens.

4. Body & Response (JSON)

Jo actual message ya data bheja aur received kiya jata hai structured text format me. The actual data payload transmitted to and from the server in JSON format.

Jab aap mobile screen par kisi button par tap karte hain (e.g. "Check My Profile"), background me 4 simple steps execute hote hain: When you tap a button on a user interface (e.g. "View My Profile"), four straightforward network stages occur behind the scenes:

1
Step 1: Phone App Constructs the Request Step 1: Phone App Constructs the Request

The client framework packages a structured HTTP request targeting an endpoint URL with your cryptographic authentication token in the headers.

2
Step 2: Request Travels over the Internet to the Server Step 2: Request Travels over the Internet to the Server

Internet ke zariye yeh packet company ke secure cloud server (API Gateway) tak pahunchti hai. Server check karta hai ki kya request valid format me hai aur koi spam/attack toh nahi hai. The packet traverses the public internet over secure TLS encryption to the company's API Gateway, where firewall and rate limiting checks are evaluated.

3
Step 3: Server Queries the Database & Prepares Data Step 3: Server Queries the Database & Prepares Data

Server database se aapka record dhoondhta hai. Lekin database se password ya sensitive internal details ko hata kar sirf zaroori public data ko JSON format me pack karta hai. The backend controller queries the database cluster for the matching record, filters out sensitive credentials, and serializes the domain entity into clean JSON format.

4
Step 4: Phone App Receives JSON & Shows on Screen Step 4: Phone App Receives JSON & Shows on Screen

Phone app ko JSON data milta hai. App ka code us data ko padhta hai aur aapki screen par sundar profile picture, naam aur balance draw kar deta hai! The mobile client receives the JSON payload, parses the properties, and renders the user's name, avatar, and balance dynamically on the display.

🚦 HTTP Status Codes: Server Ka Quick Answer HTTP Status Codes: The Server's Immediate Response Status

Server hamesha ek 3-digit number bhejta hai jisse app ko 1 millisecond me pata chal jata hai ki request ka kya result raha: Servers return a 3-digit numeric status code so software clients instantly understand the transaction outcome:

2xx = Success (Sab Theek Hai!)

• 200 OK: Request successful rahi, data mil gaya.
• 201 Created: Naya record/account successfully ban gaya.
• 204 No Content: Kaam ho gaya (e.g. record delete ho gaya), koi body nahi aayi.

4xx = Client Galti (User/App Ki Side)

• 400 Bad Request: Data format galat bheja hai.
• 401 Unauthorized: Aap logged in nahi hain! Token missing hai.
• 403 Forbidden: Aap logged in hain, par yeh doosre ka data hai!
• 404 Not Found: Yeh URL ya ID database me nahi mili.

5xx = Server Galti (Company Ki Side)

• 500 Internal Server Error: Server ke backend code me koi crash ya bug aa gaya.
• 502 Bad Gateway: Upstream server unresponsive hai.
• 503 Service Unavailable: Server par heavy traffic hai ya maintenance chal rahi hai.

🔐 API Security Basics: AuthN vs AuthZ & JWT Tokens API Security Basics: AuthN vs AuthZ & JWT Tokens

Jab hazaron users ek hi API server ko call kar rahe hote hain, toh server ko kaise pata chalta hai ki kaun access kar sakta hai? Yahan do concepts aate hain: When millions of users communicate with a single centralized API cluster, how does the server control permissions? Two foundational concepts govern access:

1. Authentication (AuthN) = Identity

Sawal: "Aap Kaun Hain?"
Jab aap username aur password daal kar login karte hain, toh server aapki identity verify karke aapko ek Digital Pass (Token) deta hai. Question: "Who are you?"
Verifying identity credentials during login to issue an authorized session token.

2. Authorization (AuthZ) = Permission

Sawal: "Kya Aapko Is File/Account Ko Dekhne Ka Haq Hai?"
Aap logged in hain (AuthN pass), lekin kya aap doosre user ka bank balance dekh sakte hain? Nahi! Yahan Authorization check hota hai. Question: "Are you allowed to access this specific resource?"
Enforcing object ownership boundaries so User A cannot read User B's records.

It functions like a digital event wristband, divided into three parts separated by dots:

⚠️ Critical Beginner Warning: JWT Encrypted Nahi Hota! Critical Beginner Warning: JWT is Encoded, NOT Encrypted!

Dhyan rahe: JWT ka Payload sirf Base64 format me likha hota hai. Koi bhi website (jaise jwt.io) par paste karke ise padh sakta hai! Isliye JWT ke andar kabhi bhi passwords, card numbers ya sensitive Personally Identifiable Information (PII) nahi rakhna chahiye! Take note: JWT payloads are simply Base64 encoded JSON text, NOT encrypted. Anyone can decode and inspect the data. Therefore, never place passwords or sensitive Personally Identifiable Information (PII) inside unencrypted token payload claims!

🎯 Hackers APIs Ko Kyun Target Karte Hain? Why Do Attackers Target APIs Directly?

Pehle ke time par hackers website ke buttons aur visual forms par attack karte the. Lekin aaj kal hackers website ya mobile app ko kholte bhi nahi hain! Wo seedhe API par attack karte hain: Traditionally, web testing focused on visual forms in browsers. Modern adversaries bypass browser interfaces completely to send raw HTTP packets directly to backend endpoints:

1
Phone App Ke Buttons Ko Bypass Karna Bypassing Frontend Client Validations

Agar phone app me "Transfer Money" button disabled hai, toh ek normal user kuch nahi kar sakta. Lekin attacker tool (jaise Burp Suite ya Postman) se seedhe server ko API request bhej deta hai: POST /transfer {"amount": 5000}. Agar server ne khud check nahi kiya, toh paisa chala jayega! If a mobile UI disables a button or checks input lengths in JavaScript, an attacker ignores the UI and sends a direct HTTP POST request straight to the server socket.

2
Numbers Badal Kar Doosre Ka Data Choorana (BOLA / IDOR) Tampering with Record Identifiers (BOLA / IDOR)

Jab aap apna account kholte hain, app bhejti hai: GET /api/users/1001. Attacker URL me 1001 ki jagah 1002 ya 1003 daal kar request bhejta hai. Agar server ne ownership check nahi kiya, toh doosre user ki private details leak ho jaati hain! Yahi BOLA (Broken Object Level Authorization) vulnerability hai. When your app loads your profile via GET /api/users/1001, an attacker simply increments the integer to 1002. If the server does not verify if the requester owns record 1002, the data leaks immediately. This is BOLA.

3
Automated High-Speed Scripting Automated High-Speed Scripting

Insaan website par 1 minute me 5 baar click kar sakta hai, lekin ek hacker ka script API par 1 second me 10,000 requests bhej kar passwords ya coupon codes guess (brute force) kar sakta hai. A human clicks a website several times a minute. An automated Python script dispatches 10,000 API calls per second to brute force OTPs, coupons, or enumeration endpoints.

            Frequently Asked Questions by Beginners
            Frequently Asked Questions by Beginners
          


          

            Agar aap API learning me bilkul naye hain, toh yeh 5 sawal aapke saare doubts clear kar denge:
            If you are new to web development and APIs, these five essential questions will clarify foundational concepts:
          


          
          

            

              ❓
              1. Kya API koi programming language hai ya software hai?
              1. Is an API a programming language or an installed software?
            

            

              
                Nahi! API na toh koi language hai aur na hi koi app jise aap download karte hain. API sirf ek standard communication set of rules (contract) hai. Jaise do log aapas me baat karne ke liye English ya Hindi language ke rules follow karte hain, waise hi do computers internet par data share karne ke liye HTTP aur JSON ke rules follow karte hain, jise API kaha jata hai.
              
              
                Neither. An API is neither a programming language nor an application you install. It is an agreed-upon communication protocol contract. Just as humans follow language rules to communicate, computers follow HTTP and JSON formatting rules to exchange data over the internet.
              
            

          


          
          

            

              ❓
              2. Frontend developer aur Backend developer ke beech API ka kya connection hota hai?
              2. What is the role of an API between Frontend and Backend developers?
            

            

              
                Backend Developer server par code likhta hai (Node.js, Python, Java) aur API banata hai jo database se data nikal kar JSON format me deti hai.

                Frontend Developer (React, Flutter, iOS) button aur screens banata hai, aur button dabane par backend ki us API ko call karke data screen par display kar deta hai. API hi in dono ko jodne wala bridge hai!
              
              
                Backend Developers construct endpoints using server runtimes (Node.js, Python, Go) to process business logic and query databases.

                Frontend Developers design mobile and web user interfaces, triggering those backend API endpoints to hydrate the UI with live data. The API is the bridge connecting both disciplines.
              
            

          


          
          

            

              ❓
              3. Agar hacker Postman ya cURL se request bhejega, toh server ko kaise pata chalta hai?
              3. When an attacker sends requests via cURL or Postman, how does the server tell them apart from legitimate apps?
            

            

              
                Kayi baar server ko pata hi nahi chalta! Kyunki wire par chahe phone app se request jaye ya hacker ke cURL script se, dono same HTTP packet hote hain. Yahi wajah hai ki API Security itni important hai! Server ko kabhi bhi yeh bharosa nahi karna chahiye ki "request phone app se aayi hai toh safe hogi". Server ko har request par Token, Permissions aur Data ko verify karna padta hai.
              
              
                In many cases, the server cannot tell the difference! Across network wires, an HTTP request from an iPhone looks identical to an HTTP request sent from a terminal running cURL. This is precisely why API Security is so critical: servers must never trust clients blindly and must always validate tokens, permissions, and input parameters independently on the backend.
              
            

          


          
          

            

              ❓
              4. HTTP aur HTTPS me API ke liye kya fark hota hai?
              4. What is the difference between HTTP and HTTPS for APIs?
            

            

              
                HTTP: Data plain text me travel karta hai. Agar aap cafe ke Wi-Fi par baithe hain, toh koi bhi Wi-Fi traffic dekh kar aapka login token aur passwords padh sakta hai.

                HTTPS (SSL/TLS): Data fully encrypt ho jata hai. Raste me koi bhi hacker intercept karega toh use sirf unreadable gibberish dikhega. Production me har API hamesha HTTPS par hi honi chahiye!
              
              
                HTTP: Data is transmitted as plain unencrypted text. Anyone listening on public Wi-Fi can capture authorization tokens and passwords in transit.

                HTTPS (TLS Encryption): The entire HTTP packet is cryptographically encrypted. Eavesdroppers only see scrambled ciphertext, preventing packet sniffing and credential theft.
              
            

          


          
          

            

              ❓
              5. Client-side validation aur Server-side validation me kya fark hai?
              5. What is the difference between client-side validation and server-side validation?
            

            

              
                Client-side validation (UX ke liye): Phone app me form par red color se "Enter valid email" likha aata hai taaki normal user galti na kare. Lekin attacker isko 1 second me bypass kar sakta hai.

                Server-side validation (Security ke liye): Server par API controller khud dobara check karta hai ki email valid hai ya nahi, aur number positive hai ya nahi. Asli security hamesha server-side validation se hi aati hai!
              
              
                Client-Side Validation (for UX): Friendly form warnings in mobile apps helping users avoid typos. Adversaries bypass client checks effortlessly by crafting custom network packets.

                Server-Side Validation (for Security): Strict schema enforcement on the backend server before touching databases. True security is solely established through robust server-side validation.
