08 Server-Side Request Forgery

Server-Side Request
Forgery (SSRF)

Server-Side Request Forgery (SSRF) tab hota hai jab backend API user ke provide kiye gaye URL ko bina strict validation aur IP check ke fetch karta hai, jisse attacker vulnerable server ko apna proxy banakar internal cloud metadata (AWS 169.254.169.254), databases aur private microservices ko compromise kar leta hai. Server-Side Request Forgery (SSRF) occurs when a backend API fetches a remote resource specified by an untrusted user without validating the target destination, effectively turning the server into an arbitrary HTTP proxy to breach cloud metadata (AWS 169.254.169.254), internal databases, and private microservices.

Critical Infrastructure Breach CWE-918 / OWASP API7:2023 ★ Cloud Metadata & Intranet Pivoting
💡
Core Insight: "Perimeter firewall par trust karna bekar hai agar aapka API server khud attacker ki bhediya ban jaye!" Attacker bahar internet par baithkar internal private network tak direct nahi pahunch sakta, lekin SSRF ke zariye wo aapke server ke credentials aur network access ka istemal karke attack karta hai. Core Insight: "A perimeter firewall is useless if your API server becomes the attacker's insider agent!" While attackers cannot route traffic directly into private subnets, SSRF coerces the trusted server itself to fetch internal secrets and forward them outward.

1. In-Band (Basic) SSRF

Jab internal server ka response (jaise AWS metadata JSON, Redis command output, ya internal HTML) directly client ke HTTP response me return ho jata hai. Attacker ko turant data screen par mil jata hai. The target service's HTTP response (such as AWS metadata JSON, Redis output, or internal admin HTML) is directly reflected in the API response sent back to the attacker.

2. Blind SSRF

Server internal request toh bhejta hai, lekin uska data attacker ko response me wapas nahi deta (jaise webhook ping). Attacker iska pata DNS interaction (Burp Collaborator) ya response timing delay se lagata hai. The server makes the outbound request but does not return the response body. Attackers verify vulnerability via Out-of-Band (OOB) DNS lookups (e.g. Burp Collaborator) or time delays.

How It Works: Under-The-Hood SSRF Execution Lifecycle How It Works: Under-The-Hood SSRF Execution Lifecycle

Jab aapka API server kisi user-supplied URL ko execute karta hai, toh operating system aur runtime network stack me 5 distinct critical phases execute hote hain. Attacker inhi phases ke gaps ko exploit karta hai: When an API server executes a user-provided URL, the underlying runtime and OS network stack progress through 5 key stages. Exploits target specific failure points across these boundaries:

🔹 1. URL Parsing & Protocol Scheme Check:

HTTP client library (Axios, cURL, Requests) user ke raw URL string ko parse karke components me divide karti hai: Scheme (http:, https:, file:, gopher:), Hostname (169.254.169.254 ya localhost), Port, aur Path. Agar scheme check missing hai, toh attacker alternative protocols (jaise file:///etc/passwd) smuggle kar sakta hai. The HTTP client runtime (Axios, Requests, cURL) parses the raw input string into protocol scheme, hostname/IP, port, and path. If scheme validation is missing, attackers inject dangerous alternate protocols like file:///etc/passwd or gopher://.

⚡ 2. DNS Resolution (The DNS Rebinding Vulnerability Window):

Agar target hostname domain name hai, toh server OS DNS resolver ko query bhejta hai. Agar developer validation ke time IP check karta hai lekin actual HTTP connect ke time dubara DNS query bhejta hai, toh attacker DNS Rebinding (TTL=0) se first check me public IP aur connect time par 127.0.0.1 return karke firewall bypass kar deta hai! If a domain hostname is provided, the OS queries recursive DNS resolvers. If the application resolves the IP for validation but the HTTP library resolves it a second time during connection, attackers leverage DNS Rebinding (TTL=0) to supply a safe IP initially and flip to 127.0.0.1 at connect time!

🚨 3. TCP Socket Creation & Gateway Handshake:

Server OS kernel resolved IP address par TCP 3-way handshake (SYN ➔ SYN-ACK ➔ ACK) initiate karta hai. Kyunki server khud internal cloud network (AWS VPC) ya localhost par reside karta hai, isliye perimeter firewalls is internal connection ko drop nahi karte—server seedha private databases aur microservices se handshake kar leta hai! The OS kernel initiates a TCP 3-way handshake to the resolved IP address. Because the API server itself is inside the private VPC or loopback environment, perimeter edge firewalls do not inspect outbound socket initiation, allowing the server to bridge straight into private databases.

🌐 4. Outbound HTTP Request & Cloud Metadata Headers:

Connection establish hone ke baad server HTTP request headers bhejta hai. Jab target http://169.254.169.254 (AWS IMDS) hota hai, toh hypervisor instance ke IAM role ka naam aur authorization keys Bina kisi login password ke return kar deta hai (IMDSv1 me). Once connected, the server transmits HTTP request headers. When the target is http://169.254.169.254 (AWS IMDS), the hypervisor responds with attached IAM role names and session credentials without requiring any password authentication under IMDSv1.

💎 5. Response Processing & Sensitive Data Reflection:

Server remote service ka response buffer me collect karta hai. Vulnerable code is downloaded body ko client ke HTTP response me echo kar deta hai ya server disk par save kar leta hai. Attacker ko screen par temporary AWS keys, Redis keyspace dumps, ya internal admin HTML mil jata hai! The server collects the remote HTTP response buffer. Vulnerable controllers echo this raw payload back into the client JSON response, immediately exfiltrating AWS IAM secrets, internal Redis memory dumps, or Kubernetes cluster configurations to the adversary.

🌐 Scenario 4: DNS Rebinding Time-Of-Check to Time-Of-Use (TOCTOU) Attack Scenario 4: DNS Rebinding Time-Of-Check to Time-Of-Use (TOCTOU) Attack

Asif validation function me DNS lookup karta hai aur dekhta hai ki IP public hai ya private. Lekin wo socket connection ke time usi IP par pin nahi karta. Atharva ek custom authoritative nameserver run karta hai jiska DNS TTL=0 hota hai. First DNS query (Validation check) par IP 34.215.1.1 return hoti hai (Safe Pass). Second DNS query (Actual Axios HTTP connect) par wahi domain 127.0.0.1 return karta hai! Is Time-Of-Check to Time-Of-Use (TOCTOU) race condition se filter fail ho jata hai aur internal service compromise ho jati hai. Asif performs DNS validation to ensure the host resolves to a public IP, but fails to pin the socket connection to that validated IP. Atharva registers a domain on a custom nameserver with DNS TTL=0. During the initial validation query, the nameserver answers with a benign public IP 34.215.1.1. Milliseconds later when the HTTP client initiates the socket connection, the nameserver answers with 127.0.0.1! This TOCTOU flaw bypasses the application check and opens an internal loopback socket.

Vulnerable vs. Secure Code Implementations (Framework Patterns) Vulnerable vs. Secure Code Implementations (Framework Patterns)

SSRF vulnerabilities ko fix karne ke liye sirf naive string regex kaafi nahi hoti. Backend code level par Pre-Connection DNS Resolution, RFC 1918 & RFC 3927 CIDR Blocking, HTTP Redirects Disabling, aur Connection Pinning lagana zaroori hai: Remediating SSRF requires defense-in-depth: Pre-DNS Resolution & Validation, Strict Private CIDR Filtering (RFC 1918 & RFC 3927), Zero HTTP Redirects, and Direct Socket Pinning. ❌ Vulnerable (Node.js / Express + Raw Axios Fetch) 
// 🚨 VULNERABLE: Direct URL fetching without IP or CIDR validation!
const express = require('express');
const axios = require('axios');
const app = express();
app.use(express.json());

// Atharva can pass "http://169.254.169.254" or "http://2130706433"!
app.post('/api/v1/user/avatar-import', async (req, res) => {
  try {
    const { avatarUrl } = req.body;

    // ⚠️ Flawed Blacklist regex easily bypassed via decimal or DNS rebinding
    if (avatarUrl.includes('127.0.0.1') || avatarUrl.includes('localhost')) {
      return res.status(400).json({ error: 'Forbidden target' });
    }

    // 🚨 DANGER: Server acts as arbitrary HTTP proxy, follows redirects!
    const response = await axios.get(avatarUrl, {
      maxRedirects: 5,
      timeout: 5000
    });

    return res.json({ success: true, data: response.data });
  } catch (err) {
    return res.status(500).json({ error: err.message });
  }
});
✅ Secure (Pre-DNS Resolution + Strict CIDR Blocker) 
// ✅ SECURE: Pre-Connection DNS Resolution + RFC 1918 / 3927 Blocker
const dns = require('dns').promises;
const ipaddr = require('ipaddr.js');
const axios = require('axios');

function isBlockedIp(ipStr) {
  const addr = ipaddr.parse(ipStr);
  const range = addr.range();
  const blocked = ['loopback', 'private', 'linkLocal', 'uniqueLocal', 'reserved'];
  return blocked.includes(range);
}

app.post('/api/v1/user/avatar-import', async (req, res) => {
  try {
    const parsed = new URL(req.body.avatarUrl);
    if (!['http:', 'https:'].includes(parsed.protocol)) {
      return res.status(400).json({ error: 'Invalid protocol scheme' });
    }

    // 1. Resolve hostname to numeric IP before socket connection
    const { address } = await dns.lookup(parsed.hostname);

    // 2. Reject all loopback, RFC 1918 private, and AWS link-local IPs
    if (isBlockedIp(address)) {
      return res.status(403).json({ error: 'SSRF Guard: Restricted destination IP' });
    }

    // 3. Zero redirects prevents Open Redirect bypasses
    const response = await axios.get(req.body.avatarUrl, {
      maxRedirects: 0,
      timeout: 3000,
      maxContentLength: 2 * 1024 * 1024
    });
    return res.json({ success: true, type: response.headers['content-type'] });
  } catch (err) {
    return res.status(500).json({ error: err.message });
  }
});

✅ Secure (Python + socket + ipaddress Module) 
# ✅ SECURE: Strict IP Parsing + Zero Redirects + Private Network Filter
import ipaddress, socket
from urllib.parse import urlparse
import requests
from fastapi import FastAPI, HTTPException

app = FastAPI()

def verify_safe_url(url_str: str):
    parsed = urlparse(url_str)
    if parsed.scheme not in ["http", "https"]:
        raise HTTPException(status_code=400, detail="Invalid scheme")

    # Resolve IP address before connection
    raw_ip = socket.gethostbyname(parsed.hostname)
    ip_obj = ipaddress.ip_address(raw_ip)

    # Reject loopback, RFC 1918, link-local (169.254.0.0/16)
    if ip_obj.is_private or ip_obj.is_loopback or ip_obj.is_link_local:
        raise HTTPException(status_code=403, detail="Restricted IP target")

@app.post("/api/v1/webhook")
def trigger_webhook(payload: dict):
    target_url = payload.get("callbackUrl")
    verify_safe_url(target_url)

    # Disable redirects to prevent Open Redirect chained SSRF
    resp = requests.get(target_url, allow_redirects=False, timeout=3)
    return {"status": "delivered"}

Frequently Asked Questions (FAQ) Frequently Asked Questions (FAQ)

Top security interviews aur certifications (OSCP, CEH, API Pentesting) me puche jane wale Server-Side Request Forgery (SSRF) ke core questions: Critical interview and certification questions covering Server-Side Request Forgery (SSRF) and Cloud Metadata defenses:

Q1: AWS IMDSv1 aur IMDSv2 me kya difference hai aur IMDSv2 SSRF ko kaise neutralize karta hai? Q1: What is the difference between AWS IMDSv1 and IMDSv2, and how does IMDSv2 neutralize SSRF?

Answer: IMDSv1: Simple HTTP GET request se credential return karta hai (GET http://169.254.169.254/latest/meta-data/). Isme kisi authentication header ki zaroorat nahi hoti, isliye basic SSRF se attacker instant cloud keys chura leta hai. IMDSv2: Session-oriented security model hai. Attacker ko pehle ek PUT request bhejkar X-aws-ec2-metadata-token-ttl-seconds: 21600 header pass karna padta hai session token lene ke liye. Zyadatar SSRF vulnerabilities me attacker custom headers inject nahi kar sakta aur na hi PUT method force kar sakta hai. Iske alawa hop-limit=1 hone par Docker containers se host metadata query block ho jati hai. Answer: IMDSv1: Operates via simple, connectionless HTTP GET queries with zero authentication headers required, making it vulnerable to any simple SSRF vector. IMDSv2: Enforces a session-oriented model requiring a PUT request with the X-aws-ec2-metadata-token-ttl-seconds: 21600 header to generate a session token. Subsequent queries must supply X-aws-ec2-metadata-token. Since typical SSRF vulnerabilities allow arbitrary URL injection but cannot dictate custom headers or HTTP verbs, IMDSv2 effectively neutralizes exploitation.

Q2: DNS Rebinding Attack kya hota hai aur yeh traditional IP blacklists ko kaise bypass karta hai? Q2: What is a DNS Rebinding attack and how does it bypass traditional application-level IP blacklists?

Answer: DNS Rebinding ek Time-Of-Check to Time-Of-Use (TOCTOU) race condition exploit hai. Attacker ek custom authoritative nameserver setup karta hai jisme TTL=0 hota hai. (1) Validation check ke time domain resolve hota hai safe public IP 34.215.1.1 par. Server ka security check is IP ko allow kar deta hai. (2) Kuch milliseconds baad jab HTTP client socket connection initiate karta hai, toh OS dubara DNS query bhejta hai. Is baar attacker ka DNS server response badal kar 127.0.0.1 return kar deta hai! Isse server loopback service se connect ho jata hai. Secure solution: initial DNS lookup ke baad connection ko usi resolved IP par pin karein. Answer: DNS Rebinding exploits a Time-Of-Check to Time-Of-Use (TOCTOU) window using a malicious nameserver configured with TTL=0. During the initial validation phase, the domain resolves to a harmless public IP (e.g., 34.215.1.1), passing the check. Milliseconds later, when the HTTP client initiates the TCP handshake, the OS re-resolves the domain and receives 127.0.0.1! The connection is established directly to loopback. Mitigation requires pinning the socket connection directly to the verified IP address rather than re-resolving the hostname.

Q3: SSRF defense me HTTP Redirects ko disable karna kyun mandatory hota hai? Q3: Why is disabling HTTP redirects mandatory for robust SSRF remediation?

Answer: Maan lijiye aapne strict domain allowlist banayi hai ki server sirf https://trusted-cdn.com se hi download karega. Agar trusted-cdn.com par koi Open Redirect vulnerability exist karti hai (jaise https://trusted-cdn.com/redirect?to=http://169.254.169.254/), aur aapka HTTP client auto-redirect follow karta hai, toh initial URL check pass ho jayega, lekin redirect hote hi server internal AWS metadata se connect ho jayega! Isliye maxRedirects: 0 (disallow redirects) set karna critical security best practice hai. Answer: Even with a strict domain allowlist (e.g., only permitting https://trusted-cdn.com), if the trusted domain contains an Open Redirect flaw (https://trusted-cdn.com/redirect?to=http://169.254.169.254/), an HTTP client configured with auto-redirects will pass the initial allowlist check and subsequently connect into the internal metadata service or private subnet. Enforcing maxRedirects: 0 blocks this attack chain.

Q4: Blind SSRF kya hota hai aur security assessment me iska proof-of-concept kaise demonstrate karte hain? Q4: What is Blind SSRF and how do you demonstrate proof-of-concept during an assessment?

Answer: Blind SSRF me server remote resource ko fetch toh karta hai, lekin uska response client ko return nahi karta (jaise background asynchronous webhook dispatcher ya PDF rendering engine). Iska PoC demonstrate karne ke liye Out-of-Band (OOB) techniques use ki jati hain: (1) Burp Collaborator / Interactsh: Attacker ek unique domain provide karta hai (e.g. xyz.oastify.com) aur verify karta hai ki target server ka egress IP DNS query aur HTTP request bhej raha hai. (2) Time-based SSRF: Open internal ports vs closed internal ports ke response delay ko measure karke internal topology map ki jati hai. Answer: In Blind SSRF, the backend triggers an outbound request but does not echo the response payload back to the client (e.g., asynchronous webhooks or PDF generators). Pentesting proof-of-concept relies on Out-of-Band (OOB) channels: generating a dedicated Burp Collaborator or Interactsh domain (xyz.oastify.com) and monitoring for inbound DNS/HTTP callbacks originating from the target server's public egress IP, or measuring response timing discrepancies across internal port ranges.

Q5: Regex-based IP blacklist checks (jaise 127.0.0.1 aur localhost) secure kyu nahi maane jaate? Q5: Why are regex-based IP blacklists (e.g., blocking 127.0.0.1 and localhost) fundamentally insecure?

Answer: IP addresses ko represent karne ke darjano formats hote hain jinhe simple string regex catch nahi kar pata: (1) Decimal Notation: http://2130706433/ (127.0.0.1 ka decimal). (2) Hexadecimal: http://0x7f000001/ ya http://0x7f.0.0.1/. (3) Octal: http://0177.0.0.1/. (4) IPv6: http://[::1]/ ya http://[::]/. (5) Shorthand: http://127.1/. (6) DNS CNAME / Alternate Domains: http://spoofed.localtest.me jo 127.0.0.1 par resolve hota hai. Regex blacklist har format ko block nahi kar sakta; sirf proper numeric IP parsing aur CIDR evaluation hi secure hai. Answer: IP addresses can be expressed in diverse representations that bypass string regex filters while remaining fully valid to the operating system network stack: (1) Decimal Integer: http://2130706433/. (2) Hexadecimal: http://0x7f000001/. (3) Octal: http://0177.0.0.1/. (4) IPv6: http://[::1]/ or http://[::]/. (5) Shorthand: http://127.1/. (6) Wildcard DNS Domains: domains like localtest.me pointing to 127.0.0.1. Blacklists fail; only strict allowlisting and pre-connection CIDR range checks are secure.
