Cryptography, JWT Anatomy aur Core Concepts Cryptography, JWT Anatomy and Core Concepts

🔐 Cryptography Kya Hoti Hai Aur API Security Me Kyu Zaroori Hai? What is Cryptography & Why is it Essential in API Security?
Cryptography computer science aur mathematics ki wo branch hai jiska kaam human-readable sensitive information (Plaintext) ko aisi unreadable form (Ciphertext) me badalna hai jise sirf wahi vyakti ya system padh sake jiske paas authorized cryptographic secret key ho.

Web aur API architecture me servers open internet par untrusted clients (browsers, mobile apps) se communicate karte hain. Bina cryptography ke koi bhi hacker network traffic intercept karke passwords, bank balances ya identity chura sakta hai ya beech me badal sakta hai (Man-in-the-Middle Attack). Cryptography is the foundational science of mathematically transforming human-readable data (Plaintext) into secure, unreadable format (Ciphertext) so that only parties possessing the authorized cryptographic key can decrypt, read, or verify it.

In modern API architectures, clients and microservices communicate across untrusted public networks. Without cryptography, any adversary could intercept, modify, or fabricate identity claims and financial transactions in transit (Man-in-the-Middle attacks).
1. Confidentiality (Privacy / Data Protection)
Sirf authorized recipient hi data read kar sake. Data raste me kisi unauthorized person ko dikhayi na de (e.g. AES encryption, TLS). Ensures data remains secret from eavesdroppers during transit and storage (e.g., AES encryption, TLS/HTTPS).
2. Integrity (Tamper-Proofing)
Yeh guarantee ki data generate hone ke baad raste me 1 bit bhi tamper ya modify nahi kiya gaya hai (e.g. SHA-256 Hashing, HMAC). Guarantees that information has not been altered, tampered with, or injected during transit (e.g., Cryptographic Hashes, HMAC).
3. Authentication (Identity Verification)
Sender ki asli identity verify karna. Server confirm karta hai ki token sach me legitimate login system ne hi issue kiya tha. Confirms the true identity of the requester, proving that the digital artifact was genuinely created by an authentic authority.
4. Non-Repudiation (Undeniable Proof)
Sender baad me yeh inkaar nahi kar sakta ki usne yeh transaction ya token sign nahi kiya tha (Digital Signatures: RSA, ECDSA). Prevents the author from denying the authenticity of their signature on a document or contract (Asymmetric Digital Signatures).
📜 JSON Web Token (RFC 7519) Kya Hota Hai? Real-Life Concept What is a JSON Web Token (RFC 7519)? The Real-World Mental Model
JSON Web Token (JWT) ek open standard (RFC 7519) digital format hai jo do parties (jaise aapka browser/mobile app aur backend API server) ke beech user identity aur permissions ko ek self-contained, tamper-proof package me transmit karne ke liye use hota hai.

✈️ Real-Life Example (Airport Boarding Pass Analogy):
Maan lijiye aap airport par security check-in karte hain. Airline aapko ek Boarding Pass deti hai jisme aapka naam (Kaif), flight number, seat number (14B), aur ek official digital cryptographic barcode stamp hota hai. Jab aap flight ke gate par jate hain, to gate agent corporate headquarters ko phone karke database check nahi karta; wo sirf aapke boarding pass par laga official digital seal / barcode scan karta hai. Airline ke cryptographic stamp ki wajah se gate agent ko turant 100% bharosa ho jata hai ki aapne apna seat number ya naam pen se badalkar VIP nahi banaya hai!

JWT bilkul yahi Boarding Pass hai: Jab user login karta hai, to authentication server ek token issue karta hai. Agli har API request ke sath browser yeh token bhejta hai. Backend API database me query kiye bina sirf uske cryptographic signature ko verify karke user ko authenticate kar leti hai. A JSON Web Token (JWT) is an open RFC 7519 industry standard defining a compact, self-contained, URL-safe container for transferring verifiable security claims between a client and an API server.

✈️ The Airport Boarding Pass Mental Model:
When you check in at an airport, the airline hands you a Boarding Pass containing your identity, flight number, seat (14B), and an official cryptographic barcode seal. At the boarding gate, the agent does not telephone corporate headquarters or query the central database for all 300 passengers. They simply scan the digital signature on the pass. Because the airline's cryptographic stamp is intact, the agent instantly trusts that you didn't erase your seat number with a pen to claim First Class!

JWT is that digital boarding pass for web APIs: Upon login, the server issues a signed JWT containing user attributes. On every subsequent API call, the backend verifies the signature locally within microseconds without executing costly database session queries.
⚠️ Sabse Badi Galatfehmi (The Critical Misconception):
JWT Encrypted NAHI hota! JWT sirf Base64URL-encoded hota hai. Koi bhi vyakti token ko jwt.io me daal kar aapka user ID, email aur role saaf padh sakta hai. JWT ki security Gopniyata (Secrecy) me nahi, balki Akhandata (Tamper-Resistance via Signature) me hoti hai—yani koi use modify nahi kar sakta! A JWT is NOT encrypted! It is merely Base64URL-encoded. Anyone who intercepts the token can decode it at jwt.io and read your user ID, email, and permissions. JWT provides Tamper-Proof Integrity, NOT confidentiality (unless encapsulated in a JWE).
Key Standard: RFC 7519 (JWS / JWE)
Encoding: Base64URL (Not Encrypted)
Common Algs: HS256 (HMAC), RS256 (RSA), ES256 (ECDSA)
Core Threat: Signature Stripping, Forgery & Alg Confusion

JWT Ki 3 Parts Ki Anatomy (Header . Payload . Signature) Anatomy of a JWT: 3 Core Components

Ek valid JWT me teen hisse do dots (.) se separated hote hain: A serialized JWT consists of three Base64URL strings concatenated by periods (.):

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMDAxIiwibmFtZSI6IkthaWYiLCJyb2xlIjoidXNlciIsImlhdCI6MTcyNTUwMTAwMH0.dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

1. Header (Red)

Batata hai ki token ka format kya hai aur signature kis algorithm se bani hai (jaise {"alg": "HS256", "typ": "JWT"}). Yeh JSON Base64URL-encoded hota hai. Declares token type and signature algorithm (e.g., {"alg": "HS256", "typ": "JWT"}). Base64URL-encoded JSON.

2. Payload / Claims (Purple)

Aapka actual data (claims) jaise User ID (sub), username, role, aur token expiry timestamp (exp). Yeh bhi unencrypted JSON hota hai. Contains the claims about the user (e.g., sub: 1001, role: user, exp: 1725501000). Anyone who sees the token can read these claims.

3. Cryptographic Signature (Cyan)

Base64(Header) + "." + Base64(Payload) ko server ki secret key se hash karke banta hai. Agar payload me 1 letter bhi badla gaya, to signature match nahi karegi! Hash of Header + "." + Payload created using the server's private key or secret. The sole mechanism preventing payload tampering.
🔄 JWT Lifecycle & Validation Architecture: Agar Server Token Save Nahi Karta, Toh Validation Kaise Karta Hai? JWT Lifecycle & Stateless Validation Architecture: How Does the Server Validate Without Storing the Token?
Sabse bada sawal jo har developer aur security tester ke zehen me aata hai: "Traditional session architecture me server database ya Redis me session_id save karta tha, lekin JWT me server par token save hi nahi hota (Stateless)! Toh server har incoming request ko kaise validate karta hai ki ye genuine hai ya kisi attacker ne tamper kiya hai?" Aayiye is pure 3-stage lifecycle aur cryptographic verification engine ko step-by-step samajhte hain: The fundamental architectural question: "In traditional session architecture, the server stores active session_ids in a DB or Redis. But JWT is completely stateless—the server stores zero tokens! How does the server verify token authenticity without querying any stored session?" Below is the comprehensive step-by-step cryptographic verification breakdown:
STEP 1 • ISSUANCE (SIGNING) 🔑

Server Token Generate Aur Sign Kaise Karta Hai?

1. User (Kaif) credentials bhejta hai: POST /api/login { user: "kaif", pass: "..." }.
2. Server DB me check karta hai: Password match ho gaya.
3. Server do JSON objects taiyaar karta hai:
  • Header: {"alg":"HS256","typ":"JWT"}
  • Payload: {"sub":"1001", "name":"Kaif", "role":"user", "exp":1725501900}
4. Server dono ko Base64URL encode karta hai: header_b64 + "." + payload_b64.
5. Secret Signing: Server apni private environment key (SERVER_SECRET) se cryptographic HMAC-SHA256 signature calculate karta hai:
signature = HMAC_SHA256(header_b64 + "." + payload_b64, SERVER_SECRET) 6. Teeno parts ko dot (.) se jodkar compact JWT client ko response me bhej diya jata hai. Server is token ko database me SAVE NAHI KARTA — client ko deliver karke server memory se discard kar deta hai! 1. User (Kaif) logs in via POST /api/login.
2. Server verifies password against database.
3. Server creates Header & Claims Payload.
4. Server encodes both to Base64URL strings.
5. Server signs header + "." + payload using its private secret key (SERVER_SECRET).
6. The combined token is returned to the client. The server does NOT save the token in any database or session cache!
STEP 2 • TRANSMISSION 🚀

Client Request Ke Sath Token Bhejna

1. Client token ko browser memory ya secure HttpOnly, Secure, SameSite cookie me hold karta hai.
2. Jab bhi Kaif koi protected API call karta hai (jaise account balance dekhna ya order place karna):
Client request ke standard HTTP header me token attach karta hai:
GET /api/v1/profile HTTP/1.1
Host: api.enterprise.com
Authorization: Bearer eyJhbGci...eyJzdWI...dBjft...
3. Network ke through yeh token bina kisi previous server handshake ke backend API server tak pahunchta hai. 1. Client stores token in memory or an HttpOnly cookie.
2. For every protected API call, client transmits token in standard header:
Authorization: Bearer <token>
3. The token arrives at the API server without needing any prior server-side session lookup.
STEP 3 • VERIFICATION (ZERO DB QUERY) ⚡

Server Bina Database Ke Kaise Validate Karta Hai?

Server ke paas database me koi token record nahi hai, fir bhi server 100% mathematical certainty se kaise verify karta hai?
  1. Token Split: Server incoming token ko 3 tukdo me todta hai: header, payload, aur received_signature.
  2. Recalculate Signature: Server client ke signature par bharosa nahi karta. Server apne hidden SERVER_SECRET key se formula dobara run karta hai:
    expected_sig = HMAC_SHA256(header + "." + payload, SERVER_SECRET)
  3. Math Comparison: Server compare karta hai:
    expected_sig === received_signature
  4. Agar match hua: Header aur payload me 1 character bhi modify nahi hua! Server payload se user_id: 1001 nikal kar request instant allow karta hai.
  5. Agar tamper hua: Math fail! Token turant reject (HTTP 401).
 Even with zero database lookups, the server validates mathematically:
1. Split: Splits token into Header, Payload, and Signature.
2. Recalculate: Server runs HMAC-SHA256 over received Header.Payload using its own secret key.
3. Compare: If computed signature matches received signature, payload integrity is guaranteed!
4. Authorize: Extracts user identity directly from payload and fulfills request in microseconds.

Server ne compute kiya: HMAC("header.payload", SECRET).
Server signature: dBjftJeZ4CVP...

Attacker Kaif ne base64 decode kiya, payload me "role": "admin" badal diya.

JWT me server par ZERO session storage hoti hai. Token ka validation pure CPU mathematical calculation hai jo microsecond me execute hota hai. Yahi wajah hai ki modern microservices aur distributed systems JWT use karte hain. 💡 Why JWT is "Stateless": Traditional architectures stored millions of active session rows in DB/Redis. JWT requires zero server storage—token verification is pure CPU cryptographic math executed in microseconds across any distributed microservice.

JWT Security Ke 4 Pillars The 4 Pillars of JWT Security

Kisi bhi production application me JWT implement karte waqt in 4 cryptographic aur architectural pillars ka palan karna anivarya (mandatory) hai: Production JWT architectures must adhere to these 4 non-negotiable security pillars to prevent total authentication collapse:

Pillar 1: Strict Algorithm Whitelisting & Header Pinning (Never Trust Client Headers)

Kyu Zaroori Hai: JWT ke header me "alg" field hoti hai jo client server ko bhejta hai. Agar backend library bina validation ke header me aane wale algorithm par vishwas kar leti hai, to attacker do khatarnak attacks execute karta hai:
1. "alg": "none" Attack: Attacker algorithm ko "none" kar deta hai aur signature ko blank chhod deta hai. Flawed libraries signature verify kiye bina user ko login kar leti hain!
2. Algorithm Confusion Attack (RS256 ➔ HS256): Server asymmetric RSA public key se check karna chahta hai, lekin attacker header me symmetric HS256 bhej deta hai. Server public key ko HMAC secret samajh kar verify kar leta hai.
Secure Solution: Verification code me algorithm ko hardcode karein: jwt.verify(token, key, { algorithms: ['RS256'] }). Header ke alg ko kabhi bhi dynamic choice na banane dein. Why it's Critical: The "alg" header is untrusted user input. If your verification library blindly trusts what the client supplies, adversaries perform signature stripping via "alg": "none" or execute Algorithm Confusion by switching asymmetric RS256 to symmetric HS256 and signing with the exposed public key.
Secure Solution: Explicitly whitelist permitted algorithms during verification: jwt.verify(token, key, { algorithms: ['RS256'] }). Never allow the unverified token header to dictate server algorithm selection.

Pillar 2: High-Entropy Secrets & Key Storage (Anti-Brute Force Protection)

Kyu Zaroori Hai: HMAC-SHA256 (HS256) me ek symmetric password (secret key) use hoti hai. Kyunki JWT token browser ke paas hota hai, attacker us token ko download karke apne computer par offline le ja sakta hai. Wo Hashcat ya John the Ripper jaise tools se per second 10 arab passwords test karta hai. Agar aapka secret "secret", "company123" ya "jwtpassword" hai, to wo 5 second me crack ho jayega. Ek baar secret mil gaya, to attacker kisi bhi user ya CEO ka fake token mint kar sakta hai.
Secure Solution: Secret key hamesha cryptographically secure random number generator (CSPRNG) se kam se kam 256 bits (32 random bytes) ki generate karein aur use environment secret managers (AWS Secrets Manager / Vault) me rakhein, source code me nahi. Why it's Critical: In symmetric signing (HS256), the same secret signs and verifies tokens. Attackers extract the JWT and crack weak secrets offline using GPU-accelerated tools (Hashcat) against rockyou dictionaries without sending a single request to your server. A cracked secret permits forging valid signatures for any identity.
Secure Solution: Enforce minimum 256-bit cryptographic entropy (e.g., crypto.randomBytes(32).toString('hex')). Securely store keys in hardware security modules (HSM) or cloud secret vaults, never in code repositories.

Pillar 3: Asymmetric Key Separation (Public-Private Key Architecture)

Kyu Zaroori Hai: Modern microservice architecture me darjano services (billing, orders, notifications, inventory) hoti hain. Agar aap HS256 symmetric secret use karenge, to har service ko token verify karne ke liye wahi secret key deni padegi. Agar kisi ek chhoti service (jaise logging worker) ka server hack ho gaya, to attacker puri company ke sabhi systems ke liye fake admin tokens generate kar sakega!
Secure Solution: Hamesha asymmetric algorithms (RS256 ya ES256) use karein. Sirf Central Authentication Server ke paas token sign karne ki Private Key hoti hai. Baaki sabhi downstream API microservices ko sirf verify karne ke liye Public Key di jati hai. Public key leak hone par bhi koi naya token nahi bana sakta! Why it's Critical: In distributed microservice environments, using symmetric HS256 requires sharing the signing secret across every service. If a low-privilege analytics worker is breached, the attacker gains the master signing secret and mints root tokens for the entire enterprise.
Secure Solution: Implement asymmetric cryptography (RS256 / ES256). Only the dedicated Identity Provider (IdP) holds the Private Key to sign tokens. Downstream API gateways only receive the Public Key to verify signatures, guaranteeing zero privilege escalation even if a gateway is compromised.

Pillar 4: Short Token Lifetime (TTL) & Stateless Revocation Strategy

Kyu Zaroori Hai: Traditional sessions me agar user logout karta hai ya account hack hota hai, to database me session delete karte hi access turant band ho jata hai. Lekin stateless JWT me server database check nahi karta; jab tak token ka expiry time (exp) valid hai, token accept hota rahega! Agar aapne 30-day token banaya aur wo XSS se chori ho gaya, to attacker 30 din tak logged in rahega!
Secure Solution: Access tokens ka lifetime bohot chota rakhein (5 se 15 minutes). Token renew karne ke liye Refresh Tokens use karein jo HttpOnly, Secure cookie me save hote hain. Instant logout ke liye Redis me revoked token IDs (jti) ki short-lived blocklist rakhein ya database me token_version increment karein. Why it's Critical: Stateless JWTs cannot be instantly "deleted" by the server. As long as the expiration claim (exp) is in the future and the signature is valid, the token is accepted. Issuing 30-day access tokens means an XSS theft gives attackers a month of uncontrolled access even after the victim changes their password.
Secure Solution: Enforce short access token lifetimes (5–15 minutes max) paired with HttpOnly, Secure, SameSite refresh tokens. Support immediate revocation via Redis-backed denylists of unique token IDs (jti) or incrementing a user-level token_version on password change.

JWT Attack Vectors Kaise Kaam Karte Hain? How JWT Attack Vectors Work

JWT attacks cryptographic vulnerabilities aur flawed verification logic ka fayda uthate hain. Niche top 4 attack execution pipelines samjhai gayi hain: JWT attacks leverage cryptographic implementation flaws and parser leniency. Below are the 4 primary execution pipelines:

Vector 1: The "none" Algorithm Signature Stripping

RFC 7519 me debugging purposes ke liye "none" algorithm define kiya gaya tha. Agar API library is algorithm ko reject nahi karti, to attacker header me "alg": "none" set karke signature part ko pura blank chhod deta hai (header.payload.). Server signature verify kiye bina payload ko valid maan leta hai! RFC 7519 originally permitted an algorithm termed "none" for unsecure tokens. If backend libraries fail to disallow it, an adversary sets "alg": "none", strips the signature, and modifies claims arbitrarily (header.payload.). The server accepts the forged payload.

Vector 2: Algorithm Confusion (Asymmetric RS256 ➔ Symmetric HS256)

Jab server RS256 (RSA asymmetric) use karta hai, to token private key se sign hota hai aur public key se verify. Attacker header ko change karke "alg": "HS256" kar deta hai. Agar server library key parameter ko algorithm-agnostic rakhti hai, to server verification ke dauran public key (jo public hoti hai) ko HMAC secret samajhkar verify karta hai! Attacker usi public key se HS256 token banakar auth bypass kar leta hai. When a server intends to verify asymmetric RS256 signatures using an RSA public key, an attacker changes the algorithm to symmetric HS256. If the verification routine does not enforce RS256, it treats the public key string as the HMAC symmetric secret. The attacker HMAC-signs the forged token using the publicly known public key!

Vector 3: Offline HMAC Secret Key Cracking

Kyunki JWT client ke paas accessible hota hai, attacker token ko offline le jakar tools jaise Hashcat ya John the Ripper (rockyou.txt dictionary) ke sath GPU-accelerated brute force karta hai. Agar secret simple ho (e.g. secret, admin123, jwtpass), to secret minute bhar me nikal aata hai aur attacker arbitrary tokens sign kar sakta hai. Because HMAC tokens are stored on client browsers and APIs, adversaries perform offline dictionary attacks via Hashcat/John the Ripper against rockyou wordlists without triggering server rate limits. Weak static secrets are cracked in seconds.

Vector 4: Key ID (`kid`) Parameter Injection

JWT header me optional kid (Key ID) parameter hota hai jo batata hai database ya filesystem me se kaunsi key pick karni hai. Agar backend ise sanitize nahi karta, to attacker Path Traversal (e.g. "kid": "../../../dev/null") inject karta hai. Linux par /dev/null empty hota hai, jisse HMAC empty string "" se verify ho jata hai! Ya SQLi inject karke key value control kar leta hai. The kid header parameter specifies which key file or DB entry to retrieve. Without sanitization, adversaries execute Directory Traversal (e.g., "kid": "../../../dev/null") forcing validation against an empty buffer, or inject SQL statements returning arbitrary signing keys.

JWT Code Prevention & Secure Implementation JWT Code Prevention & Secure Implementation

JWT vulnerabilities se bachne ke liye token verification me algorithm ko explicitly lock karna aur cryptographic keys ko securely manage karna anivarya hai. To prevent JWT vulnerabilities, verify routines must explicitly pin permissible algorithms and safeguard signing keys.

❌ Vulnerable Implementation (Node.js / Express) 
// VULNERABLE: Relies on incoming token's header algorithm
app.use((req, res, next) => {
  const token = req.headers['authorization']?.split(' ')[1];
  
  // DANGER: No algorithm whitelist! Accepts 'none' and 'HS256'
  jwt.verify(token, secretOrPublicKey, (err, decoded) => {
    if (err) return res.status(401).json({ error: "Invalid Token" });
    req.user = decoded;
    next();
  });
});
✅ Secure Implementation (Node.js / Express) 
// SECURE: Explicit algorithm pinning and claim validation
app.use((req, res, next) => {
  const token = req.headers['authorization']?.split(' ')[1];
  
  jwt.verify(token, PUBLIC_RSA_KEY, {
    algorithms: ['RS256'], // Enforce RS256 strictly!
    issuer: 'https://auth.company.internal',
    audience: 'https://api.company.internal',
    maxAge: '15m'
  }, (err, decoded) => {
    if (err) return res.status(401).json({ error: "Unauthorized" });
    req.user = decoded;
    next();
  });
});

✅ Python (PyJWT) Secure Verification

security_jwt.py 
import jwt
from fastapi import HTTPException, Security

def verify_user_token(token: str):
    try:
        # Always pass algorithms as a list; disallows algorithm confusion & none
        payload = jwt.decode(
            token,
            PUBLIC_KEY_PEM,
            algorithms=["RS256"],
            options={"require": ["exp", "sub", "iss"]},
            issuer="https://auth.company.internal"
        )
        return payload
    except jwt.PyJWTError:
        raise HTTPException(status_code=401, detail="Invalid or expired token")
🛡️ 3 Golden Rules for JWT Defense
  • Rule 1: Never Trust the `alg` Header: Verification methods must enforce an explicit allowed algorithms array. Never allow the unauthenticated token header to decide the verification algorithm.
  • Rule 2: Enforce 256-bit Key Entropy: If using HMAC (HS256), the secret must be generated using a cryptographically secure pseudo-random number generator (CSPRNG) with minimum 32 random bytes.
  • Rule 3: Always Validate Standard Claims: Require and enforce exp (Expiration), nbf (Not Before), and iss (Issuer). Never issue long-lived access tokens without revocation capabilities.

                Frequently Asked Questions (FAQ)
                Frequently Asked Questions (FAQ)
              

            


            

              
              

                
Q1: JWT me RS256 aur HS256 algorithm confusion attack kyu aur kaise kaam karta hai?

                

                  Answer: RS256 ek asymmetric algorithm hai jisme private key token sign karti hai aur public key verify. Lekin HS256 symmetric algorithm hai jisme wahi key signing aur verification dono ke liye use hoti hai. Agar verification function algorithms: ['RS256'] restrict nahi karta, to attacker token ko "alg": "HS256" se sign karta hai using the server's public RSA key (jo openly available hoti hai). Backend public key ko HMAC secret ki tarah treat karke signature verify kar leta hai aur attack safal ho jata hai.
                  Answer: RS256 uses asymmetric cryptography (private key signs, public key verifies). HS256 uses symmetric cryptography (same secret signs and verifies). When backend verification libraries accept any algorithm in the token header, an attacker changes "alg" to "HS256" and HMAC-signs the token using the server's publicly accessible RSA public key as the symmetric secret string. The server checks the signature against the public key file and accepts it.
                

              


              
              

                
Q2: Stateless JWT architecture me immediate logout ya token revocation kaise implement kiya jata hai?

                

                  Answer: Stateless JWTs by default revoke nahi kiye ja sakte jab tak unka exp khatam na ho. Isko solve karne ke 3 best enterprise patterns hain: (1) Short-lived access tokens (5–15 mins) with server-managed refresh tokens, (2) Redis Token Blocklist: Logout par token jti (JWT ID) ko Redis me exp time tak store karna aur middleware me check karna, (3) User Token Version: Database me token_version rakhna aur JWT claim me embed karna; password reset par version increment kar dena.
                  Answer: Pure stateless JWTs cannot be revoked prior to expiration without maintaining state. Recommended approaches: (1) Issue short-lived access tokens (5-15 mins) paired with revocable refresh tokens in a database, (2) Redis Revocation Denylist: Cache revoked jti identifiers in Redis with a TTL equal to the token's remaining lifetime, (3) Token Versioning: Store a token_version counter on the user database record; incrementing it invalidates all previously issued tokens.
                

              


              
              

                
Q3: JWS (JSON Web Signature) aur JWE (JSON Web Encryption) me kya difference hai?

                

                  Answer: Standard JWTs JWS hote hain—jisme data Base64URL encoded hota hai aur cryptographically signed hota hai (Integrity provide karta hai, Confidentiality nahi; koi bhi payload padh sakta hai). Jabki JWE me payload encrypted hota hai (e.g. AES-GCM), jisse token ka content unauthorized parties ke liye completely unreadable hota hai.
                  Answer: A JWS provides digital signatures ensuring payload integrity, but claims remain Base64URL encoded and readable in plaintext. A JWE encrypts the payload so that only authorized recipients possessing the decryption key can inspect the claims, guaranteeing both confidentiality and integrity.
                

              


              
              

                
Q4: JWT header injection attacks (jku, jwk, kid) se bachne ka sabse secure tarika kya hai?

                

                  Answer: (1) Client-controlled jku (JWK Set URL) parameters ko completely disable ya strict corporate domain whitelist se match karein, (2) Inline jwk public key injection ko server par deny karein, (3) kid parameter ko direct filesystem path ya raw SQL query me na dalein; safe pre-configured dictionary lookup (e.g. KEYS[kid]) use karein.
                  Answer: (1) Strictly disallow or enforce strict domain whitelisting on jku headers, (2) Reject self-contained jwk public keys supplied by the client, (3) Never concatenate kid directly into filesystem paths (path traversal) or database queries (SQLi); map kid against an immutable in-memory map of known public keys.
                

              


              
              

                
Q5: Kya client side par JWT ko localStorage me rakhna safe hai ya HttpOnly cookie me?

                

                  Answer: HttpOnly, Secure, SameSite=Strict/Lax cookies sabse zyada safe hain kyunki JavaScript document.cookie se token read nahi kar sakti, jisse XSS attacks se token theft prevent ho jata hai. LocalStorage me token store karne par koi bhi injected XSS script token ko extract karke attacker ko bhej sakti hai.
                  Answer: HttpOnly, Secure, SameSite=Strict cookies are strongly recommended over LocalStorage. HttpOnly cookies cannot be accessed via JavaScript document.cookie, effectively insulating the token from XSS-driven token exfiltration.
