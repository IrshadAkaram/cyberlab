JSON Web Token (JWT) Kya Hai?What is a JSON Web Token (JWT)? JWT ek open standard (RFC 7519) format hai jiska use do parties (client aur server) ke beech securely claims (data) transfer karne ke liye hota hai. Modern web apps mein login ke baad server user ko session ID database mein save karne ke bajaye ek stateless JWT thama deta hai. Token mein user ki identity (jaise user_id: 101, role: "user") hoti hai, jise server ek cryptographic Signature se stamp karta hai. JWT is an open standard (RFC 7519) defining a compact, URL-safe container for transferring claims between client and server. Modern web apps use it for stateless authentication: instead of storing session IDs in a central database, the server issues a signed token containing user claims (e.g. user_id: 101, role: "user"), sealed with a cryptographic Signature.

JWT Vulnerabilities Tab Paida Hoti Hain jab backend server aane wale token ki signature ko verify karne mein laparwahi baratta hai — jaise "alg": "none" ko accept karna, weak secret key use karna jise seconds mein brute force kiya ja sake, ya asymmetric algorithm (RS256) ko symmetric (HS256) mein confuse kar dena. Aisi galatiyon se koi bhi attacker token mein apna role admin banakar bina password ke system ka full control le leta hai! JWT Vulnerabilities Occur when backend implementations improperly verify incoming token signatures — such as trusting the "alg": "none" header, using low-entropy secret keys susceptible to dictionary cracking, or misinterpreting asymmetric keys (RS256) under symmetric mode (HS256). These flaws empower attackers to forge arbitrary claims, escalate privileges to admin, and bypass authentication entirely!

JWT: Kyun Banaya, Kaise Kaam Karta Hai Aur Kya Flaws HainJWT: Why Engineered, How It Works & Vulnerability Mechanics

JWT authentication ki engineering zaroorat, internal execution lifecycle, aur vulnerabilities ki technical anatomy ko samjhein: Understand the engineering necessity of JWT, its internal cryptographic lifecycle, and vulnerability root causes:

1. Kyun Banaya Gaya? (Why JWT Was Engineered)1. Why Was It Engineered? (The Scaling Problem)

Traditional web architecture mein authentication Stateful hoti thi. Jab user login karta tha, server ek random Session ID banakar database ya Redis cache mein save karta tha, aur user ko Set-Cookie: session_id=abc123xyz bhejta tha. Lekin modern applications ke scale hone par do badi problems aayi: Traditional web architectures relied on Stateful Sessions. When a user authenticated, the server generated a random session identifier, stored it in a central database or Redis cluster, and returned a cookie. As systems expanded into microservices, two critical bottlenecks emerged:

  • Database Bottleneck: Har incoming HTTP request par database mein SELECT * FROM sessions WHERE id = '...' chalana padta tha. Millions of users par session store server crash hone lagta tha.
  • Distributed Microservices: Agar user ka login Auth Service par hua hai, toh Payment Service ya Video Streaming Service ko user ka session check karne ke liye baar-baar centralized database ko query karna padta tha.

The Solution (RFC 7519): JWT ko ek Stateless, Self-Contained Token banaya gaya. Server ko database mein kuch save hi nahi karna! User ki identity (user_id, email, permissions) token ke andar hi pack hoti hai. Server bas mathematical Cryptographic Signature verify karta hai aur request ko bina DB lookup ke process kar leta hai. The Solution (RFC 7519): JWT was designed as a Stateless, Self-Contained Container. The server persists zero session state in memory or databases! User claims (user_id, role, expiration) travel directly within the token. The server verifies mathematical authenticity in RAM via its Cryptographic Signature in fractions of a millisecond.

2. Kaise Kaam Karta Hai? (Under The Hood Execution)2. How It Works Under The Hood

Ek JWT string teen Base64URL-encoded hisson se banti hai, jinhe dot (.) se separate kiya jata hai: A JWT string consists of three Base64URL-encoded segments delimited by periods (.):

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyIjoidmljdGltIiwicm9sZSI6InVzZXIiLCJleHAiOjE3MDAwMDAwMDB9.dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
Segment Underlying JSON / Mathematical Formula Technical Purpose
1. Header {"alg": "HS256", "typ": "JWT"} Specifies token metadata and cryptographic signing algorithm (e.g. HS256, RS256, ES256).
2. Payload (Claims) {"user": "alice", "role": "user", "exp": 1725400000} Contains assertions (claims) about the entity. Note: Base64URL encoded, NOT encrypted! Cleartext to all.
3. Signature HMACSHA256(Base64Url(Header) + "." + Base64Url(Payload), secretKey) Cryptographic hash guaranteeing tamper-resistance. If a single byte of Header or Payload changes, the hash mismatch fails!
🏛️ REAL-WORLD ANALOGY

Socho ek VIP Club ka Entry Wristband hai. Wristband par aapka naam aur tier likha hai (Payload), serial code likha hai (Header), aur sabse neeche club manager ki holographic tamper-proof stamp (Signature) lagi hui hai! Agar aap marker se apna tier "General" se badalkar "VIP" kar doge, toh manager ki holographic seal mismatch ho jayegi aur guard entry reject kar dega. Lekin agar gatekeeper stamp check karna hi chhod de (None algorithm) ya manager ki duplicate seal chor ke haath lag jaye (Weak Secret) — tab koi bhi fake pass bana sakta hai! Imagine a VIP concert wristband stating your name and tier (Payload), sealed with an official tamper-proof holographic stamp (Signature). If you alter your tier from "General" to "VIP", the seal mismatches and entry is denied. However, if the gatekeeper stops checking the seal (None Algorithm) or an attacker duplicates the signing stamp (Weak Secret), forged passes gain total access!

JWT specification ke mutabiq, "alg": "none" ka matlab hota hai ki token bina signature ke hai. Kuch flawed verification libraries ya developers header me aaye alg parameter par andha bharosa karte hain: Per RFC 7519 specifications, "alg": "none" denotes an unsecured token without verification. Vulnerable libraries inspect the incoming header's alg field and conditionally skip signature checks if set to none! 

// 1. Attacker changes Header to:
{ "alg": "none", "typ": "JWT" }

// 2. Attacker changes Payload to:
{ "user": "admin", "role": "superuser", "admin": true }

// 3. Attacker removes the signature completely (keeps the trailing dot):
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJ1c2VyIjoiYWRtaW4iLCJyb2xlIjoic3VwZXJ1c2VyIiwiYWRtaW4iOnRydWV9.
⚠️ DANGER POINT

Agar backend library ne check kiya if (token.header.alg === 'none') return true; toh server bina signature verify kiye attacker ko superuser rights de dega! Note karein ki token ke aakhri mein dot (.) rehna zaroori hai taaki 3-part syntax valid rahe. If the server runtime checks if (header.alg === 'none') verify = true;, privilege escalation succeeds instantly without cryptographic keys! Notice the trailing dot (.) must remain intact to preserve the three-segment syntax.

Kayi developers development ke waqt secret = "secret123" ya secret = "supersecret" likh kar production mein chhod dete hain. Kyunki JWT client ke browser mein aati hai, attacker ko target server par baar-baar request bhejne ki zaroorat nahi padti! Attacker apne GPU par hashcat ya jwt-cracker chala kar 1 second mein lakho passwords test kar leta hai: Developers frequently rely on placeholder secrets (e.g. "secret123", "password", "jwtsecret"). Because JWTs reside on the client, cracking occurs completely offline with zero rate-limiting or server alerts: 

# Cracking JWT secret offline using Hashcat
hashcat -m 16500 -a 0 jwt_token.txt rockyou.txt

# Result in 3 seconds:
eyJhbGciOiJIUzI1NiIsInR5... : secret123 [FOUND]

Ek baar secret mil gaya, toh attacker apne system par baithe-baithe kisi bhi user ya admin ka valid signed JWT generate kar sakta hai! Once the symmetric secret is cracked, the attacker possesses the cryptographic authority to forge legitimate tokens for any user on the platform!

Yeh JWT ka sabse shandaar aur dimaag hila dene wala attack hai! Isko bilkul asaan shabdon mein samjhein: One of the most elegant cryptographic implementation exploits. Let us break down the mathematical confusion:

  • Normal RS256: Server Private Key se sign karta hai, aur Public Key se verify karta hai. Public key internet par sabhi ke paas hoti hai (e.g. /jwks.json).
  • The Flaw: Server ka code kuch aisa likha hai: jwt.verify(token, key) bina algorithm enforce kiye!
  • Attacker's Trick: Attacker token ka header badal kar kar deta hai "alg": "HS256" (Symmetric HMAC). Ab server sochta hai ki yeh HMAC token hai aur verification ke liye usi Public Key string ko HMAC secret maan leta hai!
  • Exploit: Kyunki public key attacker ke paas pehle se thi, attacker usi public key ko secret password bana kar apna fake admin token khud sign kar leta hai! Server dono taraf match paata hai aur access de deta hai!

👑 1. Total Privilege Escalation To Superuser / Admin1. Total Privilege Escalation To Superuser / Admin

Application agar user ke role aur permissions token ke andar store karti hai (e.g. "isAdmin": false, "org_id": 14), aur signature check bypass ho jata hai (via None algorithm ya weak secret), toh attacker token decode karke "isAdmin": true likh deta hai aur billing portals, customer PII data, ya master consoles ko fully seize kar leta hai! If claims dictate authorization (e.g. "isAdmin": false) and signature checks fail due to algorithmic flaws or broken verification, attackers rewrite their claims to "isAdmin": true, obtaining instantaneous administrative privileges across the infrastructure.

🎭 2. RS256 To HS256 Key Confusion (Algorithm Switching)2. RS256 To HS256 Key Confusion (Algorithm Switching)

Jab server asymmetric algorithm RS256 use karta hai, toh verification ke liye Public RSA Key use hoti hai jo sabhi ke liye open hoti hai. Flawed libraries mein attacker header ko "alg": "HS256" mein switch kar deta hai aur server ki public key ko HMAC secret ki tarah use karke sign kar deta hai. Server token ko valid maan leta hai aur kisi bhi user ya CEO ka account instantly hijack ho jata hai! When an authentication server validates RS256 tokens using a public key, an attacker changes the header to "alg": "HS256" and signs the token with the server's public key as the HMAC shared secret. Flawed libraries pass the public key directly to the HMAC validator, culminating in arbitrary account takeover!

🌐 3. JKU Header Injection & Key Spoofing3. JKU Header Injection & Key Spoofing

Agar server token header mein diye gaye jku (JWK Set URL) parameter ko bina whitelist ke fetch karta hai, toh attacker jku: "https://attacker-server.com/fake_keys.json" daal deta hai. Backend server attacker ke server se public key download karke attacker ke signature ko valid maan leta hai! If the server dynamically resolves public keys via the jku header without strict domain allowlists, an attacker points it to https://attacker.com/keys.json. The backend ingests the attacker's public key and validates the forged token as authentic!

📁 3. "kid" (Key ID) Path Traversal / SQL Injection3. "kid" (Key ID) Path Traversal / SQL Injection

Header parameter kid agar filesystem path ki tarah use hota hai, toh attacker "kid": "../../../../../dev/null" inject kar deta hai. Linux mein /dev/null ek empty file hoti hai (0 bytes). Attacker token ko empty string ("") se HMAC sign karta hai aur server par validation 100% pass ho jati hai! If the kid header resolves directly against disk without sanitization, an attacker injects "kid": "../../../dev/null". In UNIX, /dev/null is an empty file. Signing the token with an empty secret string ("") satisfies verification!

🤔 Most Confusing Questions Solved 🤔 Most Confusing Questions Solved

BILKUL NAHI! Standard JWT (JWS - JSON Web Signature) sirf Base64URL ENCODED hota hai, encrypted nahi hota. Koi bhi insaan jwt.io par token paste karke payload ka poora data padh sakta hai. JWT mein kabhi bhi raw password, credit card number, ya secret API keys nahi rakhni chahiye! (Agar data chupana ho toh JWE - JSON Web Encryption use kiya jata hai). ABSOLUTELY NOT! Standard JWTs (JWS) are merely Base64URL encoded, NOT encrypted. Anyone intercepting the token can paste it into jwt.io and inspect all claims in cleartext. Never store passwords, PINs, or sensitive PII in standard JWT payloads. To encrypt claims, JWE (JSON Web Encryption) must be used.
Security best practice ke mutabiq HttpOnly, Secure, SameSite Cookie hamesha behtar hai! Agar aap LocalStorage mein JWT rakhte hain aur site mein choti si bhi XSS vulnerability hoti hai, toh attacker JavaScript se localStorage.getItem('jwt') karke user ka token chura lega. HttpOnly cookies ko JavaScript access nahi kar sakti, isliye XSS se token chori hone se bach jata hai. Security guidelines strongly recommend HttpOnly, Secure, SameSite Cookies. If stored in LocalStorage, any Cross-Site Scripting (XSS) vulnerability allows an attacker to execute localStorage.getItem('token') and steal the session. HttpOnly cookies block JavaScript access, neutralizing XSS credential theft.
Stateless JWT ka sabse bada challenge revocation hai. Jab tak token ka exp (expiry time) khatam nahi hota, tab tak wo valid rehta hai. Solution: (1) Token ka lifespan chota rakhein (e.g. 10-15 minutes) aur sath mein Refresh Token use karein, (2) Redis cache mein logout kiye gaye tokens ka ek blacklist (denylist) maintain karein jisme unki expiry tak token ID (jti) save rahe. Statelessness makes immediate revocation challenging. Until expiration (exp), signatures remain mathematically valid. Industry solutions: (1) Issue short-lived access tokens (5-15 mins) paired with revocable Refresh Tokens, (2) Implement a Redis memory denylist matching the unique Token ID (jti) until expiry.
