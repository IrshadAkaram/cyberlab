Local File Inclusion (LFI)Local File Inclusion (LFI) ek aisi high-severity vulnerability hai jisme web application user ke input ko use karke server ki local files ko dynamic load (include/require) karti hai bina strict sanitization ya allowlisting ke. Path Traversal jahan sirf file content ko read karta hai, LFI included file ko as code execute karta hai! is a critical vulnerability that occurs when a web application dynamically includes local filesystem files based on unsanitized user input. While directory traversal merely reads files, file inclusion interprets and executes file contents within the server's runtime context!

Path Traversal se LFI ka sabse bada farak: Agar aap /etc/passwd include karenge, toh woh text print karega. Lekin agar aap php://filter wrappers, data:// stream wrappers, ya Session File Poisoning use karenge, toh attacker backend server par full interactive Web Shell aur Remote Code Execution (RCE) hasil kar leta hai! The critical distinction from Path Traversal: While reading /etc/passwd reveals sensitive text, including PHP wrappers (php://filter, data://) or poisoning server session files enables an attacker to inject PHP payloads and achieve full interactive Remote Code Execution (RCE)!

1. Kyun Banayi Gayi? (The Architectural Problem Solved)1. Why Was It Engineered? (The Architectural Problem Solved)

Web applications me code reusability aur clean modular architecture maintain karne ke liye developers common components (jaise header, navigation, footer, language translations) ko alag-alag files me store karte hain. Ek single master layout file (e.g. index.php) me URL parameter ke hisaab se specific page view include kiya jata hai (jaise ?page=contact ya ?lang=es). Isse har page ke liye duplicate HTML aur code likhne ki zaroorat nahi padti! To maintain modular code and reusability, web applications split visual layouts into partials (headers, navbars, footers, language strings). A central controller template dynamically loads specific views based on query parameters (e.g. ?page=dashboard). This eliminates the redundancy of copying common logic across hundreds of static pages.

2. Kaise Kaam Karta Hai? (Under The Hood Mechanics)2. Under The Hood Mechanics (Runtime File Interpretation)

PHP me jab include($_GET['page']) call hota hai, runtime kernel OS filesystem API (e.g. open(), stat()) ke zariye path resolve karta hai. File read karne ke baad runtime tokenizer us file ke content ko parse karta hai: agar usme PHP opening tag <?php ... ?> milta hai, toh engine use machine instructions me compile karke execute karta hai; agar PHP tag nahi hota, toh direct plaintext browser ko output kar diya jata hai! When PHP encounters include($_GET['page']), the runtime invokes OS filesystem primitives (open(), read()). The tokenizer scans the target file: if PHP tags (<?php ... ?>) exist, the Zend engine compiles and executes the instructions with the privileges of the web server (e.g., www-data); otherwise, the plaintext is emitted directly to the HTTP response!

Agar aap direct include('config.php') karenge, toh PHP config.php ko execute kar dega aur browser me blank page dikhega kyunki database passwords variables me save ho jate hain aur print nahi hote. Lekin PHP ke built-in Stream Filter Wrappers file ko execute hone se pehle Base64 me encode kar dete hain: Directly including config.php simply executes the script, outputting nothing because database passwords are bound to internal variables. Jab user website par login ya interact karta hai, PHP session data ko disk par standard path par save karta hai: /var/lib/php/sessions/sess_<PHPSESSID> ya /tmp/sess_<PHPSESSID>. Attacker apne session variable me malicious PHP code inject karta hai: When users interact with a PHP app, session variables are serialized directly onto the server's local disk at /var/lib/php/sessions/sess_<PHPSESSID> or /tmp/sess_<PHPSESSID>. Attackers craft an HTTP request saving PHP payload code into their session: 

// Step 1: Poison the session file via input field (e.g. username):
POST /login.php HTTP/1.1
Cookie: PHPSESSID=attacker123

username=<?php system($_GET['cmd']); ?>

// Session file /var/lib/php/sessions/sess_attacker123 now contains:
// user|s:32:"<?php system($_GET['cmd']); ?>";

// Step 2: Include the session file via LFI:
GET /index.php?page=/var/lib/php/sessions/sess_attacker123&cmd=id;uname -a HTTP/1.1

// Output:
uid=33(www-data) gid=33(www-data) Linux prod-app-01 5.15.0-generic

Server par complete interactive Remote Code Execution (RCE) establish ho jata hai! Attacker reverse shell connect karke pure database aur server ko dump kar sakta hai! The PHP engine parses the session file, detects the PHP tags, and executes the OS command! The attacker obtains an interactive shell as www-data!

Agar session file accessible na ho, toh attacker web server access log (e.g. /var/log/apache2/access.log ya /var/log/nginx/access.log) ko poison karta hai. Attacker User-Agent header me PHP code bhejta hai: User-Agent: <?php system($_GET['c']); ?>. Web server is line ko access log me likh leta hai. Jab attacker ?page=/var/log/apache2/access.log&c=whoami call karta hai, toh log me saved payload execute ho jata hai! If session directories are restricted, attackers target server access logs (/var/log/apache2/access.log). By dispatching a request with a malicious User-Agent (User-Agent: <?php system($_GET['c']); ?>), the web server records the PHP code in its log. Including the log file executes the payload with root/web-server privileges!

1. PHP Dynamic Inclusion Security1. PHP Dynamic Inclusion Security

// ❌ INSECURE: Blindly concatenating user input into include()
$page = $_GET['page'];
include("templates/" . $page . ".php"); // Allows ../../ or php://filter!

// ✅ SECURE: Strict Whitelist Array Mapping
$ALLOWED_PAGES = [
    'home'     => 'templates/home.php',
    'about'    => 'templates/about.php',
    'contact'  => 'templates/contact.php'
];

$page = $_GET['page'] ?? 'home';
if (!array_key_exists($page, $ALLOWED_PAGES)) {
    http_response_code(404);
    die("Page not found!");
}
include($ALLOWED_PAGES[$page]);

2. PHP.ini Hardening Flags2. PHP.ini Hardening Flags

# Disable execution of remote URLs inside include/require
allow_url_include = Off

# Disable opening remote URLs via file functions
allow_url_fopen = Off

# Restrict PHP file access strictly to application webroot
open_basedir = "/var/www/html:/tmp"

Path Traversal sirf file ka plaintext content read karta hai (jaise readfile() ya file_get_contents()). Agar us file me PHP code hoga, toh woh sirf screen par text ban kar dikhega. Lekin LFI file ko include() ya require() karta hai, jisse uske andar ka code SERVER PAR EXECUTE ho jata hai aur RCE banta hai! Path Traversal reads raw bytes as plaintext (like cat). If the target contains PHP code, Path Traversal merely prints the source. Local File Inclusion, however, evaluates the file via include(), executing embedded scripts in runtime memory to trigger Remote Code Execution (RCE)!
PHP 5.3.4 se pehle C-level string termination ke loophole se %00 string ke baad ke .php extension ko kat deta tha (e.g. /etc/passwd%00.php ban jata tha /etc/passwd). Lekin PHP 5.3.4+ aur modern runtimes me core level par null byte check laga diya gaya hai, jisse yeh reject ho jata hai. Ab wrappers aur session poisoning use hote hain! Prior to PHP 5.3.4, a null byte character ( / %00) truncated strings at the C-level, bypassing appended extensions like .php. Modern interpreters strictly reject null bytes in file paths, shifting real-world exploitation towards stream wrappers and session poisoning.

Inline data stream wrappers (data://, php://input) require allow_url_include = On. However, the read-oriented php://filter wrapper operates even when allow_url_include is disabled, making it universally effective for source code exfiltration!
