HTTP Host HeaderHTTP Host Header HTTP/1.1 ka ek mandatory request header hai jo batata hai ki client kis domain ya hostname ko access karna chahta hai (jaise Host: example.com). Virtual Hosting mein ek hi IP address par hazaron websites chalti hain, aur server isi Host header ko dekh kar decide karta hai ki request kis website ke paas bhejna hai. is a mandatory HTTP/1.1 request header specifying which domain or virtual host the client intends to access (e.g. Host: example.com). In Virtual Hosting, thousands of websites run on a single IP, and the web server inspects this header to route traffic to the intended site.

Host Header Injection tab banti hai jab backend application ya proxy is Host header ki value ko USER-SUPPLIED INPUT samajhne ke bajaye ek 100% "trusted configuration" maan leti hai. Agar developer password reset link banane, redirects karne, ya scripts include karne mein bina validation ke $_SERVER['HTTP_HOST'] use karta hai, toh attacker ise tamper karke Password Reset Poisoning, Web Cache Poisoning, aur SSRF jaise massive attacks execute kar sakta hai! Host Header Injection occurs when a backend application or reverse proxy treats the Host header as trusted system configuration rather than untrusted user input. If developers construct password reset links, redirect URLs, or script imports using $_SERVER['HTTP_HOST'] without strict validation, attackers manipulate it to trigger Password Reset Poisoning, Web Cache Poisoning, and Routing-based SSRF!

RFC 2616 RuleRFC 2616 Specification

HTTP/1.1 standard ke hisaab se har request mein Host header aana compulsory hai. Agar koi request bina Host header ke aati hai, toh server ko 400 Bad Request return karna hota hai. Under RFC 2616, every HTTP/1.1 request MUST include a Host header. Any request lacking a Host header must be rejected with 400 Bad Request.

Developers aksar ye soch lete hain ki Host header toh browser khud bhejta hai, isliye yeh safe hoga. Lekin attackers browser ki jagah Burp Suite, curl, ya custom Python scripts use karte hain. Attacker request bhejte waqt Host header ko kuch bhi likh sakta hai: Developers frequently assume that because browsers generate the Host header automatically, it can be trusted implicitly. However, security researchers and attackers use intercepting proxies like Burp Suite or curl to replace the Host header with arbitrary domains:

Modern websites aksar Reverse Proxies (Cloudflare, AWS ALB, Nginx, Varnish) ke peeche hoti hain. Jab front-end proxy request ko backend server tak forward karta hai, tab alag-alag headers create ya parse hote hain: Modern enterprise architectures sit behind Reverse Proxies, Load Balancers, and CDNs. Forwarding proxies frequently handle and inject auxiliary headers:

Header / Technique Exploitation Mechanism Impact
X-Forwarded-Host Backend frameworks (Django, Symfony, Rails) check this proxy header before standard Host. Overrides generated absolute URLs without breaking proxy routing.
Duplicate Host Headers Sending two Host headers (e.g. one for target.com, second for evil.com). Proxy routes on the first, backend processes the second!
Host with Arbitrary Port Host: target.com:@evil.com or Host: target.com:badport SSRF, SSRF-based redirection, or parser errors.
Absolute URI in Request Line GET https://target.com/ HTTP/1.1 with Host: evil.com Reverse proxy uses the request line; application uses the Host header.

🔑 1. Password Reset Poisoning (Zero-Interaction Account Takeover)1. Password Reset Poisoning (Zero-Interaction Account Takeover)

Jab user "Forgot Password" request karta hai, server ek secret cryptographic token generate karta hai aur user ki email par reset link bhejta hai. Agar server link banane ke liye Host ya X-Forwarded-Host use karta hai, toh attacker victim ke email ke sath apna domain inject kar deta hai. Victim jab email me link par click karta hai, secret token attacker ke server par leak ho jata hai, aur victim ka account turant hijack ho jata hai! When a user requests a password reset, the server generates a high-entropy secret token and emails a reset URL. If the server constructs this URL dynamically using the client's Host or X-Forwarded-Host, an attacker submits a reset request for the victim's email while pointing the Host to their own server. Clicking the email link leaks the token directly to the attacker, culminating in total account takeover!

🌐 2. Web Cache Poisoning (Mass XSS & Site-Wide Defacement)2. Web Cache Poisoning (Mass XSS & Site-Wide Defacement)

Front-end Caching proxies (Varnish, Cloudflare, Akamai) URL ko "Cache Key" maante hain lekin aksar Host header ko cache key me include nahi karte (unkeyed input). Attacker poisoned Host header bhej kar server se malicious JavaScript import (jaise <script src="//evil.com/app.js">) generate karwata hai. CDN is malicious response ko cache kar leta hai. Ab har legitimate visitor jo site kholega, uske browser me attacker ka script chalega — mass cookie theft aur defacement! Front-end caching reverse proxies determine cache entries using the request path (cache key) but often treat the Host or X-Forwarded-Host header as unkeyed input. If the backend reflects the Host in script tags or import URLs, the poisoned response is saved in the CDN cache. Every subsequent legitimate user visiting the homepage receives the attacker's malicious script — achieving mass Stored XSS!

🚪 3. Internal Virtual Host Routing & Access Control Bypass3. Internal Virtual Host Routing & Access Control Bypass

Kayi enterprise servers par internal admin panels (e.g. localhost:8080/admin ya internal.corp/admin) internet par direct accessible nahi hote. Lekin agar attacker public IP par request bhejte waqt Host: localhost ya Host: internal.corp bhejta hai, toh web server request ko internal private site par route kar deta hai, bypassing all network firewall rules! Many enterprise applications restrict administrative interfaces to local or private networks. However, sending a request to the public gateway with Host: localhost or Host: admin.internal.corp may convince the internal routing layer to grant access to restricted virtual hosts, bypassing IP firewalls!

1. PHP & Apache / Nginx Configuration1. PHP & Apache / Nginx Configuration

// ❌ INSECURE: Blindly trusting HTTP_HOST
$host = $_SERVER['HTTP_HOST'];
$redirect_url = "https://" . $host . "/dashboard";
header("Location: " . $redirect_url);

// ✅ SECURE: Use Hardcoded Whitelist or Fixed Base URL from Config
define('ALLOWED_HOSTS', ['portal.company.com', 'api.company.com']);
$host = $_SERVER['HTTP_HOST'];

if (!in_array($host, ALLOWED_HOSTS, true)) {
    http_response_code(400);
    exit("Invalid Host header");
}
$redirect_url = "https://" . $host . "/dashboard";

Host standard HTTP/1.1 header hai jo client web server ko bhejta hai. Jab beech mein reverse proxy (jaise Cloudflare ya Nginx) hoti hai, toh proxy original domain ko X-Forwarded-Host header mein wrap karke backend ko pass karti hai. Kayi frameworks (Django, Express, Spring) agar backend par X-Forwarded-Host paate hain, toh standard Host ko ignore karke is proxy header ko use kar lete hain! Host is the standard HTTP/1.1 header sent by the client. When requests traverse reverse proxies or load balancers, the proxy encapsulates the original requested host into X-Forwarded-Host. Many backend frameworks prioritize X-Forwarded-Host when building absolute URLs, making it a fertile vector if proxies don't strip incoming untrusted instances!
