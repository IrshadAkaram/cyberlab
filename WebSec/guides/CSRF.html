Ye Hua Kaise? CSRF Ka Asli MechanismHow Did This Happen? The Real Mechanism Of CSRF

COOKIE KYA HAI AUR BROWSER USE KAISE USE KARTA HAIWHAT A COOKIE IS AND HOW THE BROWSER USES IT

Cookie ek chhota sa text data hota hai jo user ke login karne ke baad server browser ko Set-Cookie response header ke through bhejta hai, aur browser use save kar leta hai. Uske baad, jab bhi us SAME domain par koi request jaati hai, browser automatically wahi cookie request ke saath attach karke bhej deta hai — server ko har request par dobara login karwane ki zaroorat nahi padti, kyunki cookie hi "main already logged in hoon" ka proof ban jaati hai. A Cookie is a small piece of text data that the server sends to the browser (via the Set-Cookie response header) after the user logs in, and the browser saves it. After that, whenever a request goes to that SAME domain, the browser automatically attaches that same cookie along with the request — the server doesn't need to make you log in again on every request, because the cookie itself becomes proof that "I'm already logged in."

YAHI AUTOMATIC ATTACHMENT CSRF KI JAD HAITHIS AUTOMATIC ATTACHMENT IS THE ROOT OF CSRF

Jab browser decide karta hai ki kis request ke saath kaunsi cookie bhejni hai, wo sirf ek cheez dekhta hai: request KAHAN JAA RAHI HAI (destination domain). Wo ye bilkul nahi dekhta ki request KAHAN SE AA RAHI HAI — kisi trusted tab se, ya kisi malicious website ke ek chhote se hidden form se. Agar Rahul ke browser mein sbi.com ke liye cookie save hai, toh sbi.com ko jaane wali HAR request — chahe wo asli banking page se ho ya freegift.com ke ek invisible form se — usi cookie ke saath jaayegi. When the browser decides which cookie to send with a request, it looks at exactly one thing: WHERE the request is GOING (the destination domain). It does not look at all at WHERE the request is COMING FROM — a trusted tab, or a hidden form on some malicious website. If Rahul's browser has a saved cookie for sbi.com, then EVERY request going to sbi.com — whether from the real banking page or from an invisible form on freegift.com — will go out with that same cookie attached.

⚠️ ISE "AMBIENT AUTHORITY" KEHTE HAIN⚠️ THIS IS CALLED "AMBIENT AUTHORITY"

Security terminology mein, jab koi credential (jaise cookie) automatically, bina kisi explicit user action ke, har relevant request ke saath attach ho jaaye, use ambient authority kehte hain. Password ya API key alag hain — unhe har baar explicitly type ya set karna padta hai. Cookie khud-ba-khud attach hoti hai, isliye browser aur server dono maan lete hain ki request genuine hai — aur wahi assumption CSRF mein galat nikalti hai. In security terminology, when a credential (like a cookie) attaches automatically to every relevant request, without any explicit user action, it's called ambient authority. A password or API key are different — they must be explicitly typed or set every single time. A cookie attaches itself automatically, so both the browser and the server assume the request is genuine — and it's exactly that assumption that turns out wrong in CSRF.

CSRF KAAM KARNE KE LIYE 3 ZAROORI SHART3 NECESSARY CONDITIONS FOR CSRF TO WORK

Ek web security tester ke nazariye se, kisi bhi endpoint ko CSRF ke liye test karne se pehle ye teen sharton ko check karna zaroori hai: From a web security tester's point of view, before testing any endpoint for CSRF, these three conditions need to be checked:

1. RELEVANT ACTIONRELEVANT ACTION — kya ye request kuch aisa STATE badalti hai jo attacker ke fayde ka ho (paisa transfer, email change, password change)? Agar request sirf DATA read karti hai (jaise GET /profile), CSRF ka koi practical impact nahi — attacker response padh hi nahi sakta, toh forge karne ka fayda hi nahi.does this request change some STATE that benefits the attacker (money transfer, email change, password change)? If the request only READS data (like GET /profile), CSRF has no practical impact — the attacker can't read the response anyway, so there's no point forging it.

2. COOKIE-BASED SESSION HANDLINGCOOKIE-BASED SESSION HANDLING — kya authentication SIRF cookie par depend karta hai? Agar app authentication ke liye ek custom header use karta hai (jaise Authorization: Bearer <token>) jise JavaScript explicitly set karti hai — aur wo cookie mein nahi hai — toh browser wo header automatically attach nahi karega, aur classic CSRF yahan kaam nahi karega.does authentication depend ONLY on a cookie? If the app uses a custom header for authentication instead (like Authorization: Bearer <token>) that JavaScript must explicitly set — and it isn't stored in a cookie — the browser won't auto-attach that header, and classic CSRF won't work here.

3. NO UNPREDICTABLE PARAMETERSNO UNPREDICTABLE PARAMETERS — kya request ke saare parameters attacker ko pehle se pata hain ya guess kiye ja sakte hain? Agar request mein koi aisi value chahiye jo attacker ko maloom nahi (jaise current password, ya ek session-bound CSRF token), toh attacker poori request bana hi nahi sakta — isi principle par aage ke saare defense based hain.are all the request's parameters already known to, or guessable by, the attacker? If the request requires some value the attacker doesn't know (like the current password, or a session-bound CSRF token), the attacker cannot construct the full request at all — every defense covered ahead is built on exactly this principle.

Kaise developers ne protections lagaye aur kaise attackers ne unhe bypass kiya (Step-by-Step) How developers implemented protections and how attackers bypassed them (Step-by-Step)

REFERER AUR ORIGIN HEADER MEIN FARAKTHE DIFFERENCE BETWEEN REFERER AND ORIGIN HEADERS

Origin header sirf scheme + host + port batata hai, path nahi. For example, agar request https://evil.com/transfer se aayi hai, to Origin header hoga Origin: https://evil.com. Ye khaas taur par cross-origin requests, jaise POST, PUT aur DELETE, mein use hota hai aur server isse check karke dekh sakta hai ki request trusted website se aayi hai ya nahi. The Origin header only tells the scheme + host + port, not the path. For example, if a request comes from https://evil.com/transfer, the Origin header will be Origin: https://evil.com. This is specially used in cross-origin requests, like POST, PUT and DELETE, and the server can check this to see if the request came from a trusted website.

Defense idea seedha hai: state-changing request aane par, in headers ko apne khud ke domain se compare karo: The defense idea is straightforward: on a state-changing request, compare these headers to your own domain:

if (request.headers.origin !== "https://sbi.com") {
  return reject("Cross-origin request blocked");
}
⚠️ PROBLEM — HEADER HAMESHA MAUJOOD NAHI HOTA⚠️ PROBLEM — THE HEADER ISN'T ALWAYS PRESENT

Privacy badhane ke liye aajkal bahut saare Ad-blockers aur VPNs in headers ko raaste mein hi mita (strip) dete hain. Ab server ko ye header milta hi nahi! Agar server strict banega aur bina header wali request ko block karega, toh aam (genuine) users bhi login nahi kar payenge. Is majboori ka fayda utha kar attacker jaanbujh kar in headers ko delete karwa dete hain aur check bypass kar lete hain. Aur haan, agar server code me galti ho (sirf "bank.com" word check kare), toh attacker www.bank.com.attacker.com naam ki website banakar bhi easily dhokha de dete the. To enhance privacy, many modern Ad-blockers and VPNs strip these headers in transit. Now the server doesn't receive the header at all! If the server becomes strict and blocks requests without headers, genuine users won't be able to log in. Attackers exploit this limitation by intentionally stripping the headers to bypass the check. Also, if there's a flaw in the server code (e.g., checking only for the word "bank.com"), attackers can easily deceive it by creating a website named www.bank.com.attacker.com.

SYNCHRONIZER TOKEN PATTERN KAISE KAAM KARTA HAIHOW THE SYNCHRONIZER TOKEN PATTERN WORKS

Server ek random, lambi, guess-na-ho-sakne-wali string generate karta hai, use us user ke session se JODTA hai (server-side store karta hai), aur har state-changing FORM mein ek hidden field ki tarah bhej deta hai: The server generates a random, long, unguessable string, TIES it to that user's session (stores it server-side), and sends it as a hidden field in every state-changing FORM:

<form action="/api/transfer-funds" method="POST">
  <input type="hidden" name="csrf_token" value="8f14e45fceea167a5a36...">
  <input type="text" name="amount">
</form>

Submit hone par, server submitted token ko us session ke liye stored token se compare karta hai — match na ho toh reject. Attacker ye value kahin se copy nahi kar sakta, kyunki uska apna JavaScript sbi.com ke real page ko cross-origin se READ hi nahi kar sakta (Same-Origin Policy) — isliye wo apne hidden form mein sahi token daal hi nahi sakta. On submit, the server compares the submitted token to the token stored for that session — if it doesn't match, it's rejected. The attacker can't copy this value from anywhere, because their own JavaScript cannot READ sbi.com's real page cross-origin (the Same-Origin Policy) — so they simply cannot put the correct token into their hidden form.

⚠️ IMPLEMENTATION PITFALLS — CONCEPT NAHI, LAAGU KARNE KI GALTIYAN⚠️ IMPLEMENTATION PITFALLS — NOT THE CONCEPT, BUT MISTAKES IN APPLYING IT

Session se bound nahiNot bound to the session — agar server sirf ye check karta hai ki token "ek valid-looking token hai" (jaise, koi bhi token jo database mein exist karta ho), attacker apne HI account se ek token le kar victim ki forged request mein daal sakta hai.if the server only checks that the token "is a valid-looking token" (e.g., any token that exists in the database), the attacker can grab a token from their OWN account and put it into the victim's forged request.

GET URL mein leakLeaking via a GET URL — agar token query parameter ke through bheja jaata hai (?csrf_token=...), wo browser history, server access-logs, aur third-party Referer header (agar page par koi external resource load hoti hai) mein leak ho sakta hai.if the token is sent as a query parameter (?csrf_token=...), it can leak into browser history, server access logs, and a third-party Referer header (if the page loads any external resource).

Inconsistent coverageInconsistent coverage — Ye idea isiliye nahi chal paaya kyunki ise server-side store karna padta tha aur har ek form ke liye CSRF check logic baar baar likhna padta tha jisme developer se mistake hone ke zyada chances the.This idea failed to scale well because tokens had to be stored server-side, and developers had to repeatedly write CSRF check logic for every single form, which significantly increased the chances of developer mistakes.

SAMESITE ATTRIBUTE KE TEEN VALUESTHE THREE VALUES OF THE SAMESITE ATTRIBUTE

Ye ek cookie attribute hai — server Set-Cookie header mein ye bataata hai ki browser is cookie ko CROSS-SITE requests ke saath bheje ya nahi: This is a cookie attribute — the server states in the Set-Cookie header whether the browser should send this cookie with CROSS-SITE requests or not:

Set-Cookie: session=abc123; SameSite=Lax; Secure; HttpOnly
Strict — Cookie sirf tab jaati hai jab request usi site ke andar se ho. Kisi bhi doosri site se aane wali request ke saath — chahe wo sirf ek link click karke bhi aayi ho — cookie bilkul nahi jaati. Example: Agar aap bank.com pe login hain aur kisi email mein diye gaye bank.com link pe click karte hain, to bhi cookie nahi jaayegi — aapko dubara login karna pad sakta hai.The cookie is only sent when the request originates from within the same site. It is never sent with requests coming from any other site — even if it's just clicking a link. Example: If you are logged into bank.com and click a bank.com link in an email, the cookie won't go — you might have to log in again.
Lax — Cookie tab nahi jaati jab koi doosri site background mein silently request bhejti hai (jaise image load, hidden form, ya fetch). Lekin agar aap khud kisi link pe click karke ya URL type karke us site pe jaate hain (top-level navigation) aur request simple GET ho, to cookie chali jaati hai. Saath hi, agar request usi site ke kisi subdomain se aa rahi hai (jaise app.example.com se api.example.com ko request), to use cross-site nahi maana jaata — cookie us case mein bhi chali jaati hai, chahe wo background request ho ya navigation. Ye browsers ka default hai. Example: login.example.com se api.example.com ko fetch request bhejne par cookie chali jaayegi, kyunki dono ek hi "site" (example.com) ke hisse hain — ye same-site request hai, cross-site nahi.The cookie is not sent when another site sends a request silently in the background (like an image load, hidden form, or fetch). But if you manually click a link or type a URL to go to that site (top-level navigation) and the request is a simple GET, the cookie is sent. Also, if the request comes from a subdomain of the same site (like a request from app.example.com to api.example.com), it's not considered cross-site — the cookie is sent in that case too, whether it's a background request or navigation. This is the browser default. Example: sending a fetch request from login.example.com to api.example.com will send the cookie, because both are part of the same "site" (example.com) — it's a same-site request, not cross-site.
None — Purana/original behavior — cookie har jagah jaati hai, chahe request kahin se bhi aayi ho (image, iframe, form, fetch — sab jagah). Isko safe banane ke liye Secure flag zaroori hai (yani cookie sirf HTTPS pe hi bheji jaaye). Example: Agar ye set ho, to attacker ki site se bhi silently forged request ke saath cookie chali jaayegi — CSRF ka poora risk wapas aa jaata hai.The old/original behavior — the cookie goes everywhere, regardless of where the request came from (image, iframe, form, fetch — everywhere). To make this safe, the Secure flag is required (meaning the cookie is only sent over HTTPS). Example: If this is set, the cookie will be sent even with a silently forged request from the attacker's site — the full risk of CSRF comes back.

Browsers ne Lax ko default isliye banaya kyunki Strict normal cross-site linking ko tod deta — jaise Google search result se click karke kisi logged-in site par jaana, ya ek external link se apni site par aana, in dono mein user ko LOGGED-OUT dikhna galat UX hota. Browsers made Lax the default because Strict would break normal cross-site linking — like clicking through from a Google search result to a site you're logged into, or arriving at your site from an external link; in both cases, showing the user as LOGGED-OUT would be broken UX.

⚠️ Lax mein bache hue Problems:⚠️ Problems remaining in Lax:

Problem 1 — GET wali top-level navigation
Attacker ek hidden form ya auto-redirect link banata hai jo user ko seedha sbi.com pe GET request ke saath le jaata hai. Ye ek normal navigation lagti hai (jaise link click karna), isliye Lax ise allow kar deta hai aur cookie chali jaati hai. Problem tab hoti hai jab koi state-changing action (jaise fund transfer, password change) galti se GET method accept kar le — aisi situation mein attacker isi navigation trick se attack kar sakta hai.
Simple line: Agar sensitive action GET se ho sakta hai, to Lax use CSRF se nahi bacha payega. Problem 1 — Top-level GET navigation
The attacker creates a hidden form or auto-redirect link that takes the user straight to sbi.com with a GET request. This looks like a normal navigation (like clicking a link), so Lax allows it and the cookie goes through. The problem occurs when a state-changing action (like fund transfer, password change) mistakenly accepts the GET method — in such a situation, the attacker can use this exact navigation trick to attack.
Simple line: If a sensitive action can be done via GET, Lax won't be able to protect it from CSRF.

Problem 2 — Compromised subdomain
SameSite "site" ko domain ke base part se define karta hai — matlab a.sbi.com aur b.sbi.com dono ek hi "site" maane jaate hain. Agar attacker kisi ek subdomain (a.sbi.com) ko hack/compromise kar le, to wahan se bheji gayi request bhi "same-site" hi treat hogi — aur SameSite=Lax use block nahi karega.
Simple line: Ek weak/compromised subdomain pura SameSite protection bypass kar sakta hai. Problem 2 — Compromised subdomain
SameSite defines "site" based on the base part of the domain — meaning a.sbi.com and b.sbi.com are both considered the same "site". If an attacker hacks/compromises one subdomain (a.sbi.com), a request sent from there will also be treated as "same-site" — and SameSite=Lax will not block it.
Simple line: A weak/compromised subdomain can bypass the entire SameSite protection.

LAYER 1 — SAMESITE=STRICTLAYER 1 — SAMESITE=STRICT

Defence 3 ka top-level-GET-navigation problem band karne ke liye, sensitive/state-changing actions ke session cookie par Strict use karo — ab cookie kisi bhi cross-site request (top-level navigation samet) ke saath bilkul nahi jaayegi. To close Defence 3's top-level-GET-navigation gap, use Strict on the session cookie for sensitive/state-changing actions — now the cookie won't go out with any cross-site request at all, including top-level navigation.

LAYER 2 — DOUBLE-SUBMIT COOKIE PATTERNLAYER 2 — DOUBLE-SUBMIT COOKIE PATTERN

Server ek random token do jagah bhejta hai: pehla cookie ki tarah, jise browser automatically har request ke saath attach kar deta hai, aur doosra response body ya meta-tag mein, jise page ki JavaScript padh kar explicitly request ke form field ya header mein attach karti hai. Server request accept tabhi karta hai jab dono values match karein. Ye secure kyun hai — SOP ki wajah se: Attacker apni site (evil.com) se forged request to bhej sakta hai, aur cookie bhi browser automatically attach kar dega (kyunki cookies domain-based hain, request kahin se bhi trigger ho). Lekin attacker ko doosri value (jo JS explicitly attach karti hai) khud set karni padegi apne forged request mein — aur uske liye usse pehle asal cookie ki value pata honi chahiye. Yahi par Same-Origin Policy (SOP) kaam karti hai: SOP browser ka rule hai ki ek origin ki JavaScript sirf usi origin ka data read kar sakti hai. Isliye evil.com ki JavaScript sbi.com ki cookie ko read nahi kar sakti — chahe cookie automatically request ke saath chali bhi jaaye, uski value attacker ki JS ke liye invisible rehti hai. Result: Attacker cookie to bhijwa sakta hai (uska control nahi), par matching doosri value bhejne ke liye jo asal cookie value chahiye, wo SOP ki wajah se kabhi mil hi nahi sakti — isliye server ka match-check fail ho jaata hai aur forged request reject ho jaati hai. The server sends a random token in two places: first as a cookie, which the browser automatically attaches to every request, and second in the response body or a meta-tag, which the page's JavaScript reads and explicitly attaches to the request's form field or header. The server only accepts the request when both values match. Why this is secure — because of SOP: The attacker can send a forged request from their site (evil.com), and the browser will automatically attach the cookie (because cookies are domain-based, regardless of where the request is triggered). But the attacker has to manually set the second value (which JS explicitly attaches) in their forged request — and for that, they first need to know the actual cookie's value. This is where the Same-Origin Policy (SOP) comes into play: SOP is a browser rule stating that JavaScript from one origin can only read data from that same origin. Therefore, evil.com's JavaScript cannot read sbi.com's cookie — even if the cookie goes with the request automatically, its value remains invisible to the attacker's JS. Result: The attacker can send the cookie (they don't control that), but to send the matching second value, they need the actual cookie value, which they can never get due to SOP — so the server's match-check fails and the forged request is rejected.

LAYER 3 — CUSTOM HEADER REQUIREMENTLAYER 3 — CUSTOM HEADER REQUIREMENT

Server ye bhi require karta hai ki request mein ek custom header ho (jaise X-Csrf-Token). Ek plain HTML <form> KABHI custom header set nahi kar sakta — sirf JavaScript ka fetch/XHR ye kar sakta hai. Aur jab attacker ka cross-origin JS custom header ke saath fetch karne ki koshish karta hai, browser pehle ek CORS preflight (OPTIONS) request bhejta hai: The server also requires the request to carry a custom header (like X-Csrf-Token). A plain HTML <form> can NEVER set a custom header — only JavaScript's fetch/XHR can. And when the attacker's cross-origin JS tries to fetch with a custom header, the browser first sends a CORS preflight (OPTIONS) request:

OPTIONS /api/transfer-funds HTTP/1.1
Origin: https://freegift.com
Access-Control-Request-Headers: x-csrf-token

-- sbi.com ka server jawab deta hai ---- sbi.com's server responds --
HTTP/1.1 403 Forbidden
(freegift.com is server ki allowed-origins list mein nahi hai)(freegift.com is not in the server's allowed-origins list)

Ek legitimate server ke paas attacker ke random domain ko allow karne ki koi wajah hi nahi hoti, isliye preflight fail hota hai aur actual request kabhi bheji hi nahi jaati. A legitimate server has no reason to allow the attacker's random domain, so the preflight fails and the actual request never even gets sent.

✅ HAR PICHLE PROBLEM KO YE KAISE SOLVE KARTA HAI✅ HOW THIS CLOSES EVERY PREVIOUS PROBLEM

Hidden Form (POST ya GET) — Strict ne cookie hi rok di, aur form custom header set nahi kar sakta. Background Fetch — same-origin nahi hai, cookie phir se rukti hai, aur custom header preflight par hi reject ho jaata hai. Hidden Form (POST or GET) — Strict blocks the cookie outright, and the form can't set the custom header anyway. Background Fetch — not same-origin, the cookie is blocked again, and the custom header gets rejected right at the preflight.

Ab tak jitne bhi defense discuss kiye — Referer/Origin check, CSRF Token, SameSite, Double-Submit — sabki EK common assumption hai: attacker ka code ek ALAG origin (evil site) se chal raha hai. Ye assumption tab TOOT jaati hai jab sbi.com khud kahin XSS-vulnerable ho. Every defense discussed so far — Referer/Origin check, CSRF Token, SameSite, Double-Submit — shares ONE common assumption: the attacker's code is running from a DIFFERENT origin (an evil site). That assumption BREAKS the moment sbi.com itself has an XSS vulnerability somewhere.

CSRF attacks isliye safal hote hain kyunki browsers har cross-site request ke sath user ki saved cookies ko automatically attach kar dete hain (Ambient Authority). Simple Referer/Origin headers par rely karna fragile hai — proxies unhe strip karte hain aur top-level GET navigations pe Origin header aata hi nahi. Production-grade defense ke liye neeche 4 layered controls zaroori hain: CSRF attacks succeed because browsers automatically attach session cookies to every cross-site request (ambient authority). Relying on Referer/Origin headers alone is fragile — proxies strip them and top-level GET navigations omit Origin entirely. Modern production-grade defense requires 4 layered controls:

1
🔑 Anti-CSRF Synchronizer Token Pattern Anti-CSRF Synchronizer Token Pattern
Har authenticated user session ke liye ek cryptographically secure, unpredictable random token generate karo. Ise HTML forms mein hidden field (_csrf) ya AJAX/Fetch requests mein custom header (X-CSRF-Token) ke through bhejo. Server har state-changing POST / PUT / DELETE / PATCH request par is token ko validate kare — bina valid token ke request reject ho. Generate a cryptographically unpredictable, session-bound random token for every authenticated user. Embed it in HTML forms as a hidden field (_csrf) or dispatch it via a custom request header (X-CSRF-Token) for AJAX/Fetch calls. The server must strictly validate this token on every state-changing POST / PUT / DELETE / PATCH — requests without a valid token are rejected outright.
2
🍪 SameSite Cookie Attribute Enforcement SameSite Cookie Attribute Enforcement
Authentication cookies par SameSite=Lax ya SameSite=Strict ke saath Secure aur HttpOnly flags lagao. Isse cross-site requests par browser level par hi ambient session cookies attach nahi hongi — request server tak pahunchne se pehle hi browser block kar deta hai. Strict mode zyada secure hai lekin cross-origin navigations ko bhi block karta hai. Flag authentication cookies with SameSite=Lax or SameSite=Strict alongside Secure and HttpOnly. This ensures ambient session cookies are never attached to cross-site subrequests at the browser level — the browser itself blocks them before the request reaches your server. Strict is stronger but also blocks cross-origin top-level navigations.
3
🔄 Double-Submit Cookie Pattern (Stateless APIs) Double-Submit Cookie Pattern (Stateless APIs)
Stateless architectures ke liye: server ek cryptographically signed token ko cookie aur request header dono mein bhejta hai. Cross-site attacker cookie automatically bhijwa to sakta hai (browser karta hai), lekin header mein match karne wali value Same-Origin Policy (SOP) ki wajah se read ya set nahi kar sakta — isliye server ka match-check fail ho jaata hai aur forged request reject hoti hai. For stateless or decoupled API architectures: send a cryptographically signed token in both a cookie and a request header. A cross-site attacker can force the browser to send the cookie, but Same-Origin Policy (SOP) prevents them from reading or setting the matching header value — so the server's comparison fails and the forged request is rejected.
4
🔒 Re-Authentication / Step-Up Auth Re-Authentication / Step-Up Auth
High-risk actions — jaise password change, funds transfer, email update, 2FA disable — ke liye re-authentication ya secondary OTP mandatory karo. Isse CSRF bypass hone par bhi asal user ki explicit consent ke bina action complete nahi ho sakta. Ye last-resort safety net hai jo baaki teeno defenses ke bypass hone par bhi protect karta hai. For high-risk actions — password changes, fund transfers, email updates, 2FA disable — mandate re-authentication or a secondary out-of-band OTP. Even if all other CSRF defenses are bypassed, the attacker cannot complete the action without the real user's explicit re-confirmation. This is the last-resort safety net of defence-in-depth.

// 2. Synchronizer Token Generator & Validation Middleware
function generateCsrfToken(req) {
    if (!req.session.csrfSecret) {
        req.session.csrfSecret = crypto.randomBytes(32).toString('hex');
    }
    // Create an HMAC token tied to the user's secret
    return crypto.createHmac('sha256', req.session.csrfSecret)
                 .update('csrf-token-binding')
                 .digest('hex');
}

function csrfProtection(req, res, next) {
    // Exclude safe idempotent HTTP methods per RFC 7231
    const safeMethods = ['GET', 'HEAD', 'OPTIONS'];
    if (safeMethods.includes(req.method)) {
        return next();
    }

    // Extract CSRF token from multiple possible inputs (Header, Body, Query)
    const clientToken = req.headers['x-csrf-token'] || 
                        req.headers['x-xsrf-token'] || 
                        (req.body && req.body._csrf);

    if (!req.session || !req.session.csrfSecret) {
        return res.status(403).json({ error: 'CSRF token missing or session expired' });
    }

    const expectedToken = generateCsrfToken(req);

    // Cryptographic constant-time comparison prevents timing attacks
    if (!clientToken || !crypto.timingSafeEqual(Buffer.from(clientToken), Buffer.from(expectedToken))) {
        return res.status(403).json({ error: 'CSRF validation failed: Invalid token' });
    }

    next();
}

// 3. API Custom Header Guard (Enforces CORS preflight on cross-origin requests)
function requireCustomHeader(req, res, next) {
    const customHeader = req.headers['x-requested-with'];
    if (customHeader !== 'XMLHttpRequest') {
        return res.status(400).json({ error: 'Missing required security header: X-Requested-With' });
    }
    next();
}

    const token = generateCsrfToken(req);
    res.json({ csrfToken: token });
});

    return res.json({ status: 'Transfer verified and executed securely', toAccount, amount });

📖 Zaroori Terms (Glossary)Important Terms (Glossary)

1. CSRF (Cross-Site Request Forgery)1. CSRF (Cross-Site Request Forgery)

Ek web attack jahan attacker victim ke already-logged-in browser ko use karke, uski cookie ke sahaare, uski taraf se ek state-changing request forge (nakli bana request) kar deta hai — bina victim ke password ya session ke kabhi churaaye. A web attack where the attacker uses the victim's already-logged-in browser, riding on their cookie, to forge a state-changing request on their behalf — without ever stealing the victim's password or session.

2. State-Changing Request2. State-Changing Request

Koi bhi request jo server par data MODIFY karti hai (paisa transfer, password change, settings update) — na ki sirf padhती hai. HTTP spec ke hisaab se GET jaise "safe" methods ko sirf DATA padhne ke liye use hona chahiye, state change ke liye nahi. Any request that MODIFIES data on the server (money transfer, password change, settings update) — as opposed to just reading it. Per the HTTP spec, "safe" methods like GET are meant only for reading data, never for changing state.

3. SameSite Cookie Attribute3. SameSite Cookie Attribute

Ek cookie setting (Strict/Lax/None) jo browser ko batati hai ki cross-site requests ke saath ye cookie bheji jaaye ya nahi. Ye application code mein nahi, browser ke andar hi enforce hoti hai. A cookie setting (Strict/Lax/None) that tells the browser whether this cookie should be sent with cross-site requests. It's enforced inside the browser itself, not in application code.

4. CSRF Token (Synchronizer Token)4. CSRF Token (Synchronizer Token)

Ek random, session-bound, unpredictable value jo server har state-changing form mein bhejta aur submit hone par validate karta hai. Attacker Same-Origin Policy (SOP) ki wajah se ise cross-origin se padh nahi sakta. A random, session-bound, unpredictable value that the server sends in every state-changing form and validates on submission. The attacker cannot read it cross-origin, thanks to the Same-Origin Policy (SOP).

5. Double-Submit Cookie Pattern5. Double-Submit Cookie Pattern

Ek defense jisme ek hi random token DO jagah bheja jaata hai (cookie + custom header/body). Request tabhi valid maani jaati hai jab dono values match karein — attacker cross-origin se na cookie padh sakta hai, na custom header reliably set kar sakta hai. A defense where the same random token is sent in TWO places (a cookie + a custom header/body field). The request is only valid when both values match — the attacker can neither read the cookie cross-origin, nor reliably set the custom header.

6. SOP (Same-Origin Policy)6. SOP (Same-Origin Policy)

Ye ek browser security feature hai jo ek origin ki script ko kisi dusre origin ke web page ke data ko padhne (read) se rokti hai. Yehi policy attacker ko cross-origin request bhejte waqt CSRF token read karne se rokti hai. This is a browser security feature that restricts a script on one origin from reading data on a web page belonging to another origin. This policy is what prevents an attacker from reading the CSRF token during a cross-origin request.

7. Top-Level Navigation & Background Requests7. Top-Level Navigation & Background Requests

Top-Level Navigation: Browser ka pura page jab kisi naye URL pe shift hota hai — chahe link click se, URL bar se, ya redirect se — usse top-level navigation kehte hain. Jab ye shift GET request ke through ho, to wo top-level GET navigation kehlata hai.
➡️ Ye cross-site request hai, lekin SameSite=Lax cookie top-level GET navigation ke saath ja sakti hai.

Background Requests: Iframe ke andar navigation ya JS se background me fetch hona — ye top-level navigation nahi maana jata isliye cookie nhi jaati...
Iframe navigation: Sirf iframe ke andar ka content badalta hai. Example: news.com pe embedded YouTube iframe.
Background fetch: JS se data mangwaya jata hai bina page reload ke. Example: Twitter ka infinite scroll.
Dono cases me poora page/URL badal nahi raha, isliye SameSite=Lax cookie inme cross-site request pe nahi bhejta. Top-Level Navigation: When the browser's entire page shifts to a new URL — whether via a link click, the URL bar, or a redirect — it is called top-level navigation. When this shift happens through a GET request, it is called top-level GET navigation.
➡️ This is a cross-site request, but a SameSite=Lax cookie can be sent along with a top-level GET navigation.

Background Requests: Navigation inside an iframe or fetching data in the background via JS — this is not considered top-level navigation, so the cookie does not go with the request...
Iframe navigation: Only the content inside the iframe changes. Example: Switching a video inside an embedded YouTube iframe.
Background fetch: Data is fetched via JS without reloading the page. Example: Twitter's infinite scroll.
In both cases, the entire page/URL is not changing, hence SameSite=Lax does not send cookies for these cross-site requests.

Sending a request → Is allowed. The attacker can fire a request to bank.com.
Reading a response → Is not allowed. The attacker simply cannot see the response of that request (which contains the token) in their JS code.

The HTTP spec treats GET as "safe" (read-only only) — apps should never break that convention.
Double-submit CSRF token akela perfect nahi hai — kuch specific weaknesses hain jinhe Origin/Referer header check karke cover kiya jata hai:

1. Subdomain-level attack: Agar attacker kisi same-site subdomain se cookie set kar de, to wo CSRF token cookie ko overwrite kar sakta hai. Origin/Referer header is scenario me extra check dete hain.
2. Defense-in-depth: Double-submit token ek single mechanism hai — agar kisi implementation bug se token compromise ho jaye, to Origin/Referer header ek doosri independent layer bana deta hai. The Double-submit CSRF token alone is not perfect — there are specific weaknesses that are covered by checking Origin/Referer headers:

1. Subdomain-level attack: If an attacker sets a cookie from a same-site subdomain, they can overwrite the CSRF token cookie. The Origin/Referer headers provide an extra check in this scenario.
2. Defense-in-depth: A double-submit token is a single mechanism — if the token is compromised due to an implementation bug, the Origin/Referer header creates a second independent layer.
Referer ek full/partial URL hota hai jo privacy policy, browser settings, ya attacker ki apni marzi se suppress ho sakta hai. Origin specifically CSRF-jaise defense ke liye design kiya gaya — sirf domain bhejta hai (isliye kam privacy-leaky), aur state-changing requests par zyada reliably present hota hai.Referer is a full URL that can be suppressed by privacy policy, browser settings, or the attacker's own choice. Origin was specifically designed for CSRF-style defense — it only sends the domain (so less privacy-leaky), and is more reliably present on state-changing requests.
Haan, poore site ke liye — CSRF defense un requests ko abhi bhi rokta hai jo GENUINELY cross-origin hain (kisi malicious website se). Sirf us EK vulnerable page ke against ye defense kaam nahi karta, kyunki wahan attacker ka code already same-origin chal raha hota hai. Yani XSS ko FIX karna zaroori hai, CSRF defense hatana nahi.Yes, for the site as a whole — CSRF defenses still stop requests that are GENUINELY cross-origin (from any malicious website). The defense simply doesn't apply against that ONE vulnerable page, because the attacker's code is already running same-origin there. The takeaway is to FIX the XSS, not to remove the CSRF defense.
Session hijacking mein attacker VICTIM ka session cookie churata hai aur victim BAN kar login karta hai. Login CSRF mein ulta hota hai — attacker VICTIM ko apne (attacker ke) account mein login karwa deta hai. Victim ko lagta hai wo khud hi hai, aur wo jo bhi save karti hai, wo attacker ke account mein jaata hai — koi cookie kabhi churaayi hi nahi jaati.In session hijacking, the attacker steals the VICTIM's session cookie and logs in AS the victim. In Login CSRF, it's the reverse — the attacker forces the VICTIM to log into the attacker's own account. The victim believes they're still themselves, and anything they save goes into the attacker's account — no cookie is ever stolen.
Sirf tab, jab server STRICTLY application/json require karta hai aur kuch aur reject kar deta hai. Ek plain HTML <form> ye Content-Type bina JavaScript ke set hi nahi kar sakta — isliye ye ek incidental protection banti hai. Lekin agar server LENIENT hai (kisi bhi Content-Type ko parse kar leta hai), ye protection turant khatam ho jaati hai.Only when the server STRICTLY requires application/json and rejects anything else. A plain HTML <form> cannot set that Content-Type without JavaScript — so this becomes an incidental protection. But if the server is LENIENT (parses the body regardless of Content-Type), this protection disappears immediately.
