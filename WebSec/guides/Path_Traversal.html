Vulnerability tab banti hai jab attacker special sequences (jaise ../) use karke server ki file-system hierarchy mein upar ki taraf navigate kar leta hai, aur application ke intended folder se bahar ki sensitive files tak pahunch jaata hai. occurs when an application uses a user-supplied filename/path directly in a file-system operation, without checking whether that path stays inside the INTENDED directory. The vulnerability arises when an attacker uses special sequences (like ../) to navigate upward through the server's file-system hierarchy, reaching sensitive files outside the application's intended folder.

Before diving into the mechanism, it's important to understand: if this bug is found on a real website, what can the attacker ACTUALLY do? Below are concrete scenarios that have repeatedly been seen in real incidents.

🗂️ 1. Sensitive Configuration Files Padhna1. Reading Sensitive Configuration Files

Attacker ../../.env ya ../../config.php jaisa path traverse karke seedha DATABASE PASSWORD, API keys, aur application source code padh sakta hai — inse aage ek poora data breach ya server takeover ho sakta hai. By traversing a path like ../../.env or ../../config.php, an attacker can directly read the DATABASE PASSWORD, API keys, and application source code — leading to a full data breach or server takeover.

🔑 2. System Credentials Aur SSH Keys Chori2. Stealing System Credentials And SSH Keys

Linux servers par /etc/passwd, aur agar permissions weak hon /etc/shadow (password hashes), ya kisi user ki ~/.ssh/id_rsa (private SSH key) padh kar attacker doosre servers/systems tak lateral movement kar sakta hai. On Linux servers, reading /etc/passwd, and if permissions are weak, /etc/shadow (password hashes), or a user's ~/.ssh/id_rsa (private SSH key), lets an attacker move laterally to other servers/systems.

📄 3. Application Source Code Disclosure3. Application Source Code Disclosure

Attacker application ki apni source code files padh sakta hai — isse na sirf intellectual property leak hoti hai, balki attacker ko code padh kar aur bhi vulnerabilities (jaise hardcoded secrets, dusre bugs) dhundhne mein madad milti hai, jo aage aur bade attacks ka rasta khol deti hai. An attacker can read the application's own source code files — this doesn't just leak intellectual property, it also helps the attacker find even more vulnerabilities (like hardcoded secrets or other bugs) by reading the code, opening the door to further, bigger attacks.

⚙️ 4. Path Traversal Ko RCE Mein Escalate Karna (Log Poisoning)4. Escalating Path Traversal Into RCE (Log Poisoning)

Agar application kisi log file (jaise web server access log) ko "include" karne ke liye bhi path traversal ka use karti hai, attacker pehle apna User-Agent header ek malicious script (jaise PHP code) se set karta hai — server wo string apne log file mein likh deta hai. Fir attacker path traversal se usi log file ko "include" karwa deta hai, jisse uska injected code server par EXECUTE ho jaata hai — ye "Log Poisoning to RCE" chain hai. If an application also uses path traversal-style "include" functionality to load a log file (like the web server's access log), the attacker first sets their User-Agent header to a malicious script (like PHP code) — the server writes that string into its log file. Then the attacker uses path traversal to get that same log file "included", which EXECUTES their injected code on the server — this is the "Log Poisoning to RCE" chain.

💻 5. Arbitrary File Write (Agar Write Bhi Possible Ho)5. Arbitrary File Write (If Write Is Also Possible)

Agar vulnerable feature sirf READ nahi, WRITE bhi karti hai (jaise file upload ka save path), attacker path manipulation se apni file ko web-accessible directory ke andar ek executable extension (jaise .php) ke saath save karwa sakta hai — ek webshell upload karke seedha Remote Code Execution tak pahunch sakta hai. If the vulnerable feature does WRITE too, not just READ (like a file upload's save path), an attacker can manipulate the path to save their file inside a web-accessible directory with an executable extension (like .php) — uploading a webshell and reaching Remote Code Execution directly.

Ye dikhata hai ki Path Traversal sirf custom application code tak limited nahi hai — well-established, widely-used software mein bhi ho sakti hai. In 2021, a specific version of Apache HTTP Server had a well-documented, publicly-known Path Traversal vulnerability (assigned CVE-2021-41773) — allowing an attacker to read arbitrary files on unpatched servers via path traversal, and in some configurations, escalate directly to Remote Code Execution. This shows Path Traversal isn't limited to custom application code — it can exist even in well-established, widely-used software.

APPS FILENAME KO USER SE KYU LETE HAIN WHY APPS TAKE A FILENAME FROM THE USER

Bahut saari legitimate features ek SPECIFIC file ko user ke bataye hue naam se serve karti hain — jaise ek "download report" feature, ek avatar/theme loader, ya ek log-viewer. Developer user ke diye hue filename ko apni INTENDED base directory ke saath jod deta hai, taaki disk se exact file mil jaaye. Many legitimate features serve a SPECIFIC file by a name the user provides — like a "download report" feature, an avatar/theme loader, or a log-viewer. The developer joins the user-supplied filename with their INTENDED base directory, so the exact file is fetched from disk.

TECHNICAL EXAMPLE TECHNICAL EXAMPLE

Ek chhota real code snippet socho — ek "download" feature jo user-supplied filename se file serve karta hai: Consider a small real code snippet — a "download" feature that serves a file by a user-supplied filename: 

@app.route('/download')
def download_file():
    filename = request.args.get('file')
    return open('/var/www/uploads/' + filename).read()

Normal use case mein file=report.pdf ke saath final path banta hai: /var/www/uploads/report.pdf — bilkul theek. Developer ne yahan ek assumption bana li: "user hamesha ek simple filename hi dega, koi navigation instruction nahi". In the normal case, with file=report.pdf, the final path becomes: /var/www/uploads/report.pdf — perfectly fine. The developer made one assumption here: "the user will always give a simple filename, never a navigation instruction".

💡 SIMPLE WORDS MEIN 💡 IN SIMPLE WORDS

Har operating system ki file-system mein .. ek SPECIAL, universally-understood instruction hai jiska matlab hai "current folder se ek level UPAR jao" — ye koi application-specific cheez nahi hai, ye khud OS file-system ka hi built-in rule hai. Jab open() function ko ek path milta hai, wo poori string ko sirf ek "address" ki tarah follow karta hai — usse koi farq nahi padta ki us address ka ../ wala hissa "developer ne likha" ya "user ne diya" — bilkul waise hi jaise shell ek ; ko sirf ek instruction-separator ki tarah samajhta hai, chahe wo kahin se bhi aaya ho. In every operating system's file-system, .. is a SPECIAL, universally-understood instruction meaning "go one level UP from the current folder" — this isn't something application-specific, it's a built-in rule of the OS file-system itself. When the open() function receives a path, it just follows the whole string as one "address" — it doesn't care whether the ../ part of that address was "written by the developer" or "supplied by the user" — exactly the way a shell treats a ; as just an instruction-separator, no matter where it came from.

⚠️ PROBLEM KI JADD ⚠️ THE ROOT OF THE PROBLEM

File-system ko sirf EK STRING (poora path) milta hai — usse pata nahi hota ki us string ka kaunsa part "intended base directory" hai aur kaunsa "user-supplied, potentially malicious relative path". ../ jaisi sequences ki hi wajah se file-system decide karta hai kahan navigate karna hai — isi trust boundary ki galti se Path Traversal possible hoti hai. The file-system only receives ONE STRING (the whole path) — it has no way to know which part of that string is the "intended base directory" and which part is "user-supplied, potentially malicious relative path". The file-system decides where to navigate purely based on sequences like ../ — it is exactly this broken trust boundary that makes Path Traversal possible.

SABSE BASIC MISTAKE THE MOST BASIC MISTAKE

Level 0 ka code exactly yehi karta hai — koi validation hi nahi. Attacker file parameter mein ek normal filename ke bajaye ye value deta hai: Level 0's code does exactly this — no validation at all. Instead of a normal filename, the attacker supplies this value in the file parameter: 

GET /download?file=../../../../etc/passwd
⚠️ GAP ⚠️ GAP

Final path banta hai: /var/www/uploads/../../../../etc/passwd. OS file-system har ../ ko "ek level upar jao" ki tarah resolve karta hai — 4 baar upar jaane par path root / tak (ya usse aage) pahunch jaata hai, aur fir etc/passwd add hone se final resolved path ban jaata hai /etc/passwd — application ke intended uploads folder se BILKUL bahar. The final path becomes: /var/www/uploads/../../../../etc/passwd. The OS file-system resolves each ../ as "go one level up" — going up 4 times reaches the root / (or beyond), and then adding etc/passwd gives the final resolved path /etc/passwd — COMPLETELY outside the application's intended uploads folder.

Server ye file padh kar seedha attacker ko response mein wapas bhej deta hai — user list, application config, ya kisi bhi readable file ke against yehi pattern kaam karta hai. Extra ../ daalna harmless hai (root se aage jaane ki koshish bas root par hi ruk jaati hai), isliye attacker aksar zyada ../ daal deta hai taaki depth ka guess sahi ho jaaye. The server reads this file and sends it straight back to the attacker in the response — this same pattern works against the user list, application config, or any readable file. Adding extra ../ is harmless (trying to go past root just stops at root), so attackers often add more ../ to make sure the depth guess is correct.

BLACKLIST KA REACTIVE FIX THE REACTIVE BLACKLIST FIX

Level 1 ka incident dekh kar developer ek check add karta hai jo literal ../ substring ko reject kare: Seeing the Level 1 incident, the developer adds a check that rejects the literal ../ substring: 

if "../" in filename:
    reject_request()

Ab ../../../../etc/passwd jaisa literal payload reject ho jaata hai — developer confident feel karta hai. Now a literal payload like ../../../../etc/passwd gets rejected — the developer feels confident.

⚠️ GAP — DECODE HONE SE PEHLE HI CHECK HO RAHA HAI ⚠️ GAP — THE CHECK RUNS BEFORE DECODING HAPPENS

Attacker ab slash character ko URL-encode kar deta hai: ..%2f..%2f..%2f..%2fetc%2fpasswd. Is RAW string mein literal ../ substring maujood hi nahi hai (kyunki / ki jagah %2f hai), isliye blacklist check PASS ho jaata hai. Lekin web framework standard practice ke tehat request parameters ko AUTOMATICALLY URL-decode karta hai — aur ye decoding check ke BAAD, file-open call se THODA PEHLE hoti hai. Decode hote hi %2f wapas / ban jaata hai, aur poora ../../../../etc/passwd traversal restore ho jaata hai. The attacker now URL-encodes the slash character: ..%2f..%2f..%2f..%2fetc%2fpasswd. This RAW string doesn't contain the literal ../ substring at all (since / is replaced with %2f), so the blacklist check PASSES. But as standard practice, the web framework AUTOMATICALLY URL-decodes request parameters — and this decoding happens AFTER the check, just BEFORE the file-open call. As soon as it's decoded, %2f becomes / again, and the full ../../../../etc/passwd traversal is restored.

Ye ek classic order-of-operations flaw hai — validation aur actual use do ALAG moments par ho rahe hain, aur beech mein automatic decoding cheezein badal deti hai. Isi tarah ka gap hum SQLi aur SSRF mein bhi dekh chuke hain, jahan koi bhi check jo "raw, as-received" input par hoti hai lekin baad mein koi TRANSFORMATION hoti hai, bypass ho sakti hai. This is a classic order-of-operations flaw — validation and actual use happen at two DIFFERENT moments, and automatic decoding in between changes things. We've seen a similar gap in SQLi and SSRF too, where any check that runs on "raw, as-received" input, but a TRANSFORMATION happens afterward, can be bypassed.

DECODE-THEN-CHECK FIX KARNE KE BAAD AFTER FIXING DECODE-THEN-CHECK

Developer ab pehle decode karta hai, fir ../ check karta hai, AUR ek extra layer bhi add karta hai: filename ko sirf ek expected extension (jaise .jpg, .pdf) ke saath end hone par hi allow karta hai — sochte hue ki isse sirf images/documents hi serve ho sakti hain, koi system file nahi. The developer now decodes first, then checks for ../, AND adds an extra layer too: only allowing filenames that end with an expected extension (like .jpg, .pdf) — thinking this ensures only images/documents can be served, never a system file. 

if not decoded_filename.endswith((".jpg", ".pdf")):
    reject_request()
⚠️ GAP — NULL BYTE INJECTION ⚠️ GAP — NULL BYTE INJECTION

Attacker payload bhejta hai: ../../../../etc/passwd%00.jpg. Decode hone ke baad ye ban jaata hai ../../../../etc/passwd + ek NULL BYTE character (\0) + .jpg. Application ka extension CHECK poori string dekh kar pass ho jaata hai (kyunki wo ".jpg" par khatam hoti hai) — lekin kuch purane, C-language-based file-open functions (jaise purane PHP versions mein) null byte ko "STRING KA END" samajh kar us point ke aage sab kuch IGNORE kar dete hain. Actual OS-level file-open call ko sirf ../../../../etc/passwd hi milta hai — .jpg wala hissa kabhi file-system tak pahunchta hi nahi. The attacker sends the payload: ../../../../etc/passwd%00.jpg. Once decoded, this becomes ../../../../etc/passwd + a NULL BYTE character (\0) + .jpg. The application's extension CHECK passes when looking at the full string (since it ends in ".jpg") — but some older, C-language-based file-open functions (like in older PHP versions) treat the null byte as "END OF STRING" and IGNORE everything after that point. The actual OS-level file-open call only receives ../../../../etc/passwd — the .jpg part never reaches the file-system at all.

GAP ye hai ki VALIDATION (extension check) aur ACTUAL FILE-OPEN OPERATION do ALAG components dwara, do ALAG rules ke saath, string ko interpret kar rahe the — application ne dekha ".jpg", lekin OS ne dekha "string yahan khatam ho gayi". Ye exact wahi pattern hai jo hum SSRF ke redirect-bypass mein dekh chuke hain: jo cheez VALIDATE hui, wahi cheez ACTUAL OPERATION mein use nahi ho rahi. The GAP is that VALIDATION (the extension check) and the ACTUAL FILE-OPEN OPERATION were interpreting the string via two DIFFERENT components, following two DIFFERENT rules — the application saw ".jpg", but the OS saw "the string ends here". This is the exact same pattern we've seen in SSRF's redirect-bypass: what got VALIDATED isn't the same thing used in the ACTUAL OPERATION.

LAYER 1 — CANONICALIZE, FIR PREFIX CHECK KARO LAYER 1 — CANONICALIZE, THEN CHECK THE PREFIX

Sabse important step: filename ko base directory ke saath jodne ke BAAD, us poore path ko OS se REAL, FULLY-RESOLVED ABSOLUTE PATH banwa lo (jisme saare ../ already resolve ho chuke hon, aur symlinks bhi follow ho chuke hon) — fir check karo ki ye RESOLVED path, INTENDED base directory ke RESOLVED path se hi shuru hota hai: The most important step: after joining the filename with the base directory, get the OS to produce the REAL, FULLY-RESOLVED ABSOLUTE PATH (with all ../ already resolved, and symlinks already followed) — then check that this RESOLVED path actually starts with the RESOLVED path of the INTENDED base directory: 

import os
base_dir = os.path.realpath("/var/www/uploads")
requested = os.path.realpath(os.path.join(base_dir, filename))

if not requested.startswith(base_dir + os.sep):
    reject_request()

os.path.realpath() null bytes, symlinks, aur ../ sequences — sabko already-resolved, canonical form mein convert kar deta hai, isliye check karne ka waqt tak koi "surprise" transformation baaki nahi bachti. Chahe input ../../etc/passwd ho ya ..%2f..%2fetc/passwd ho ya etc/passwd%00.jpg ho — decode/resolve hone ke baad agar final path base_dir ke bahar hai, to reject ho jaata hai. os.path.realpath() converts null bytes, symlinks, and ../ sequences — everything — into an already-resolved, canonical form, so no "surprise" transformation remains left by the time the check runs. Whether the input is ../../etc/passwd, ..%2f..%2fetc/passwd, or etc/passwd%00.jpg — once decoded/resolved, if the final path is outside base_dir, it gets rejected.

LAYER 2 — RAW FILENAMES KI JAGAH OPAQUE ID USE KARO LAYER 2 — USE OPAQUE IDS INSTEAD OF RAW FILENAMES

Jahan possible ho, user se seedha filename lena hi band kar do — iske bajaye ek opaque ID (jaise file=42) use karo jo server-side database mein actual file path se mapped ho. Isse attacker ke paas kabhi file-system syntax control karne ka mauka hi nahi aata. Where possible, stop taking a raw filename from the user altogether — instead use an opaque ID (like file=42) that's mapped server-side, in a database, to the actual file path. This way the attacker never even gets a chance to control file-system syntax.

✅ DEFENSE-IN-DEPTH KE LIYE ADDITIONAL LAYERS ✅ ADDITIONAL LAYERS FOR DEFENSE-IN-DEPTH

Application ko OS-level Principle of Least Privilege ke tehat run karo — agar app ka user account /etc/shadow padhne ki permission hi nahi rakhta, to chahe path traversal ho bhi jaaye, wo file access nahi ho paayegi. Sandbox/chroot environments bhi ek extra layer dete hain jahan process ki file-system visibility hi ek chhote subset tak limited kar di jaati hai. Run the application under OS-level Principle of Least Privilege — if the app's user account doesn't even have permission to read /etc/shadow, then even if path traversal occurs, that file still can't be accessed. Sandbox/chroot environments also add an extra layer, limiting the process's entire file-system visibility to a small subset.

Code Level Fixes: Vulnerable vs. Secure Code ImplementationsCode Level Fixes: Vulnerable vs. Secure Code Implementations

Path Traversal (Directory Traversal) attacks ko rokne ke liye user input par basic string replacement (jaise filename.replace('../', '')) lagana fail ho jata hai kyunki attackers nested sequences (....//), URL encoding (%2e%2e%2f), double encoding (%252e%252e%252f), aur null-byte injections ke zariye ise aasaani se bypass kar lete hain. Sabse secure aur production-grade tareeka hai: (1) Path normalization ke baad verify karna ki canonical path strictly target base directory ke andar hi resolve hota hai (jaise Node.js mein path.resolve + startsWith aur fs.realpathSync), (2) Safe framework primitives use karna (jaise Flask mein send_from_directory aur secure_filename), aur (3) Direct user filenames ke bajaye random IDs ya strict character allowlists use karna. Niche Node.js aur Python (Flask) ke real-world vulnerable code aur unke production-grade secure implementations diye gaye hain: Preventing Path Traversal (Directory Traversal) by relying on simple string replacements (like filename.replace('../', '')) consistently fails because attackers bypass filters using nested traversal patterns (....//), URL encoding (%2e%2e%2f), double encoding (%252e%252e%252f), or alternate separators. The industry gold standard defense is: (1) Resolving canonical paths and validating that the target path strictly starts with the base directory prefix (using path.resolve + startsWith or fs.realpathSync in Node.js), (2) Using battle-tested framework primitives (like Flask's send_from_directory and Werkzeug's secure_filename), and (3) Utilizing indirect ID lookups or strict character allowlists. Below are vulnerable vs. production-grade secure implementations across Node.js and Python (Flask): 

// ==========================================
// 1. Node.js (Express / fs / path)
// ==========================================

const express = require('express');
const fs = require('fs');
const path = require('path');
const app = express();

const PUBLIC_UPLOADS_DIR = path.resolve(__dirname, 'public', 'uploads');

// ❌ INSECURE: Naive path concatenation or flawed string stripping
app.get('/api/view-file', (req, res) => {
    let filename = req.query.file; // e.g. "../../../../etc/passwd"

    // FLAW 1: Weak strip attempt - can be bypassed with "....//....//etc/passwd"
    // filename = filename.replace(/\.\.\//g, '');

    // FLAW 2: path.join() still resolves "../" upward outside the intended directory!
    const targetPath = path.join(PUBLIC_UPLOADS_DIR, filename);

    // VULNERABILITY: An attacker accesses arbitrary files on the filesystem:
    // Request: /api/view-file?file=../../../../etc/passwd
    fs.readFile(targetPath, 'utf8', (err, data) => {
        if (err) {
            return res.status(404).json({ error: 'File not found' });
        }
        return res.send(data);
    });
});


// ✅ SECURE Pattern 1: Canonical Path Boundary Verification (Industry Standard)
app.get('/api/view-file-secure', (req, res) => {
    const filename = req.query.file;

    if (!filename || typeof filename !== 'string') {
        return res.status(400).json({ error: 'Invalid file parameter' });
    }

    // 1. Resolve canonical absolute path
    const safeBaseDir = path.resolve(PUBLIC_UPLOADS_DIR);
    const resolvedPath = path.resolve(safeBaseDir, filename);

    // 2. CRITICAL: Verify resolved path starts with the base directory + separator
    // Adding path.sep prevents prefix confusion (e.g. "/var/uploads-secret" matching "/var/uploads")
    if (!resolvedPath.startsWith(safeBaseDir + path.sep)) {
        return res.status(403).json({ error: 'Access denied: Directory traversal detected' });
    }

    // 3. Symlink Hardening: Ensure symbolic links do not point outside safe directory
    try {
        const realPath = fs.realpathSync(resolvedPath);
        if (!realPath.startsWith(safeBaseDir + path.sep)) {
            return res.status(403).json({ error: 'Access denied: Symlink traversal detected' });
        }

        // Stream the file safely
        const fileStream = fs.createReadStream(realPath);
        fileStream.on('error', () => res.status(404).json({ error: 'File not found' }));
        return fileStream.pipe(res);
    } catch (err) {
        return res.status(404).json({ error: 'File not found' });
    }
});


// ✅ SECURE Pattern 2: Strict Filename Allowlisting (Regex Whitelist)
app.get('/api/download-receipt', (req, res) => {
    const filename = req.query.name;

    // Strict allowlist: Only alphanumeric characters, dashes, and single extension
    // Completely prohibits dots (..), slashes (/ or \), and null bytes (%00)
    const SAFE_FILENAME_REGEX = /^[a-zA-Z0-9_-]+\.(pdf|png|jpg|txt)$/;

    if (!filename || !SAFE_FILENAME_REGEX.test(filename)) {
        return res.status(400).json({ error: 'Invalid filename format. Traversal characters prohibited.' });
    }

    // Safe to use path.basename as additional safeguard
    const safeName = path.basename(filename);
    const finalPath = path.join(PUBLIC_UPLOADS_DIR, safeName);

    return res.sendFile(finalPath);
});

# 2. Python / Flask (os / pathlib / werkzeug)
# ==========================================

from flask import Flask, request, jsonify, send_file, send_from_directory, abort
from werkzeug.utils import secure_filename
import os
import pathlib

app = Flask(__name__)

SAFE_STORAGE_DIR = os.path.abspath(os.path.join(os.path.dirname(__file__), 'safe_storage'))


# ❌ INSECURE: Directly joining user input and opening files
@app.route('/api/view', methods=['GET'])
def view_file_insecure():
    filename = request.args.get('filename', '')

    # VULNERABILITY 1: os.path.join doesn't block directory traversal!
    # If filename is '../../../../etc/passwd', file_path resolves to outside SAFE_STORAGE_DIR
    # VULNERABILITY 2: If filename starts with absolute slash '/etc/passwd',
    # os.path.join discards the first argument entirely!
    file_path = os.path.join(SAFE_STORAGE_DIR, filename)

    try:
        with open(file_path, 'r', encoding='utf-8') as f:
            content = f.read()
        return jsonify({"filename": filename, "content": content})
    except Exception as e:
        return jsonify({"error": "File not found or unreadable"}), 404


# ✅ SECURE Pattern 1: Flask's Built-in send_from_directory (Recommended Standard)
@app.route('/api/download-secure', methods=['GET'])
def download_file_secure():
    filename = request.args.get('filename', '')

    if not filename:
        return jsonify({"error": "Filename parameter is required"}), 400

    # FIX: send_from_directory internally checks for directory traversal
    # and automatically raises a 404/403 NotFound if the path attempts to escape the root directory!
    try:
        return send_from_directory(
            SAFE_STORAGE_DIR,
            filename,
            as_attachment=True
        )
    except Exception:
        abort(404, description="Resource not found or unauthorized path")


# ✅ SECURE Pattern 2: pathlib.Path.resolve() Boundary Check
@app.route('/api/read-safe', methods=['GET'])
def read_safe_file():
    raw_filename = request.args.get('filename', '')

    # 1. Sanitize filename using Werkzeug (strips path separators and relative dots)
    clean_name = secure_filename(raw_filename)
    if not clean_name:
        return jsonify({"error": "Invalid filename"}), 400

    base_dir = pathlib.Path(SAFE_STORAGE_DIR).resolve()
    target_path = (base_dir / clean_name).resolve()

    # 2. Strict Boundary Verification:
    # Ensure target_path is within base_dir (prevents symlink tricks and canonical escapes)
    try:
        target_path.relative_to(base_dir)
    except ValueError:
        # relative_to raises ValueError if target_path is not a subpath of base_dir
        return jsonify({"error": "Security Alert: Directory traversal detected"}), 403

    if not target_path.is_file():

📖 GlossaryGlossary

01 Path Traversal / Directory Traversal
Ek vulnerability jisme attacker ek application ke intended directory se bahar, file-system ke doosre hisson tak pahunch jaata hai. A vulnerability where an attacker reaches parts of the file-system outside an application's intended directory.
02 Dot-Dot-Slash (../) Sequence
Har OS file-system mein ek special instruction jiska matlab hai "current folder se ek level upar jao". A special instruction in every OS file-system meaning "go one level up from the current folder".
03 Canonicalization
Ek path ko uski fully-resolved, absolute, simplified form mein convert karna — jisme saare ../, symlinks, aur relative parts already resolve ho chuke hote hain. Converting a path into its fully-resolved, absolute, simplified form — where all ../, symlinks, and relative parts have already been resolved.
04 Null Byte Injection
Ek bypass technique jisme ek null byte (%00/\0) character daala jaata hai — purane, C-string-based systems isse "string ka end" samajh kar aage ka sab kuch ignore kar dete hain. A bypass technique that inserts a null byte (%00/\0) character — older, C-string-based systems treat this as "end of string" and ignore everything after it.
05 LFI (Local File Inclusion)
Jab Path Traversal se aage badh kar application us file ko sirf padhta hi nahi, balki uske content ko CODE ki tarah "include"/execute bhi kar leta hai (jaise PHP include()). When Path Traversal goes further and the application doesn't just read the file but "includes"/executes its content as CODE (like PHP's include()).
06 RFI (Remote File Inclusion)
LFI jaisa hi, lekin local server file ke bajaye attacker ek REMOTE URL (jo unka apna server hoster hota hai) include karwa deta hai, jisse seedha unka malicious code execute ho jaata hai. Similar to LFI, but instead of a local server file, the attacker gets a REMOTE URL (hosted on their own server) included, directly executing their malicious code.
07 Absolute Path
Ek complete path jo root (/ ya C:\) se shuru hota hai, jaise /etc/passwd — kisi bhi current directory par depend nahi karta. A complete path starting from root (/ or C:\), like /etc/passwd — doesn't depend on any current directory.
08 Symlink (Symbolic Link)
Ek special file jo asal mein kisi doosri file/folder ki taraf "point" karta hai — agar isse handle na kiya jaaye, ye validation checks ko bypass kar sakta hai. A special file that "points" to a different file/folder — if not handled properly, it can bypass validation checks.
09 Chroot Jail / Sandbox
Ek OS-level mechanism jo ek process ki file-system visibility ko ek chhote, restricted subset tak limited kar deta hai — us process ko is "jail" ke bahar kuch dikhta hi nahi. An OS-level mechanism that restricts a process's file-system visibility to a small, limited subset — the process can't see anything outside this "jail".
10 Log Poisoning
Ek technique jisme attacker ek log file mein (jaise User-Agent header ke through) malicious code plant karta hai, fir Path Traversal/LFI se usi log file ko execute karwa deta hai. A technique where an attacker plants malicious code inside a log file (like via the User-Agent header), then uses Path Traversal/LFI to get that same log file executed.
11 Arbitrary File Write
Jab attacker sirf files padh hi nahi sakta, balki path manipulation se koi bhi file kahin bhi WRITE bhi kar sakta hai — often ek webshell ki tarah RCE tak escalate hoti hai. When an attacker can not just read files, but also WRITE a file anywhere via path manipulation — often escalating to RCE via a webshell.
12 URL Encoding / Double Encoding
Special characters ko %XX format mein represent karna (jaise / = %2f) — Double Encoding mein isi encoded value ko DOBARA encode kiya jaata hai, taaki ek hi decode-pass filter ko bypass kiya ja sake. Representing special characters in %XX format (like / = %2f) — Double Encoding encodes this same value AGAIN, to bypass a filter that only decodes once.
13 Allowlist Of Filenames / Opaque ID
User se raw filename lene ke bajaye, ek opaque ID (jaise ek number) accept karna jo server-side ek fixed, safe file path se mapped hota hai. Instead of taking a raw filename from the user, accepting an opaque ID (like a number) that's mapped server-side to a fixed, safe file path.
14 Base Directory Restriction
Ek check jo confirm karta hai ki resolved, final file path hamesha ek specific, intended "base" folder ke ANDAR hi rehta hai — bahar nikalne ki koi bhi koshish reject ho jaati hai. A check confirming the resolved, final file path always stays INSIDE a specific, intended "base" folder — any attempt to escape gets rejected.
15 CVE
Common Vulnerabilities and Exposures — ek unique ID (jaise CVE-2021-41773) jo kisi publicly-known security vulnerability ko diya jaata hai. Common Vulnerabilities and Exposures — a unique ID (like CVE-2021-41773) assigned to a publicly-known security vulnerability.

🤔 Confusing QuestionsConfusing Questions

Ye wo sawaal hain jo Path Traversal samajhne ke baad bhi log ghumte rehte hain — expand karke apna concept clear karo. These are the questions people still get confused about even after understanding Path Traversal — expand each to clear your concepts.

Path Traversal ek general concept hai — application ke intended directory se bahar file-system access pana. LFI (Local File Inclusion) ek SPECIFIC, aur zyada severe outcome hai, jab application us traversed file ko sirf PADHTA nahi, balki uske content ko CODE ki tarah execute bhi kar leta hai (jaise PHP include()). Har LFI mein Path Traversal involve hota hai, lekin har Path Traversal LFI tak escalate nahi hoti — kai baar sirf file READ tak hi limited rehti hai. Path Traversal is a general concept — gaining file-system access outside an application's intended directory. LFI (Local File Inclusion) is a SPECIFIC, and more severe outcome, where the application doesn't just READ the traversed file, but also EXECUTES its content as CODE (like PHP's include()). Every LFI involves Path Traversal, but not every Path Traversal escalates to LFI — many stay limited to just a file READ.

LFI (Local File Inclusion) mein attacker server ki APNI hi disk par maujood ek file ko include/execute karwata hai. RFI (Remote File Inclusion) mein attacker apni khud ki, kisi doosre server par hosted, REMOTE file ko include karwata hai — jisse unka apna, poori tarah controlled malicious code seedha target server par execute ho jaata hai. RFI generally zyada directly dangerous hai kyunki attacker ko file ke content par poora control hota hai, lekin ye sirf tab possible hai jab application remote URLs ko bhi "include" karne deti ho. In LFI (Local File Inclusion), the attacker gets a file that already exists on the server's OWN disk included/executed. In RFI (Remote File Inclusion), the attacker gets their own, REMOTE file (hosted on a different server) included — running their own, fully-controlled malicious code directly on the target server. RFI is generally more directly dangerous since the attacker has full control over the file's content, but it's only possible when the application also allows "including" remote URLs.

Nahi. Jaisa Level 2 mein dikhaya, URL-encoding (%2f) se filter ko easily bypass kiya jaa sakta hai, kyunki check un-decoded string par ho rahi hoti hai. Double encoding, absolute paths (jinme ../ hai hi nahi, jaise seedha /etc/passwd), aur single-pass string-replace ki apni gaps bhi ek naya bypass bana sakte hain. Sahi fix hamesha RESOLVED, CANONICAL path ko check karna hai, raw string ko regex se scan karna nahi. No. As shown in Level 2, URL-encoding (%2f) can easily bypass the filter, since the check runs on the un-decoded string. Double encoding, absolute paths (which don't contain ../ at all, like directly using /etc/passwd), and single-pass string-replace's own gaps can all create a new bypass. The correct fix is always to check the RESOLVED, CANONICAL path, not to regex-scan the raw string.

C-language mein string ka "end" ek null byte (\0) character se maana jaata hai. Kuch purani systems (jaise PHP < 5.3.4, ya C-based file-open functions) is convention ko internally follow karti hain — matlab agar string mein kahin bhi null byte aa jaaye, wo VAHIN "khatam" ho jaati hai, chahe programming-language-level string variable mein uske aage aur characters likhe hon. Isse extension checks (jo poori string dekhti hain) aur actual file-open (jo null byte tak hi ruk jaata hai) mein MISMATCH ho jaata hai — jaisa Level 3 mein dikhaya gaya. In C, the "end" of a string is marked by a null byte (\0) character. Some older systems (like PHP < 5.3.4, or C-based file-open functions) internally follow this convention — meaning if a null byte appears anywhere in the string, it "ends" right THERE, even if more characters are written after it at the programming-language-level string variable. This creates a MISMATCH between extension checks (which look at the whole string) and the actual file-open (which stops at the null byte) — as shown in Level 3.

Haan, kai file-open functions/languages mein agar diya gaya path ek ABSOLUTE path hai (root / se shuru ho raha hai), to wo INTENDED base directory ko poori tarah IGNORE kar deta hai — chahe developer ne base_dir + filename concatenate kiya ho. Agar filename = "/etc/passwd" diya jaaye, to os.path.join("/var/www/uploads", "/etc/passwd") jaisi calls bhi (Python mein) result mein SEEDHA /etc/passwd deti hain, base directory ko ignore karte hue — is behavior ko developers aksar miss kar dete hain. Yes, in many file-open functions/languages, if the given path is an ABSOLUTE path (starting from root /), it completely IGNORES the INTENDED base directory — even if the developer concatenated base_dir + filename. If filename = "/etc/passwd" is given, calls like os.path.join("/var/www/uploads", "/etc/passwd") (in Python) actually return just /etc/passwd, ignoring the base directory entirely — developers often miss this behavior.

Attacker pehle koi field (jaise User-Agent HTTP header) ek malicious script (jaise PHP code) se set karta hai — server automatically ye header apne ACCESS LOG file mein likh deta hai (bina execute kiye, sirf ek text entry ki tarah). Agar application mein ek separate feature Path Traversal ke saath ek file ko "include" (execute) kar sakta hai, attacker use isi log file ki taraf point kar deta hai — is baar file ka content EXECUTE ho jaata hai, matlab attacker ka planted code chal jaata hai. Isi combination ko "Log Poisoning to RCE" kehte hain. The attacker first sets a field (like the User-Agent HTTP header) to a malicious script (like PHP code) — the server automatically writes this header into its ACCESS LOG file (without executing it, just as a text entry). If the application has a separate feature that can "include" (execute) a file via Path Traversal, the attacker points it at that same log file — this time the file's content gets EXECUTED, meaning the attacker's planted code runs. This combination is called "Log Poisoning to RCE".

Agar ek defense sirf RAW STRING prefix check karti hai (na ki symlink-resolved real path), to attacker (agar unhe kisi bhi tarah base directory ke ANDAR ek file/symlink create karne ka mauka mile, jaise upload feature se) ek symlink bana sakta hai jo apparently base directory ke andar dikhta hai, lekin actually kisi bahar wali file/folder ki taraf POINT karta hai. STRING prefix check pass ho jaata hai (kyunki symlink ka apna naam base directory ke andar hai), lekin file ACTUALLY open hone par, OS us symlink ko FOLLOW kar leta hai aur bahar wali file tak pahunch jaata hai. Isiliye canonicalization (realpath()) itni zaroori hai — ye symlinks ko bhi resolve kar deti hai check karne se pehle hi. If a defense only checks a RAW STRING prefix (not the symlink-resolved real path), an attacker (if given any way to create a file/symlink inside the base directory, like via an upload feature) can create a symlink that appears to be inside the base directory, but actually POINTS to a file/folder outside it. The STRING prefix check passes (since the symlink's own name is inside the base directory), but when the file is ACTUALLY opened, the OS FOLLOWS that symlink and reaches the outside file. This is exactly why canonicalization (realpath()) matters so much — it resolves symlinks too, before the check even runs.

Linux/Unix mein path separator forward-slash / hai, isliye standard payload ../../etc/passwd jaisa hota hai. Windows mein path separator backslash \ hai (halaanki bahut saare Windows APIs forward-slash bhi accept kar lete hain), isliye payloads ..\..\windows\win.ini jaisa bhi ho sakte hain. Isliye jo filter sirf ek variant (jaise sirf /) block karta hai, wo doosre OS ke context mein incomplete ho sakta hai — tester ko dono variants try karne chahiye. On Linux/Unix, the path separator is forward-slash /, so a standard payload looks like ../../etc/passwd. On Windows, the path separator is backslash \ (though many Windows APIs also accept forward-slash), so payloads can also look like ..\..\windows\win.ini. A filter that only blocks one variant (like just /) can be incomplete in the other OS's context — a tester should try both variants.

Nahi. Jaisa Level 3 mein dikhaya, extension check sirf FULL STRING dekhta hai, jabki actual file-open operation kabhi-kabhi (null byte, ya kuch specific parsing quirks ki wajah se) STRING KE EK CHHOTE HISSE par hi kaam karta hai. Extension check hamesha ek ADDITIONAL layer honi chahiye, primary defense (canonicalization + base-directory check) ka substitute nahi. No. As shown in Level 3, the extension check only looks at the FULL STRING, while the actual file-open operation sometimes (due to a null byte, or certain specific parsing quirks) only acts on a SMALLER PART of the string. An extension check should always be an ADDITIONAL layer, not a substitute for the primary defense (canonicalization + base-directory check).

Canonicalization ek path ko uski SIMPLEST, FULLY-RESOLVED, ABSOLUTE form mein convert karne ka process hai — saare ../, ./, aur symlinks ko already-resolve karke, sirf ek final destination path chhodta hai. Jab check is CANONICAL path par hota hai (na ki raw, un-resolved string par), to koi bhi encoding trick, single-pass replace flaw, null byte, ya symlink — sab already "expose" ho chuke hote hain check hone se pehle hi. Isliye canonicalization structural fix hai: ye validation aur actual use ke beech ka GAP hi khatam kar deta hai. Canonicalization is the process of converting a path into its SIMPLEST, FULLY-RESOLVED, ABSOLUTE form — resolving all ../, ./, and symlinks already, leaving only a final destination path. When the check runs on this CANONICAL path (not the raw, unresolved string), any encoding trick, single-pass-replace flaw, null byte, or symlink has already been "exposed" before the check even runs. This is why canonicalization is a structural fix: it eliminates the very GAP between validation and actual use.
