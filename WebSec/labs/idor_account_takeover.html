🛡️ Technical Root Cause & Secure Architecture

Why accepting Object IDs in state-changing update requests causes critical Broken Object Level Authorization (BOLA).

❌ Vulnerable Code (Trusting Client-Supplied user_id) Node.js / Express 
// ❌ Fatal IDOR: Reading user_id from req.body
app.post('/api/v1/users/update-email', requireAuth, async (req, res) => {
    const { user_id, new_email } = req.body;

    // 🚨 BUG: The server updates whoever's user_id is in the JSON payload!
    // It verifies that Om is logged in, but NEVER verifies that
    // req.user.id === user_id!

    return res.json({ success: true, message: "Email updated successfully" });
});
✅ Secure Code (Binding Session User & Re-Authentication) Node.js / Express 
// ✅ Secure: Enforce server-side session identity exclusively
app.post('/api/v1/users/update-email', requireAuth, async (req, res) => {
    const { new_email, current_password } = req.body;

    // 1. Enforce ID strictly from cryptographically signed session/JWT
    const authenticatedUserId = req.user.id; // NEVER req.body.user_id!

    // 2. Require current password re-confirmation for sensitive changes
    const user = await db.User.findById(authenticatedUserId);
    const valid = await bcrypt.compare(current_password, user.passwordHash);
    if (!valid) return res.status(401).json({ error: "Invalid password confirmation" });

    // 3. Send verification link to OLD email before committing change
    await db.User.findByIdAndUpdate(authenticatedUserId, { email: new_email });
    return res.json({ success: true });
});
