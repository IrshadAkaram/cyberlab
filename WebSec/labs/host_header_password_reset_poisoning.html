How Password Reset Poisoning works: When users request a password reset, the server needs to construct an absolute URL to email the victim. In flawed architectures, the backend dynamically prepends "https://" . $_SERVER['HTTP_HOST'] instead of reading a hardcoded base URL from configuration.

When an attacker substitutes their own domain (evil-attacker.net) into the Host or X-Forwarded-Host header, the server unwittingly generates an official email pointing directly to the attacker's server with the legitimate high-entropy secret token attached! 

// ❌ VULNERABLE PHP BACKEND
$token = bin2hex(random_bytes(16));
$reset_url = "https://" . $_SERVER['HTTP_HOST'] . "/auth/reset?token=" . $token;
mail($email, "Reset Password", "Click here: " . $reset_url);

// ✅ SECURE PHP BACKEND (HARDCODED CONFIG)
$token = bin2hex(random_bytes(16));
$base_url = Config::get('app.url'); // Hardcoded 'https://portal.enterprise.com'
$reset_url = $base_url . "/auth/reset?token=" . $token;
mail($email, "Reset Password", "Click here: " . $reset_url);

Bug Bounty Hunting Methodology:

  • Always test password resets with your own Collaborator/Burp server domain in the Host header.
  • If modifying Host triggers a 404 or connection reset from the load balancer, inject X-Forwarded-Host: collaborator.net.
  • Test duplicate Host headers: Load balancers like HAProxy may route on the first, while backend servers (like Apache/PHP) read the second!
  • Check for port tricks: Host: target.com:@attacker.com or Host: target.com:1337.
