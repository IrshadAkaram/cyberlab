🔍 How This Attack Works

  • XSS delivers the payload

    Attacker finds an XSS vulnerability (stored comment, reflected param, malicious ad script). One line of injected JS is enough to start the attack.

  • CSRF token read from DOM

    Since the payload runs on the same origin, it has full DOM access. It reads input[name="csrf_token"] — the same protection meant to stop CSRF attacks.

  • fetch() with credentials:include

    The browser attaches the victim's session cookies to the request automatically. The server receives a perfectly valid, authenticated, CSRF-token-bearing request — indistinguishable from a real user action.

  • Victim never notices

    No redirect. No popup. No UI change (until the balance drops). The whole attack takes milliseconds and leaves no obvious trace.

🛡 Real Defenses
🧱

Fix XSS First

This entire attack requires XSS as an entry point. Escaping output and using strict CSP headers eliminates the attack surface entirely.

🔐

Re-auth for Sensitive Actions

Require password/OTP re-entry for transfers, email changes. Even with a valid session, the attacker can't supply the user's password.

📍

Double Submit + Origin Check

Verify the Origin header server-side and require CSRF tokens to be sent in a custom header (not just form field) — harder for XSS to forge.

⏱

Anomaly Detection

Flag transfers that happen within seconds of page load, or that differ from normal user behavior patterns — bot-like timing is a giveaway.
