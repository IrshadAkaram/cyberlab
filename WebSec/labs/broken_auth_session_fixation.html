🔍 Technical Mechanics: How Session Fixation Enables Account Hijacking

In a secure authentication workflow, the server must regenerate the session identifier immediately upon user authentication. Session Fixation occurs when an application accepts a session ID provided by an unauthenticated client (or via URL query parameters) and continues to reuse that same session ID after the user successfully logs in.

Because the attacker already knows the session ID (having pre-seeded or fixed it), as soon as the privileged victim logs in, the session token is upgraded to an authenticated admin session on the server. The attacker, still holding that exact same session token, refreshes their browser and immediately inherits all administrative powers.

❌ Vulnerable Login Handler (No Rotation)
// login.php — Flawed session management
<?php
  session_start(); // Accepts pre-set session ID from cookie/URL

  if (verify_credentials($_POST['user'], $_POST['pass'])) {
      // VULNERABLE: Binds user data to existing session
      // without generating a brand new session ID!
      $_SESSION['authenticated'] = true;
      $_SESSION['user_id'] = $user['id'];
      $_SESSION['role'] = $user['role']; // Attacker session now elevated!
      header("Location: /dashboard.php");
  }
?>
✅ Secure Login Handler (With Session Rotation)
// login.php — Hardened session rotation
<?php
  session_start();

  if (verify_credentials($_POST['user'], $_POST['pass'])) {
      // SECURE: Immediately invalidate old session and issue new token!
      session_regenerate_id(true);

      $_SESSION['authenticated'] = true;
      $_SESSION['user_id'] = $user['id'];
      $_SESSION['role'] = $user['role'];

      // Enforce strict cookie flags (prevent URL session passing)
      // ini_set('session.use_only_cookies', 1);
      header("Location: /dashboard.php");
  }
?>
