What is Web Cache Poisoning? Caching reverse proxies (like Cloudflare, Varnish, Akamai) sit in front of web applications to reduce server load. They determine whether a request has already been cached using a subset of the request called the Cache Key (typically HTTP Method + Path).

If the backend server dynamically reflects headers that are not included in the cache key (unkeyed inputs such as X-Forwarded-Host or Host), an attacker can poison the cache with malicious script imports, triggering Stored XSS against every innocent visitor!

Keyed vs. Unkeyed Headers: 

// Cache Key Configuration:
Cache-Key: {Method: GET, Path: /}

// Incoming Request:
GET / HTTP/1.1
Host: cloud-portal.io
X-Forwarded-Host: evil-cdn.org  <-- UNKEYED INPUT (Ignored by Cache, read by Backend!)

// Backend Response:
HTTP/1.1 200 OK
<script src="//evil-cdn.org/assets/main.js"></script>
// Stored in CDN cache under Cache-Key: GET / for the next 3600 seconds!

Defensive Architecture:

  • Strip or sanitize incoming forwarding headers (X-Forwarded-Host, X-Host) at the proxy boundary before forwarding requests internally.
  • Never reflect client-supplied host values into HTML script tags, asset imports, or canonical link headers.
  • If host-specific caching is required, add the Host header to the proxy's Cache Key configuration!
